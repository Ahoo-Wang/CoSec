## 0. 结论先行

第 5 阶段结束时，数据面已经是"读快照 → 纯函数决策 → 义务与监听器"，但写入一侧还停在第 3 阶段：任何拿到 `SnapshotPublisher` 的代码都能改策略，
写入不经授权，没有修订链，也没有发布前的影子比较。本阶段把写入一侧补成控制面，它是快照文档唯一的写入者：

```
变更请求 = 基准修订 + 条目级操作
    → 授权（谁能写这里）→ 校验 → 编译（与数据面同一个编译器）→ 授出分析（不能越权授权）
    → 影子窗口（数据面在真实流量上比较基准与候选）→ 必要时审批 → 发布（一次 putIfMatch）→ 修订记录
```

- **已发布的快照文档就是存储的权威**（§5）。不另设"策略库"：控制面的存储由已发布的快照文档（头）、只建不改的**修订记录**（按摘要寻址，经文档头里的
  `parent` 指针连成链）、**变更请求**以及它们的索引组成，都在 CoCache 8 的 `Store` 上，写入一律是条件写；发布只对一个 key 做比较并交换，
  数据面看到的永远是某一个完整修订（P7）。回滚就是把一条旧记录作为新修订重新发布，同样走完整流程。
- **编译失败保留旧版本，在源头上成立**（§6.3）。控制面用数据面的编译器、对完整的组合快照编译候选文档，有任何 `Broken` 条目就拒绝发布；
  头没有被写，每个实例都继续用上一个修订。数据面自己的 F5（RFC 0003 §4.4）仍是失败即拒绝：在数据面回退到旧版本会让一条已发布的 DENY 被静默忽略（§3 M2）。
- **影子窗口默认强制**（§6.4）。候选文档写进单独的命名空间，数据面在采样请求上用它再评估一次，按实例汇总差异；窗口达到最短时长和最少样本后关闭，
  发布者必须按数字确认差异。跳过窗口需要单独的权限，并记入审计（§3 M1）。
- **控制面用同一个引擎保护自己**（§7）。控制面的动作是 `cosec:*` 命名空间的 `service:verb`，资源是文档、条目和作用域；检查经 `AuthorizationChecker`
  在刚确认过的快照上进行，另有一条不经策略的硬性规则：租户的主体只能写自己租户的文档。
- **不能越权授权**（§7.4）是 RFC 0001 §7.1 那条决定的可执行版本：把一次变更拆成"授出的语句片段"，每一片必须被授权者自己的**某一条** ALLOW 包含——
  适用范围覆盖、动作与资源模式包含（RFC 0005 §5.5）、条件蕴含（RFC 0005 §4.2 的 `implies`，先把授权者自身的属性代换成常量），并且不与授权者
  受到的非 `Anyone` DENY 重叠。判断不了的进入审批，从不按"大概包含"放行。语义定义和可靠性论证都写出来，由性质测试 A5–A8 守护。
- **信任根与审批**（§7.3、§7.5）：信任根是平台租户中持有 `cosec:approve` 的人；工作负载的凭据（API key、服务自己的身份）从不是信任根，也从不批准；
  经服务配置（服务端口与门面）没有人是信任根。审批是另一个人对候选摘要的批准，发布时再核实一次。
- **平台边界**（§7.6）：租户文档的 `boundary` 字段（只有平台能写）或平台的默认边界指向一条平台策略；引擎在得到 Permit 之后检查请求是否落在边界之内。
  没有边界数据时这一步是恒等的。
- **break-glass**（§8）只能经控制面创建：主体是平台租户的主体，双人（申请人与批准人不同），有上限的有效期（默认 4 小时，至多 24 小时），创建前必须有一个
  `REQUIRED` 的控制面审计监听器写入成功；使用仍按 RFC 0006 §9.4.3 写 `REQUIRED` 审计。
- **租户自助**（§9）：租户写自己的 `Tenant(T)` 文档，可以引用平台策略和应用目录里的权限策略；平台层、边界、break-glass 不可写。
  DENY 上的 `onMissing: nomatch` 经显式确认后可以写在任何文档里。
- **API**（§10）：一个挂起函数的库 `ControlPlane`；starter 在类路径上有 `cosec-control` 时提供 HTTP 路由，并可以另开一个只服务服务配置的端口；
  控制面宿主镜像 `cosec-control-server` 是只做这件事的应用。应用经门面 `ControlService` 调用控制面：进程内的 `LocalControlService`，或经 HTTP 调控制面宿主
  服务端口的 `HttpControlService`，两者走同一条路由的代码路径；其上是类型化的 `ControlClient`。控制请求没有自己的期限：期限是调用方的，经取消到达（§10.2）。
  `schema/<line>/*.schema.json` 从 `cosec-document` 里的文档格式描述生成，`check` 校验提交的文件没有过期。
- **门槛 D**（§12）已由 [RFC 0008](0008-conformance-and-direct-build.md) 的规范一致性套件取代；本阶段的性质（P-B1–P-B3、发布往返）作为规范性质保留。
- 实现按 §16 的 PR 划分合入，都已完成；29 项决定见 §17（2026-10-26 全部按推荐确认），其后的决定写在它们所改的章节里。

## 1. 范围与非目标

### 1.1 本阶段要做的

1. `cosec-control`（§5.1）：`ControlPlane`、变更请求、发布流程、授出分析、审批、break-glass、回滚、声明式 `apply`、`simulate`/`explain`/`analyze`。
2. `ControlStore` 端口与基于 CoCache 的实现（`cosec-cocache`）：修订记录、修订索引、变更请求、候选文档、反向引用索引（§5.2）。
3. 发布前的校验与编译（§6.2、§6.3），包括 RFC 0005 推迟到这里的成本上限与 `Catalog` 校验。
4. 影子窗口（§6.4）：候选文档的分发、数据面读取候选、影子报告与汇总、窗口判定与确认。
5. 控制面写操作的授权（§7.1–§7.3）与不能越权授权（§7.4）、审批（§7.5）。
6. 平台边界与 `withinBoundary`（§7.6），涉及 `engine` 与文档编译。
7. break-glass（§8）、租户自助的规则与隔离检查（§9）、DENY 上 `onMissing: nomatch` 的确认（§9.5）。
8. 控制面审计事件与变更监听器（§10.5），Kafka 实现。
9. 从文档格式描述生成 JSON schema（§10.4）。
10. `cosec-migrate bootstrap`、`restore`（§5.9）；`cosec-migrate publish` 经控制面的存储写入。
11. 控制面的 HTTP 路由、服务端口与门面 `ControlService`（§10.2），控制面宿主镜像。
12. JMH 与控制面延迟测量（§14）。
13. 删除 `SnapshotPublisher`、`RedisSnapshotPublisher`、`LocalPolicyInitializer` 的写库模式、`PolicyHistory` 与两个 `PolicyRevisionStore`、
    `ShadowPolicyProvider` 与本地影子文件、`cosecExplain` actuator 端点（随 RFC 0008 的切换完成）。

### 1.2 非目标

| 内容 | 处理 | 留到 |
|---|---|---|
| 管理界面（UI） | 不做。HTTP API 是 UI 的后端，UI 由应用自建 | — |
| 文档签名（防止拿到 Redis 写权限的人伪造文档） | 不做。拥有 Redis 写权限的一方在威胁模型之外，与 7.x 相同；靠 Redis ACL 限制写入方（§11） | 8.0 之后，单独的 RFC |
| 修订记录的长期归档（对象存储、数据库） | 不做。只在 Redis 中按数量与时间保留（§5.7） | 有需求时加一个 `RevisionArchive` SPI |
| 跨租户的数据面访问（平台人员以某租户的身份调用业务接口） | 不做。与 RFC 0004 §4.3 相同：主体只读自己租户的文档 | — |
| GraalVM native image | 不支持（RFC 0001 §3.10） | 8.0 之后，只针对 `cosec-gateway-server` |
| 发布 8.0 | 不在本文。RC 与 GA 的条件见 RFC 0008 §3.9，由维护者决定 | — |

控制面可以嵌入管理服务（库），也可以作为独立的控制面宿主运行（`cosec-control-server`，维护者 2026-11-21 决定；§3 M9 下的说明、§10.2）。

**本阶段不改变任何数据面决策**（Permit / Deny / Indeterminate 的划分、状态码、做出决策的语句）。改变的是写入一侧、可观测性输出（§15）和 API。
没有边界数据时平台边界是恒等的（P-B1，§7.6）。

## 3. RFC 0001 中与第 6 阶段有关的不一致

与 RFC 0003 §2、RFC 0004 §3、RFC 0006 §3 一样，不悄悄选边，逐条列出，每条对应 §17 的一个决定。

| # | 合订前的 RFC 0001（`git show b164f273:docs/rfc/0001-target-architecture.md`） | 问题 | 本文的处理 |
|---|---|---|---|
| M1 | §3.7："发布前强制：Schema 校验 → 编译 → 引用完整性检查 → **可选的**影子窗口"；§6 第 6 阶段："发布流程**强制**校验 + 编译 + 影子窗口" | 影子窗口是可选还是强制，两处相反。完全强制又有两个问题：低流量的租户可能永远攒不够样本；紧急的 DENY 和 break-glass 不能等十几分钟 | 默认强制。跳过需要 `cosec:skip-shadow` 权限并写明原因（记入修订记录与审计）；break-glass 的创建与撤销按种类免除；达不到样本数的窗口在最长时长后关闭，发布者必须确认"证据不足"（§6.4）。Q1 |
| M2 | §3.4（数据面）："数据面……编译失败就保留旧版本并告警" | RFC 0003 Q8 已说明：在数据面回退意味着请求按比已发布的头更旧的修订决策，一条刚发布的 DENY（例如紧急封禁）会被静默忽略。RFC 0003 把它推迟到第 6 阶段，理由是"控制面在发布前编译之后再引入"——但发布前编译之后，数据面的编译失败只剩一种来源：实例与控制面的版本或配置不一致（缺 hint、缺属性提供者、代码版本不同），这时回退同样不安全 | "保留旧版本"在源头上实现：编译失败的候选不发布，头不变，所有实例照常使用上一个修订（§6.3）。数据面的 F5 保持失败即拒绝，告警指明"控制面接受、本实例拒绝"（`cosec.snapshot.loads{result=incompatible}`）。Q2 |
| M3 | §3.7："`PolicyStore`：……修订历史、回滚——现有 `policy/history` 搬过来" | 现有历史按**策略**记录，写在策略**之后**、与策略分属不同的 Redis key（`PolicyHistory` 的 `VersionedPolicyRepository`）：写入成功而追加历史失败时历史缺一条；绑定、目录、应用权限的变化根本没有历史；也无法回答"某次决策时三份文档各是什么"（RFC 0001 §3.3 的解释要求）。快照模型里发布的单位是文档 | 修订按**文档**记录，记录先于头写入、按摘要寻址，头里带 `parent` 指针（§5.3、§5.4）。按策略的历史是相邻修订的差异视图。现有代码不搬，删除。Q3 |
| M4 | §3.7："子集检查**在编译期**对策略做静态包含判断；判断不了的（**例如带条件的语句**）一律拒绝" | 与 §7.1 的决定不一致：§7.1 允许"授权者的条件 AND 额外条件"，并把"其余"送去审批而不是拒绝。另外，包含判断需要知道授权者是谁、有什么权限，快照编译器不知道这些 | 以 §7.1 为准（它是后来确认的决定）。检查在控制面的发布流程中进行，不在快照编译器里（§7.4） |
| M5 | §3.7："被授出的动作和资源必须是授权者本人**在同一作用域内拥有的权限**的子集" | 没有定义：① 授权者的权限按哪个快照、成员关系从哪里来；② 授权者受到的 DENY 算不算；③ 修改一条已被绑定的策略、或把策略设为可附加，是不是"授出"；④ 条件中引用主体自身属性（`subject.id`）时，"同一条件"对授权者和被授权者含义不同 | 给出语义定义（§7.4.2）：被授权者能做的每个请求，换成授权者本人发出时必须在当前快照下被允许。①当前发布的快照、授权者本次请求的成员关系；②非 `Anyone` 绑定的 DENY 计入（Q8 的备选：全部计入）；③是授出（§7.4.1）；④先把授权者自身的属性代换成常量（§7.4.3） |
| M6 | §7.1："DENY 在授权者有写权限的作用域内一律允许；其余拒绝并进入平台管理员审批" | 没说**删除或放宽 DENY**（这是放宽访问）与**删除 ALLOW、绑定**（这是收窄）。按字面，前者属于"其余"，每删一条租户自己写的 DENY 都要平台审批；后者也是"其余"，连撤销一个角色绑定都要审批 | 收窄（删除绑定、删除或收窄 ALLOW、新增 DENY）在有写权限的作用域内一律允许。删除或放宽 DENY 在有写权限的作用域内允许，租户文档里没有受保护的条目（`CTL-87`）；租户层删掉自己的 DENY，结果仍受平台层的 DENY 与边界约束（§7.4.4）。Q9 |
| M7 | §3.2、§3.7：break-glass 绑定"**只能由控制面创建**"、"只能由平台管理员创建" | 数据面编译器读到一份文档时不知道是谁写的，这条约束无法在数据面上检查；RFC 0004 §8.4 的转换工具也会生成 root 绑定 | 约束由"控制面是快照文档唯一的写入者"（PR-11 删除其他写入路径，ArchUnit 守护）加上 Redis ACL 实现；绑定带 `grantedBy`/`approvedBy`/`change` 元数据，编译器检查它们存在且两人不同；转换工具生成的 root 绑定在 `publish` 时受同样的期限上限（§8）。Q12 |
| M8 | §3.7："平台层可以给**每个租户**设一条边界策略，租户内的任何 Permit 都必须同时落在边界之内" | 没说：存在哪里（逐租户写进 `Platform` 文档会让它随租户数增长，RFC 0004 的平台文档常驻每个实例）；是否约束平台层授出的 Permit 与 break-glass；边界策略里能不能有 DENY | 平台文档放一条默认边界，租户文档的 `boundary` 字段（只有平台能写）覆盖它；约束该租户主体的**全部** Permit（包括平台层授出的）；平台租户不能有边界，break-glass 的主体只能是平台租户的主体，所以不受边界影响；边界策略只能有 ALLOW（§7.6）。Q11 |
| M9 | §4：`cosec-control` 依赖 "engine, runtime"，"自身的写操作经 Pipeline 授权"，来自"`policy/history`、生成器 endpoint" | ① Pipeline 按 HTTP 路径授权，而控制面写的是请求体里点名的文档、条目和作用域，路径级的授权表达不了；② 控制面还要文档编解码与编译器，它们在 `cosec-core`（RFC 0004 Q10、RFC 0006 Q5）；③ 生成器端点读宿主自己的 OpenAPI，放进控制面就要求控制面与业务服务同进程 | Pipeline 负责认证和粗粒度的路径授权，细粒度的授权在控制面内部经 `AuthorizationChecker`（RFC 0006 §7.6）逐个目标检查（§7.2）；`cosec-control` 依赖 `cosec-core`、`runtime/`、`engine/`、`model/`；生成器端点留在 starter，它们的输出是 `apply` 的输入（§6.7）。Q7 |
| M10 | §3.1 图："`STORE`（PolicyStore 版本化, CAS）-- CoCache 失效广播 --> `SnapshotSource`" | 读起来像有一个独立的策略库，再由它生成快照。RFC 0003/0004 已经让快照文档成为 Redis 中的权威存储（`PolicySnapshotCache`，`ttl = null`、读失败抛出）。再加一份权威数据，就要在两者之间同步，正是 D4 的形状 | 已发布的快照文档就是头；修订记录和变更请求是辅助数据，丢了也不影响数据面（§5.2）。Q4 |
| M11 | §3.7："`schema/*.schema.json` 由**模型代码**生成" | `model/` 只依赖标准库（RFC 0002、RFC 0004 Q10），文档用 `cosec-core` 里手写的 Jackson 流式代码编解码，没有可供反射的数据类，模型类的形状也不等于 JSON 的形状 | 在 `cosec-core` 中增加一份声明式的**文档格式描述**，生成 schema 并用一致性测试把它和编解码器绑在一起（§10.4）。Q19 |

上表照录合订前的 RFC 0001 与当时的处理；之后变了的几项，今天的处理以正文为准：

- **M2**：本实例编译失败今天记为 `cosec.snapshot.compile.duration{result=failure}`（`cosec-micrometer`），没有名为 `cosec.snapshot.loads{result=incompatible}` 的指标值。
- **M7**：数据面编译器检查 break-glass 绑定的 `grantedBy`/`approvedBy`/`change` 元数据的规定已取消（RC1-27）：两人原则由控制面对每种变更强制（`BRK-5`），
  修订的出处记录作者与批准人；`cosec-migrate` 不写任何 break-glass 绑定（§8）。
- **M9**：控制面的依赖今天是 `runtime`、`document`、`spi`、`engine`、`model`（`cosec-core` 已拆分，RFC 0011）；除了嵌入应用，控制面也作为独立的
  控制面宿主运行（`cosec-control-server`，§1.2、§10.2）。
- **M11**：文档格式描述在 `cosec-document`（§10.4）。
- **M12**：今天的规则是 `test/architecture` 的 `RuntimeBoundaryTest`、`ControlBoundaryTest` 与 `SourceRulesTest`：Reactor 只在边缘适配器与宿主中
  （以及 `cosec-cocache` 的响应式 Redis 客户端，从不出现在它的公开签名里），`model`、`engine`、`spi`、`document`、`runtime`、`control` 不引用 `reactor.*`。

## 5. 模型：`PolicyStore`、修订与回滚

### 5.1 模块与依赖

```
model ← engine ← spi ← document ← runtime ← control（cosec-control）
                                    ↑            ↑
cosec-cocache（CoCacheControlStore，经 compileOnlyApi 实现 control 的端口）    cosec-spring-boot（类路径上有 cosec-control 时装配）
control-sdk（ControlService 门面，只依赖 api、spi、document）← control-http（HttpControlService）
```

| 模块 | 内容 | 理由 |
|---|---|---|
| `model` | `implies`（RFC 0005 §4.2）被控制面调用 | 纯函数 |
| `engine` | `withinBoundary`（§7.6）；动作与资源模式的包含判断（§3.1 N7，`PatternContainment`；语义见 RFC 0005 §5.5） | 都是纯函数，模式实现（`HttpPathPattern`）在这里 |
| `document` | 文档格式：`provenance`、`boundary`、`boundaries`、`limits`、`attributes`（§5.3、§7.6、§3.1 N3）；编译器的规则（N1、N2、§9.5）；文档格式描述与 schema 生成（§10.4） | 编解码与编译器在这里；数据面和控制面必须用同一个编译器 |
| `spi` | 影子候选与报告的端口（`CandidateStore`、`ShadowReportSink`、`ShadowReportReader`） | 数据面与控制面都用，签名只需要模型 |
| `runtime` | 数据面读取候选文档、记录影子比较（§6.4） | 影子在数据面的请求路径上 |
| `control` | `ControlPlane`、变更请求、发布流程、授出分析、审批、break-glass、`apply`、`simulate`/`explain`/`analyze`、`ControlStore` 端口、`ChangeListener` 端口、HTTP 路由的处理（`ControlHttp`）、进程内的门面实现 `LocalControlService` | 只有控制面用到的东西；不引用 Spring、Reactor、Redis 客户端（`ControlBoundaryTest`） |
| `control-sdk` | 门面 `ControlService`、`ControlCaller`、类型化的 `ControlClient`（§10.2） | 应用调用控制面的接口；不依赖 `runtime` 与 `control`，只调用控制面宿主的应用两者都不用带 |
| `control-http` | `HttpControlService`：经 HTTP 调控制面宿主的服务端口（§10.2） | 一种技术一个模块 |
| `cosec-cocache` | `CoCacheControlStore`、影子报告与候选的存储 | CoCache 的实现都在这里；不依赖 `runtime`，只经列出的端口触及 `control` |
| `cosec-kafka` | `KafkaChangeListener` | 与 `KafkaAuditListener` 同一模块 |
| `cosec-spring-boot` | 类路径上有 `cosec-control` 时装配 `ControlPlane`、HTTP 路由与服务端口（§10.2） | 应用只在需要时引入控制面 |
| `cosec-migrate` | `bootstrap`、`restore`、`repair-references`；`publish` 经控制面的存储写入（§5.9） | 唯一在控制面之外写存储的工具 |
| `cosec-control-server` | 控制面宿主镜像（`platform/control-server`）：starter 加控制面，别无他物 | 不嵌入应用的部署（§10.2） |

### 5.2 数据

`ControlStore` 的 Redis 实现是 `cosec-cocache` 的 `CoCacheControlStore`，建在 CoCache 8 的 `Store` 上。条件写（`putIfMatch`）只对一个 key 做比较并交换；
条件删除（`deleteIfMatch`）让候选的撤回与租约的释放只删自己写的那一个（`CTL-26`）。摘要是 SHA-256，写作 `SHA-256:<64 位十六进制>`：修订记录的 key、
修订索引、`provenance.parent.digest`、变更的 `base.digest` 与 `checkedWith` 都用它。

| 数据 | CoCache 缓存 | Redis key（`<p>` 是 key 前缀） | 写入 | 读者 | 丢失的后果 |
|---|---|---|---|---|---|
| **头**：已发布的快照文档 | `PolicySnapshotCache`（RFC 0003 §4.1） | `<p>:snapshot:platform`、`…:app:<a>`、`…:tenant:<t>` | 只有控制面（以及 `cosec-migrate`）；条件写（期望 = 基准摘要） | 数据面、控制面 | 失败即拒绝 |
| **修订记录** | `RevisionRecordCache` | `<p>:control:revision:<docKey>:SHA-256:<hex>` | 控制面；只建不改 | 控制面 | 历史、回滚、按版本解释不可用；数据面不受影响 |
| 修订索引 | `RevisionIndexCache` | `<p>:control:revisions:<docKey>` | 控制面；条件写 | 控制面 | 可从头沿 `parent` 链重建（§5.4） |
| 变更请求 | `ChangeRequestCache` | `<p>:control:change:<changeId>` | 控制面；条件写的状态转换 | 控制面 | 进行中的变更丢失，已发布的不受影响 |
| 未结束变更的集合 | `ControlChangeSetCache` | `<p>:control:changes:doc:<docKey>`、`…:state:<状态>` | 控制面；逐个加入与摘除成员 | 控制面 | 见 §5.7 |
| 文档集合 | `ControlDocumentSetCache` | `<p>:control:documents:all` | 控制面 | 控制面 | 可从各个头重建 |
| app 列表 | `ControlAppListCache` | `<p>:control:apps:all` | 控制面 | 控制面的授出分析（§7.4.3） | 授出分析把所有 app 当作未读（UNKNOWN），fail closed |
| 暂存槽 | `StageCache` | `<p>:control:stage:<docKey>` | 控制面；条件写占用 | 控制面 | 见 §5.5 |
| 候选文档 | `CandidateCache` | `<p>:candidate:<docKey>` | 控制面 | 数据面 | 影子窗口没有样本；决策不受影响 |
| 已暂存候选的清单 | `CandidateStagedCache` | `<p>:candidate-staged:all` | 控制面 | 数据面 | 见 §6.4 |
| 影子报告与实例状态 | `ShadowReportCache` 等（有 TTL） | `<p>:shadow:report:<window>:<instance>`、`…:reporters:<window>`、`…:status:<instance>`、`…:resident:<instance>`、`…:instances:all` | 数据面实例，各写各的 key | 控制面 | 窗口证据不足，需要重跑 |
| 反向引用索引 | `ReferenceIndexCache` | `<p>:control:refs:<docKey>:<policyId>`（集合） | 控制面；逐个加入与摘除成员 | 控制面 | 可从各个头重建（§5.8） |
| 租约 | `ControlLeaseCache` | `<p>:control:lease:<name>` | 控制面；条件写，带期限 | 控制面 | 一次维护任务可能由两个实例做 |

- **头是唯一的权威**（§3 M10，Q4）。数据面只读头；其余数据都可以丢失而不影响任何决策。
- 除影子报告与实例状态外，这些缓存都是"记录"：永不过期、读失败抛出、删除失败抛出，由 `CoSecCacheSpecs.locks` 在任何 customizer 与属性之后固定
  （`CacheTtlPolicyTest`、`StrictCacheFailureTest`）。修订记录与变更请求不是数据面的策略数据，但读失败当作"不存在"会让控制面在错误的基准上发布，所以同样抛出。
- **存储失败绝不读成空答案**（`CTL-52`）：控制存储答不上来时（`ControlStoreException`），每条控制路由对有权调用的人回答不带细节的 503，两遍维护在那一遍
  什么都不做；存下的值解不出来是 500，绝不是 400，也不是"不存在"。
- **每条记录都带格式号，按一条规则读**（`StoredFormat`，`CTL-53`）：没有格式号的记录是格式 1；已知格式里本版本不认识的成员忽略；更晚的格式拒绝，算格式错误，
  绝不读成不存在。策略文档、API key 与反向引用的成员是判定的输入，保持严格。跨格式升级时先停控制面，登录宿主一起滚动。
- 影子报告与实例状态有 TTL：它们是可以重跑的观测结果；读失败同样抛出，存储故障从不读成"没有样本"或"没有实例"（§6.4）。
- `docKey` 沿用 `SnapshotKey` 的显式编码（`platform`、`app:<a>`、`tenant:<t>`，拒绝含 `:` 的 id）。所有 key 都经 CoCache 写入，没有绕过 CoCache 的
  Redis 命令。早期版本写下的非法 app id 一律跳过（检查、授出分析、收窄、app 列表）；反向引用集合里 id 非法的成员不跳过，整个集合读失败（失败即拒绝：反向引用是“能不能删”的输入，DR1-F-22）；
  变更记录与实例状态里的这种值是该条记录的格式错误。
- Redis 的键与 ACL 的建议写在 [`wiki/operations/storage.md`](../../wiki/operations/storage.md)。

### 5.3 文档头

```jsonc
{
  "schema": 2,
  "revision": 43,
  "publishedAt": "2027-01-10T08:00:00Z",
  "provenance": {
    "parent": { "revision": 42, "digest": "SHA-256:9f2c…" },  // 上一个头的摘要；第一个修订为 null
    "change": "0QH8K3…",                               // 变更请求 id（`IdGenerator`）
    "kind": "PUBLISH",                                 // PUBLISH / ROLLBACK / BREAK_GLASS / EXPIRE / MIGRATE / BOOTSTRAP
    "publishedBy": { "tenant": "acme", "principal": "alice" },
    "approvedBy": [ { "tenant": "(platform)", "principal": "ops-1" } ],   // 没有审批时为空
    "shadow": { "window": "0QH8M1…", "skipped": false }
  },
  "policies": [ … ], "bindings": [ … ]                 // 正文
}
```

- 数据面编译器只检查 `provenance` 的结构（字段齐全、类型正确），不用它的内容做任何决策。编译结果因此与 `provenance` 无关：同一份正文、不同的
  `provenance` 编译出结构相同的快照（发布往返的性质，§12）。
- 摘要是编码后字节的 SHA-256。修订记录按这个摘要寻址，所以 `parent.digest` 直接就是上一条记录的 key。

### 5.4 发布：写入顺序

```
publish(change c, 基准摘要 b, 候选文档 d):     // d 的 provenance.parent = (b 的修订号, b)
  1. ChangeEvent(PUBLISHING) 投递给全部 REQUIRED 监听器（§10.5）        任一失败 → 不发布，c 保持 READY
  2. revision:<key>:<digest(d)> ← d          条件写（期望 = 不存在）；已存在且字节相同 = 成功
  3. 对 d 新增的跨文档引用，先记入 d 的修订索引，再在反向索引中加上（§5.8）   索引只会多，不会少
  4. head:<key>：条件写（期望 = b, d）
       Applied     → 继续
       Conflict    → 先读头：头（或修订链）是本变更在其基准上的修订，说明另一次调用已发布了它，按当前状态返回；
                     否则 c 进入 CONFLICTED（不自动重做，§5.5）；第 2、3 步留下的记录与引用由回收任务清理（§5.7）
       结果未知     → 读回摘要：未变即已写入，否则按 Conflict 处理
  5. revisions:<key> 加入 (修订号, digest(d), d 的 parent 摘要)；失败只记告警，索引可以重建；同号而摘要不同的项不替换
  6. 从反向索引中删除 b 有而 d 没有的引用，除非更晚的修订又索引了它
  7. c → PUBLISHED（条件写）；ChangeEvent(PUBLISHED) 给全部监听器（BEST_EFFORT 语义）；写后检测（见下）
```

| 在第几步之后中断 | 头 | 数据面看到 | 修复 |
|---|---|---|---|
| 1 | b | b | 无；审计里有一条没有下文的 PUBLISHING，事件带 `change` id，可以对上 |
| 2、3 | b | b | 孤儿记录与多余的引用，回收任务处理；多余的引用最多让平台的一次删除被误拦（§5.8 的修复命令） |
| 4 | d | d（广播到达后，最迟 RFC 0003 §4.5 的落后上界） | 索引缺一项，`revisions` 读取时发现索引的最上一项不是头，沿 `parent` 链补齐（见下，`CTL-35`）；再发布一次该变更即可结算，不增加修订 |
| 5、6 | d | d | 同上；多余的引用同第 2、3 行 |

- **头写入是发布的提交点**（`CTL-2`）。第 4 步及其后各步在 `NonCancellable` 中执行；头写入成功之后的收尾（索引、引用、完成判定、结算、审计、写后检测）里，
  存储自己的超时与非致命错误只记日志，已写入的修订照常算发布，从不把它报告为失败；`afterWrite` 在头写入后恰好执行一次。重试时按头的出处认出这个变更已发布，
  结算为 `PUBLISHED`，不增加修订。
- **调用方的取消只在写头之前生效**（`CTL-82`）。写头之前被取消，与在第 1 步或第 2、3 步之后中断相同：不发布任何东西，变更保持 `READY` 并持有自己的槽位
  （槽位属于变更，不属于请求），再发布一次即可发布。写头之后被取消，后续各步照常走完；在那里失败的，再发布一次即可结算，不增加修订。
- **数据面只会看到 b 或 d**：头是一个 key，条件写是一个 Lua 脚本。其余几步的失败都只影响控制面自己的辅助数据，方向都是"多保留"而不是"少检查"。
- **写后检测**（RC1-33）。发布只对目标头比较并交换。检查与分析读过的其他头（记在变更的 `checkedWith` 里，连同 app 列表的摘要）是没有共同 hash tag 的
  独立键，而 Redis Cluster 受支持，所以多键原子写不可行（全部快照键共用一个 hash tag 会把所有文档压到一个分片上，否决）。所以写入之后重读 `checkedWith` 中的
  每个头：有变化就以当前的头重新分析，写一条 BEST_EFFORT 的变更事件 `HEADS_MOVED`（找不到发布时没批准的东西）或 `REVIEW_NEEDED`（找到了，或分析做不了；
  检测超时为 `DETECTION_TIMED_OUT`），不回滚。窗口可以接受：限制授出者不撤销它已做的授出，并发结果等于"先授出、后限制"的串行顺序；唯一例外是两个变更
  各自移除对方授出所依赖的权利且在同一窗口内落地，事件让人看到并复核。由别人结算的发布（重试、取槽的变更）不以他们的权限重新分析，记为需要复核。
- **不加 `WAIT`**（Q27），理由与 RFC 0003 §4.6 相同。修订链让主从切换丢写变得可以诊断：丢了头，数据面按 F11 报回退；丢了记录，头的 `parent`
  指向一条不存在的记录，`verify-chain`（控制面的只读检查）报告断链。`storage.md` 建议需要更强保证的部署配置 `min-replicas-to-write`。
- **历史是头的链，索引自己可以被验证（`CTL-35`）。** 一个文档的修订历史是它的头沿 `parent` 走出的链；修订索引只是这条链的缓存，头才是权威。
  索引的每一项带着它那份记录的 `parent` 摘要：记录按摘要寻址、不可变，所以不论谁在什么先后顺序下写，同一个摘要的项内容都相同。读索引时（先去掉头的修订号之上的项）
  **只有当最上一项的摘要是头的摘要、并且每一项的 `parent` 都是它下面那一项的摘要时，才把它当作历史返回**：只比较摘要，不读记录、不解码。否则从头沿链走到索引里第一个
  "摘要相符且自它以下各环都成立"的项，用链上的项替换不同的、补上缺的；被替换的摘要交给回收（仍受"未结束的变更持有的基准"保护），并记一条 WARN。走到一条缺失的记录就停：
  它以下无法证明在链上的项不返回，也不删除。写的一侧只追加：同一个修订号已有另一个摘要的项时不替换，替换只由走过链的修复来做。
  - **为什么需要它。** 头被移回（部分恢复存储）之后修订号会被重用。只按修订号比较的索引会让按修订读文档、解释、比较差异、挑选回滚的目标与回收读到旧分支上同号的那一份。
  - **为什么不是"只比最上一项，写的时候保证其余"。** 那样的设计被两个序列推翻：一次发布追加在一个没有列出的父项之上，最上一项与头相符而下面仍是旧分支；
    旧分支迟到的一次索引写入把正确的项换了回去。两个不变式分放在读与写两处、再与"迟到的结算不得截断后来的修订"合在一起，推理不下来；一项事实自带它的父摘要，读的一侧就能独自判定。
- **为什么记录先于头**：反过来，头写成功而记录失败时，修订的内容只存在于头里；下一次发布覆盖头之后它就永远丢了。先写记录的代价只是偶尔的孤儿。
- 冲突后**不**在新内容上重做修改：控制面的检查（授出分析、影子窗口）是针对基准 b 做的，换一个基准就要重做检查（§5.5）。
- **丢失的头写入**（`CTL-86`，DR1-F-7）：Redis 的故障切换可能丢掉一次已经成功的头写入，变更记录仍是 `PUBLISHED`，被它收回的东西又生效了。文档索引列在头之上的修订，
  是发布之后头写入丢失、而其后写的索引条目留下的修订。这只在 Redis Cluster 下留得下痕迹（头与索引位于不同的槽，头所在的主节点切换时可能只丢头）；单个主节点上复制保持写入顺序，
  二者一起丢失，存储里什么也不留，只有数据面的回退信号（`cosec.snapshot.regressions`）告知。回收过程在读文档历史之前查找每份文档的这种修订；从头重建索引时，也在丢弃不在头的链上的条目之前
  把它们交出。每条记 ERROR、计数（`cosec.control.revisions.lost`），并由发现它的实例告诉变更监听器一次（`HEAD_LOST`，从丢失修订自己的出处说出变更与发布者）。查找时先读索引、后读头：
  索引条目写在它的头之后，所以两次读之间落下的一次发布不会被报成丢失。控制面不自行把头前移，由发布者重新发布或回滚。防护是 Redis 的 `min-replicas-to-write`（`wiki/operations/storage.md`）。

### 5.5 并发：基准、暂存槽与变基

- **乐观并发**：变更请求创建时记下基准 `(修订号, 摘要)`；发布时条件写（期望 = 基准摘要）。中间有别人发布，这次发布就是 `Conflict`，什么也不覆盖（`CTL-4`）。
  这正是 RFC 0001 §3.7 的"CAS on version"，由 CoCache 的条件写提供，控制面不自己实现比较。
- **不自动变基**：控制面的变更带着针对基准得出的授出分析、影子报告和审批，自动换基准会让它们失效而不被察觉。变更进入 `CONFLICTED`，由作者调用 `rebase`：
  在新的头上重放条目级操作（每个操作可以带条目摘要作为前置条件，前置条件不满足即失败），得到新的候选，**全部检查重做**，审批与影子报告作废：基准移动过的变更从不发布（`CTL-7`）。
- **每份文档一个暂存槽**（`CTL-6`）：一份文档同一时间至多一个变更持有它（`stage:<docKey>`，条件写占用）。槽从影子窗口开始一直持有到 `READY`：一个已就绪而尚未发布的
  变更仍占着槽；发布、放弃、过期、拒绝、发布时落回 `CONFLICTED` 或 `DRAFT`，以及被抢占时释放。否则两个各自影子通过的变更依次发布，第二个的影子比较的是
  一个已经不存在的基准。别的变更可以照常起草和检查，但要排队进入窗口。暂存时变更先离开 `CHECKED` 再占槽，一次条件写决定两个调用的胜负；
  候选只写在自己读到的那份之上，且写前确认仍持有槽，所以写候选时被抢占的变更从不替换取走槽的变更的候选。
- **收窄的紧急变更在占槽的那一刻抢占**（`CTL-22`，RC1-12）：只包含收窄操作、由持有 `cosec:skip-shadow` 的人暂存（`:shadow` 或 `:skip-shadow`）、且基准等于当前头的变更，
  在槽被占用时照常经过自己的那一步拿到槽；原持有者先从 `SHADOWING`、`AWAITING_APPROVAL` 或 `READY` 置为 `CONFLICTED`，撤回候选并记 `FAILED`（`preempted by <id>`），
  做不到就放弃抢占（409、503）。"只收窄"按白名单判断（`Narrowing`），变更的每个操作须属于其一：删除只含 ALLOW 的策略的绑定；把可附加、只含 ALLOW 的策略改为
  不可附加，语句不变；以新 id 新增只含 DENY 的策略（不是边界），或新增绑定候选中只含 DENY 的策略的绑定（不是 break-glass）。删除含 DENY 的绑定、删除黑名单绑定、
  把含 DENY 的策略改为不可附加、替换基准中已有的条目、操作平台也定义的同 id 租户策略，都不算收窄。封禁主体不改文档（黑名单来自属性提供者的
  `environment.blocked`），不等槽。紧急封禁不必等别人的窗口结束。
- **break-glass 撤销**：撤销仍在生效的 break-glass 绑定的变更总能抢占；它持槽时，只有另一个这样的撤销能取走槽（`BRK-9`）。撤销已过期绑定的变更像普通变更一样排队，
  持槽时也不受保护；对同一绑定再撤销一次，会发布停住的 `READY` 撤销（§8）。
- **抢占与发布的剩余窗口**：持槽者的修订若已写在修订链上，来取槽的变更先把它结算为 `PUBLISHED` 再取槽。发布在写 `PUBLISHING` 之前与写头之前各查一次槽，
  写头仍只以基准摘要为条件，所以剩余窗口是一次存储往返加上发布实例在两步之间的停顿：窗口内被抢占的持槽者仍会发布，取走槽的变更随后 `CONFLICTED`
  并记下先发布的修订。
- 基准在一个变更等待审批期间移动，不会当即把它变成 `CONFLICTED`：它仍可以被批准，在发布时冲突，或在别的变更占槽时被抢占。方向是拒绝，不需要为此监视文档头。
- **代价**：标准路径上，一份文档每小时最多发布约 4 次（窗口默认 15 分钟，§6.4）。一个变更可以包含任意多个操作；租户之间互不影响；平台文档是
  唯一会排队的地方（Q5）。

### 5.6 回滚

`rollback(docKey, toRevision)` 创建一个 `kind = ROLLBACK` 的普通变更：候选的正文取自那条修订记录，头部重写（`revision` = 当前 + 1，`parent` = 当前头）。
回滚者先要对该文档有 `cosec:read`，否则与不存在的修订一样答 404，不透露历史（`CTL-18`）。它走完整的流程：

- **编译**针对**当前**的其他文档：回到第 40 修订时，那时引用的平台策略可能已经删除，编译失败即不能回滚，必须先处理引用。这正是 7.x 按策略回滚做不到的检查。
- **授出分析**照常：回滚可以恢复一个已经被撤销的高权限绑定，回滚者没有这个权限就要审批。回滚不是绕过不能越权授权的后门。
- **影子窗口**照常；需要快速回滚时由有 `cosec:skip-shadow` 的人发布（Q1）。
- **break-glass**：回滚若放入、恢复 break-glass 绑定或改动生效中的 break-glass 绑定授出的策略，就是 break-glass 变更，需要 `cosec:breakglass` 并受 V5 约束，
  回滚永远不会带回 break-glass（`BRK-7`）；只移除 break-glass 绑定的回滚立即发布。
- 只提供"回到某个修订的整份文档"，不提供"撤销某一次变更"：后者是条目级的逆操作，留给 UI 用 `propose` 自己组合。

### 5.7 保留与回收

| 对象 | 保留规则（默认） | 属性 |
|---|---|---|
| 修订记录 | 从头沿链的最近 50 个，**并且**任何不到 7 天的，后者以字节预算与索引条数为界（见下，`CTL-84`）；被未结束的变更（基准、回滚目标）引用的一律保留 | `cosec.control.revisions.max-count`、`min-age` |
| 孤儿记录（不在链上，也不被变更引用）、列出却从未写成的变更 | 满一个回收周期（1 小时）后删除 | 算出，不配置（`CTL-72`） |
| 变更请求 | 未结束的至多 `max-count` 个（加上同一时刻正在写入的），超出时先放弃作者自己最老的、检查失败的草稿，否则 `409 OPEN_LIMIT`；已结束的至多 `max-count` 个，结束一个变更的写入删除超出的最早几个；回收任务删除早于 `min-age`、发布的修订已不再保留的已结束变更（`CTL-83`，DR1-E-2） | `cosec.control.revisions.max-count`、`min-age` |
| 影子报告 | 最后一次写入后 8 天（TTL）；实例状态 2 分钟 | — |

- **变更记录的字节上界**（`CTL-83`，第二轮 DR2-E-2）：一条变更记录写入时至多是路由读取的最大请求体加文档上限（默认 18 MB），超出不写入（422）。连同新变更，一份文档的未结束变更记录合计至多
  `max-count` 乘以文档上限（默认 400 MB），超出答 409 `OPEN_LIMIT` 并说明是字节；已结束的变更记录由乘积约束（`max-count` 条乘以记录上限，默认 900 MB），不测量：测量要在每次结束一个变更时读遍已结束的记录。
  一份租户文档至多约 1.7 GB（修订、未结束、已结束、索引），乘以文档数；启动行与 `wiki/operations/storage.md` 写出这些数字。
- 删除的变更读作不存在（404）；它发布的修订若仍保留，照样可以解释，出处里仍记着它的变更、作者与审批人（`CTL-83`）。
- **体积是上界，不是常规的删除条件**（`CTL-84`，DR1-F-6）：一份文档最近的 `max-count` 个修订总是保留记录；它保留的修订记录合计（包括这些最近的）不超过 `max-count` 乘以文档上限
  （默认 400 MB），索引在最近之外至多列出“文档上限除以每条 320 字节”那么多条（默认 26,214 条）。超出任一项时从最老的开始回收，不论是否早于 `min-age`，头与未结束变更所依赖的除外；
  每条在 `min-age` 之内被回收的记录都计数（`cosec.control.revisions.reclaimed-young`）并记限频的 WARN。原先“体积不作为删除条件”的理由仍然成立（按体积删除会让最近几天的修订突然不可解释），
  所以这条界只在循环发布大文档时才碰得到：不到 7 天的记录以前不限数量也不限大小，一个租户管理员能把 Redis 写满。索引条目带着它那份记录的字节数，回收不必为了算体积去读记录；
  记录数、字节数与未结束变更数由持有回收租约的实例计量，跨实例取最大值。
- 回收由每个运行控制面的实例每小时执行一次（常量，`CTL-72`；要回收什么由 `min-age` 与 `max-count` 决定）。每轮在读任何东西之前先占用整轮的租约（`reclaim-pass`，一个回收周期），
  只有持有它的实例读各文档的未结束变更并回收（DR1-E-2）；同一份文档同时只有一个实例回收：
  以条件写占用一个租约 key（`<p>:control:lease:reclaim:<docKey>`），用完以条件删除释放。删除用 CoCache 的 `delete`、`deleteIfMatch`；
  从索引取出的内容先记入 `RevisionIndex.reclaiming`，删除失败的下一轮重试。
- **每个实例都跑维护**（`CTL-59`、`CTL-72`，维护者 2026-11-21 决定）：每个控制面实例都跑维护周期（回收修订、关闭影子窗口、对账 app 列表与暂存清单），由租约隔开：
  同一存储上任意多个实例，每个周期每个间隔只跑一次。没有关掉它们的开关（`cosec.control.maintenance.enabled` 已删除），所以配不出"没有实例跑维护"的部署。
  节奏与上限是常量或算出来的，没有属性：每小时回收一次；不在修订链上的记录满一个回收周期才删；影子窗口每 `min-duration` 的十五分之一看一次（四分之一秒到一分钟之间）；
  实例每十秒写一次报告与状态；控制路由读的请求体上限跟随文档上限（§10.2）。starter 启动时说一次它算出了什么、从什么算的。
- **未结束的变更是集合**（`CTL-54`）：按文档一个集合（`doc:<文档键>`），按状态一个集合（`state:<状态>`），成员是 `<文档键>#<变更 id>@<那次写入所写记录的摘要>`。
  变更 id 不含存储用来切分的任何字符：`:`、`#`、`@`、`/`（DR1-F-21）；实例只记“集合现在还有的成员”的失效时间，每次读一个集合就忘掉它已不再有的成员（DR1-F-20）。
  每次写变更之前先加入它的文档集合与状态集合，写完之后从不再适用的集合里摘除，且只摘除自己那次写入放进去的那个成员：变更重新进入同一状态时，
  迟到的摘除因此拿不走后一次写入的成员。集合是未结束变更的超集。只有在集合已有人维护、并且 8.0.0-beta.5 之前格式的清单（`list:open-changes`）不存在时
  才信任集合；在那之前不回收任何修订，列表请求被拒绝。`cosec-migrate repair-references` 运行一次完成转换。
- 数据面的 `explain` 需要的是决策时的修订：审计保留期比 7 天长的部署要么调大 `min-age`，要么接受较早的决策只能在当前快照上解释（`explain` 返回 410，§10.2）。

### 5.8 跨文档引用：反向引用索引

被引用的一方删除策略、或把它改成另一种东西时，引用方不会自己知道（RFC 0004 §7.2）。控制面维护一个反向索引，按被引用的策略分片：

```
refs:<被引用文档>:<policyId> = { (引用方 docKey, 索引它的修订, 标志)… }   // 例：refs:platform:shared-read = { (tenant:acme, 7, …), (app:order, 3, …) }
```

- **覆盖的引用**：`App`/`Tenant` 的绑定 → `Platform` 的策略；`Tenant` 的绑定 → `App` 的权限策略（N1）；`Tenant` 的 `boundary` → `Platform` 的边界策略（§7.6）。
  租户自有的策略 id 也记为 `(platform, id)` 的引用方，读者按引用方的头区分"定义"与"引用"（RC1-9）。
- **按策略分片**：一条共享策略可能被十万个租户引用，所以 key 带 `policyId`，不是每份文档一个大集合。
- **维护**（`CTL-25`、`CTL-44`）：一次发布把它新增的引用先记入自己的修订索引（正向记录），再为每条引用加入一个成员；发布后只删除正向记录中不高于自身修订、
  新修订已不再有的成员，不读集合。所以索引是真实引用的**超集**：它可能误拦一次删除。移除一侧在发布开始时读一次引用方，写头之前紧挨着前置条件再读一次（`CTL-30`，DR1-F-9）；恰在写头那一刻发布的引用方看不到，
  结果是那份引用方文档编译不过，基于它的判定被拒绝（失败即拒绝）；写入之后的复查与信号留到 8.1。一次租户发布读写的东西不随引用同一策略的其他文档的数量增长。
- **修复**：`cosec-migrate repair-references`（`--to-redis` 或 `--cluster`）只读每个文档的头与它自己的正向记录，不读任何反向引用集合，代价跟着文档持有的引用走；
  可在控制面运行时执行，两次运行共用一个租约。它依赖一条不变量：**记录里有的引用，要么在它的集合里，要么不在文档头里**——发布守住它（先记录、再加成员、全部加完才移动头），
  删除守住它（头里已没有它删的东西），修复自己则反过来先加成员、后写记录。它双向修复：补上头引用而索引缺少的，并删除索引有而任何头都没有的，
  且只在引用方的头已不低于写入该引用的修订、头里也没有这条引用时才删除，所以仍在进行中的发布保留自己的引用。它也把 8.0.0-beta.5 之前格式的存储转换过来
  （`MIG-4`）。
- **检查**（`CTL-5`、`CTL-43`）：发布 `Platform`/`App` 时，候选删除了某个策略 id，而索引里仍有引用方 → 拒绝发布（422），错误列出引用方；索引在头移动之前加入、
  头移动之后才摘除。平台新增一个租户已在使用的 id 同样被拒绝（`CTL-21`，§7.4.1）。只定义该 id（且边界不指向它）的租户
  不阻止平台删除自己的同名策略：是否"只定义"从集合的条目读，绝不读头；后来的修订或输掉的竞争留下的"引用"条目偏向拦截，直到该租户下一次发布或
  `repair-references` 去掉它。app 策略的每个引用方都拦截它的删除。被引用的策略在普通策略与边界策略之间改变种类，检查时与写头时都拒绝（`CTL-30`）：绑定只到达策略，
  租户的边界只到达边界，另一种对它们就是缺失；没有引用的策略可以改种类。修改被引用策略的**内容**不拦：它对每个引用方生效，影子窗口在所有租户的流量上比较（§6.4）。
- **读不出即拒绝**（`CTL-42`）：读不出的反向引用集合（含 8.0.0-beta.5 之前的格式）失败即拒绝：读取抛错并点名 `cosec-migrate repair-references`，需要它的检查拒绝变更（503），
  需要它的头写入不做，也不向它加入或摘除成员。每次读集合都问 Redis：记录的集合不留本地副本。
- **token 附加不在索引中**：主体附加哪个策略由 token 签发方决定，控制面看不到。删除一条可附加的平台策略会让附加它的主体得到
  `Indeterminate(MissingPolicies)`（失败即拒绝）；影子窗口把这些请求报告为 `BECAME_INDETERMINATE`，发布者在确认时看到数字。

### 5.9 自举与 `cosec-migrate`

控制面用快照里的策略授权自己，存储为空时没有任何人能写（§3 M15）。在控制面之外写存储的路径都在 `cosec-migrate` 里，都需要 Redis 凭据，都经控制面的存储写入，
所以都留下修订记录（写入记为 `cosec-migrate`，谁运行了它由部署自己记录；记操作人留到 8.1，DR2-M-7）：

| 命令 | 写什么 | 约束 |
|---|---|---|
| `bootstrap --platform-admin <principal>` | 在 `Tenant((platform))` 中加一条 `Principal((platform), <principal>) → cosec:platform-admin` 绑定（id `platform-admin-<principal>`），作用域 `(*, *)`，`kind = BOOTSTRAP`；文档原有的策略、其他绑定、限流规则与角色全部保留，只有头部与绑定改变（`MIG-3`） | 只有当该文档里没有任何指向 `cosec:platform-admin` 的绑定时才执行；否则拒绝，除非 `--force`（用于"管理员全部失效"的恢复） |
| `publish --in ./converted` | RFC 0004 §8.2 的转换结果，`kind = MIGRATE`，期望 = 不存在 | 拒绝含 break-glass 绑定的输入（§8）；遇到未完成的 CoCache 8 升级留下的 `<p>:meta:cocache8` 标记时拒绝写入 |
| `restore` | 把一个保留的修订或一个文件写成下一个修订，只覆盖调用者确认的那个头修订 | 从锁死中回来的路，不是发布的途径；变更监听器听不到它（控制面发现不是自己写的头并通知监听器，列入 8.1） |
| `repair-references` | 反向引用索引与 app 列表（§5.8、§7.4.3） | 只增补与按条件删除，可在控制面运行时执行 |

拥有 Redis 写凭据的人本来就能改写任何文档，这些命令没有扩大谁能做什么；它们只是让这类写入也留下修订记录。

## 6. 发布流程

### 6.1 状态机

```mermaid
flowchart LR
    N((提议)) -->|检查通过| C[CHECKED]
    N -->|检查失败| D[DRAFT]
    D -->|rebase：重做全部检查| C
    C -->|rebase| C
    C -->|占用暂存槽，开窗口| S[SHADOWING]
    C -->|不开窗口：cosec:skip-shadow<br>或 break-glass 变更| R[READY]
    C -->|不开窗口，有 UNKNOWN 片段| A[AWAITING_APPROVAL]
    S -->|窗口关闭，没有 UNKNOWN| R
    S -->|窗口关闭，有 UNKNOWN 片段| A
    S -->|头已移动| X[CONFLICTED]
    A -->|批准| R
    A -->|拒绝| J[REJECTED]
    R -->|确认差异，头写入| P[PUBLISHED]
    R -->|发布时复查失败| D
    R -->|审批不再覆盖复查结果| A
    R -->|基准已变，或槽已失| X
    S -->|被抢占| X
    A -->|被抢占| X
    R -->|被抢占| X
    X -->|rebase| C
    X -->|rebase，检查失败| D
```

所有状态转换都是对 `change:<id>` 的条件写，并发的两个操作（例如同时批准和放弃）只有一个成功。任何非终态都可以 `abandon`；变更超过
`cosec.control.changes.expire-after`（默认 7 天）未发布即 `EXPIRED`。`REJECTED`、`ABANDONED`、`EXPIRED`、`PUBLISHED` 是终态。
自己的修订正在生效的变更不论到没到期都是已发布的：一次发布写了头、却没能结算变更时，过期在写 `EXPIRED` 之前先核对头是不是它自己的修订，是就按重试发布的同一条路径落成 `PUBLISHED`；
头写入之后结算时遇到的冲突答 503“已写入，再发布一次即结算”，不是调用方的 409（`CTL-2`、`CTL-34`，DR1-E-7）。两个过期时长都必须为正，零在启动时失败（DR1-E-16）。

**转换表是规范**（`CTL-33`）。准确的定义是下面这张表：它是代码里的 `ChangeStep`，由 `core/control/src/test/resources/change-transitions.md` 提交，
测试把枚举渲染出来与那个文件逐字比较，所以改动任何一格都会出现在评审的 diff 里。提议直接生成 `CHECKED` 或 `DRAFT`，检查是命令的一部分而不是一次转换；
`rebase` 一步到 `CHECKED` 或 `DRAFT`，并且也接受 `DRAFT` 与 `CHECKED`；发布可以把变更退回 `DRAFT` 或 `AWAITING_APPROVAL`。

| 步骤 | 起始状态 | 结果状态 |
|---|---|---|
| REBASE | DRAFT、CHECKED、CONFLICTED | DRAFT、CHECKED |
| STAGE | CHECKED | SHADOWING、AWAITING_APPROVAL、READY |
| SKIP_SHADOW | CHECKED | AWAITING_APPROVAL、READY |
| SHADOWED | SHADOWING | SHADOWING、AWAITING_APPROVAL、READY、CONFLICTED |
| APPROVE | AWAITING_APPROVAL | READY |
| REJECT | AWAITING_APPROVAL | REJECTED |
| ABANDON | DRAFT、CHECKED、SHADOWING、AWAITING_APPROVAL、READY、CONFLICTED | ABANDONED |
| PUBLISH | READY | DRAFT、AWAITING_APPROVAL、CONFLICTED |
| UNRESERVE | SHADOWING、AWAITING_APPROVAL、READY | CHECKED |
| PREEMPT | SHADOWING、AWAITING_APPROVAL、READY | CONFLICTED |
| UNWRITTEN | READY、CONFLICTED | DRAFT、CONFLICTED |
| WRITTEN | 除 PUBLISHED 外的每一个状态 | PUBLISHED |
| EXPIRE | DRAFT、CHECKED、SHADOWING、AWAITING_APPROVAL、READY、CONFLICTED | EXPIRED |

前八行是命令（STAGE 在 API 上是 `:shadow`，内部入口是 `startShadow`）；其余是命令途中的步骤：UNRESERVE 是没有拿到槽的 `:shadow` 或 `:skip-shadow` 退回，
以及窗口开始一分钟后仍没有候选的变更退回（§6.4）；PREEMPT 是槽被别的变更占走；UNWRITTEN 是没有写入头的发布；WRITTEN 是头已经写入的发布；
EXPIRE 是每次读取都会施加的过期：它不是命令，从变更此刻的状态移动它，别人先移动了就答变更现在的样子，从不 409；命令照旧拒绝已过期的变更（`CTL-34`）。规则有三条：

- 一行的结果状态恰好是该步骤会写入的状态。`PUBLISHED` 只在 WRITTEN 一行里：只有本变更自己的发布写入了头，才到得了这一步。
- 命令对起始状态之外的变更答 409。内部步骤不是命令，从不答 409；一个步骤要写入表外的状态是实现的错误，什么都不写入，控制面 API 答服务端错误
  （500；发生在抢占或头写入之后的收尾里时，那里原有的兜底把它报成 503）。
- WRITTEN 的起始状态包含终态 `REJECTED`、`ABANDONED`、`EXPIRED`：发布是在变更处于 `READY` 时写入头的，如果在它记下这一点之前另一条命令
  （拒绝、放弃、过期）先改了状态，头照样已经写入，修订已经生效，记录必须如实写成 `PUBLISHED`。

**没有 `SHADOWED` 状态。** 窗口一关闭，下一个状态立刻可以算出（没有 UNKNOWN 片段就是 `READY`，有就是 `AWAITING_APPROVAL`），中间没有可以停留的地方。
窗口怎样关闭记在变更的影子摘要里，不是状态：样本足够；到最长时长仍不足（`insufficient`，发布必须确认）；任一实例报告候选出错（`blocked`，
任何发布都答 409，`CTL-12`）。审计事件 `SHADOWED`（窗口关闭这件事）保留。

"检查"按顺序是：授权（§7.2）→ 校验（§6.2）→ 编译（§6.3）→ 授出分析（§7.4）。授出分析得到 UNKNOWN 不阻止进入影子窗口：
影子只是观测，审批人需要看到影子报告再做决定。同一组检查也可以不建变更单独运行（`:check`，§10.2）。

### 6.2 校验

| # | 检查 | 失败时 |
|---|---|---|
| V1 | **格式**：按生成的 JSON schema（§10.4）给出带 JSON 路径的错误；真正的判定是编译器（V1 只为更好的错误信息） | 400 |
| V2 | **规模与结构**：文档 ≤ 8 MB（RFC 0003 Q14）；每文档主体绑定 ≤ 1,000（RFC 0004 Q2）；条目预算（`CTL-40`，见下）；保留前缀（`cosec:`、`perm:`、`g:`、`r:`）只能由内置策略和 `cosec-migrate` 使用；租户文档里的策略 id 不能与平台层重名，除非是平台策略的精确副本（N2，`CTL-14`）；命名非法 app 的绑定（不符合 `ScopeResolver.isValidAppId`） | 400 / 422 |
| V3 | **语言**：类型、属性目录（`Platform` 文档的 `attributes` 节加内置目录，N3）、成本上限（`Platform` 文档的 `limits` 节，RFC 0005 §3.5）；不可满足的条件给警告。条件先对照平台声明的外部属性、再对照宿主的属性提供者声明的检查，与实例编译时相同（`CTL-20`） | 422 |
| V4 | **锁死检查**（`CTL-38`）：对平台文档、平台租户文档、控制应用文档的变更，由引擎在候选上判定操作者在候选生效后是否仍能到达控制面（当前这次请求按 Pipeline 的判定，加上控制应用中该文档上的 `cosec:publish`）；只检查操作者自己的回路，用的是当前请求的事实 | 提议时警告；发布时 422，除非发布者确认（`"lockout": true`） |
| V5 | **语义规则**：DENY 上的 `onMissing: nomatch` 必须带确认（§9.5）；break-glass 的规则（§8）；边界策略只含 ALLOW、只在 `Platform`（§7.6） | 428 / 422 / 403 |

- **条目预算**（`CTL-40`）：平台 `limits` 里为每份文档设策略、语句、对角色的绑定、对所有人的绑定的上限（默认 10,000、20,000、10,000、1,000）。对每一项，
  候选的数量不得超过限值与它所替换的头的数量中较大的那个：已超出的文档继续被服务，可以改小，不能再增。控制面在提议、`apply`、回滚、变基与发布时检查，
  编译器与宿主不检查。
- **命名非法 app 的绑定**检查的是整个候选文档，所以头上还留着这种绑定的租户，下一次变更必须删掉它；只删掉它的变更是合法的。数据面不拒绝这类绑定：它们永远匹配不到请求，存着无害。
- **动作名不对照目录校验**：编译器只检查动作与资源的语法；目录声明的是权限 id（RFC 0012），控制面不按目录核对动作名或资源类型（RFC 0005 §5.1）。
- **路由映射**：给出各服务的路由映射（`cosec.control.analysis.route-maps`）时，变更带一条 `ROUTES` 警告，列出候选中被已映射路由绕开的 `http:` DENY 语句与限流规则；
  没有给出时，含这类语句的候选说明未提供路由映射。宿主一侧，配置了路由映射的宿主在快照源的维护线程上（绝不在加载路径上）审查它安装的每个文档修订，
  各记一条 WARN；被维护线程拒绝的审查计数（`install-review`），在一次读取确认该修订仍在生效时重新提交；之后的任何安装都会替换或丢弃它。审查从不延迟、
  失败或改变一次安装（`SNP-19`）。

警告记在变更请求上，不阻止发布；发布者在 `publish` 时看得到。

### 6.3 编译：发布前编译，失败保留旧版本

- **同一个编译器**：控制面调用 `cosec-document` 中数据面使用的那个编译器（`PolicyDocumentCompiler`），不另写一份。候选文档与它要组合的其他文档的**当前头**一起编译：
  `Tenant(T)` 的候选与当前的 `Platform` 和它引用到的 `App`；`App(a)` 的候选与当前的 `Platform`；`Platform` 的候选单独编译，另加 §5.8 的反向检查。
- **严格**：数据面编译时，一条编译失败的策略只是 `Broken`，读到它的请求失败即拒绝（RFC 0003 F4）。控制面不发布含任何 `Broken` 的文档（`CTL-1`）：候选的每一个
  条目都必须编译成功，悬空引用、跨租户引用、主体绑定超限、break-glass 缺少期限这些编译错误都在这里拦住。
- **为什么"保留旧版本"是安全的**：被拒绝的候选从未写进头，没有任何实例见过它，"旧版本"就是当前的头，每个请求仍然按已发布的头决策。
  RFC 0003 Q8 拒绝的是另一件事：数据面在**已发布**的新修订编译失败时退回旧修订。那仍然不做（§3 M2）。
- **数据面仍可能编译失败**：控制面接受、某个实例拒绝，只可能是两者不一致——代码版本不同（升级顺序错误，§3.1 N4）、实例缺少 `Platform` 文档声明的
  属性提供者（N3）、实例的栈更小（RC1-43）。这时该实例按 F5 失败即拒绝，记为失败的编译。控制面在影子窗口里也能看到它：实例第一次在暂存清单里见到
  一个窗口时就读取并编译它的候选，不等第一个被采样的请求；编不过的候选在同一个周期记为 `CANDIDATE_ERROR`，窗口因此立刻关闭并且不能发布，不取决于该实例
  有没有流量（`CTL-12`）。这种编译在上报协程上逐个进行，绝不占用快照源的编译池与队列；每个周期至多花一个上报间隔（在两个候选之间检查，不打断正在编译的那个），
  其余留给后面的周期，等得最久的先做。

### 6.4 影子窗口

**候选的分发**：

- 进入 `SHADOWING` 时，控制面先在 `<p>:candidate-staged:all` 中登记该文档与窗口，再把候选文档写进 `candidate:<docKey>`，附带窗口与基准修订。
- **暂存清单**（`CTL-46`）是已暂存候选的超集：窗口先登记、候选后写入；候选撤回之后才摘除，撤回失败则保持登记。登记是无条件加入一个成员，所以其他文档的并发暂存
  从不让它失败；登记失败则暂存失败，什么也不写。成员 `.kept` 表示清单有人维护，没有它即"无人维护"，读取方按键读。读取方不认识的成员跳过，代价至多是少了样本、
  窗口按证据不足关闭，绝不会让窗口通过。每个影子轮在租约之下对账：补登记漏掉的窗口；连续两轮都该清理的窗口才清理；候选在而没有影子中的变更认领它的，
  只有读全了所有未结束变更的一轮才撤回。
- **缺候选的窗口**：处于 `SHADOWING` 的变更，窗口开始一分钟后它的文档仍没有该窗口的候选，则退回 `CHECKED`、释放槽、记一条失败事件，由作者重新发起；
  窗口不在缺口上继续，维护任务也不代写候选。
- 数据面读候选经 `CandidateSource`（`CachingCandidateSource`）：它与执行用的文档分开，至多 1,024 份文档（最久未用的先出），每份 10 秒后重读，不参与就绪检查，
  读取失败只计数、不给候选。它在请求路径之外读暂存清单（`CTL-47`）：有清单时只为清单列出的文档读候选，只采样视图会读到清单所列文档的请求；清单为空时不采样，
  也不读候选；没有人维护清单时，照旧按键读每个候选并采样；读不了的清单算没有清单，绝不算"没有暂存"。清单只做门：候选仍按键读、按窗口核对，
  所以读晚了的清单只损失样本，绝不产生错误候选的样本，也不产生通过。只读自己采样的事件的 BEST_EFFORT 监听器（影子监听器）只拿到点它名的事件（`OBS-8`）。
- 对一个被采样的请求，若它的 `SnapshotView` 用到的某份文档 K 有候选，**且候选的基准修订等于本实例已安装的 K 的修订**，就用候选替换 K 组成候选视图，
  再调用一次引擎。基准不一致（本实例落后，或头已经变了）时不比较，计为 `BASE_MISMATCH`。
- 采样只针对用到 K 的请求：租户文档的候选只在该租户的请求上评估；`Platform` 的候选在全部请求上评估。
- 候选只为比较而编译，绝不改变本实例执行所用的编译输入：平台候选按它自己的限制与属性声明编译，其余候选按已安装的平台编译（`SNP-10`）。

**汇总**：每个实例按窗口在内存中累计，每个上报间隔（由状态的存活期与 `cosec.control.shadow.min-duration` 算出，不是属性，见
[`configuration.md`](../../wiki/operations/configuration.md#computed-not-configured)）经 `ShadowReportSink` 写一次自己的累计报告：

| 字段 | 内容 |
|---|---|
| 计数 | `SAME`、`WIDENED`（基准不是 Permit、候选是）、`NARROWED`（基准 Permit、候选不是）、`BECAME_INDETERMINATE`、`CANDIDATE_INDETERMINATE`（候选读到请求没有取的外部属性，RFC 0006 §9.5.4）、`CANDIDATE_ERROR`、`BY_CHANGED`（结果相同、决策语句不同）、`BECAME_DENIED`（基准 Indeterminate、候选 Deny）、`OBLIGATIONS_CHANGED`（同一语句的 Permit、限流义务不同）、`BASE_MISMATCH` |
| 样本 | 每类最多 20 条，字段与 `DecisionEvent` 相同的那部分（主体、作用域、动作、资源摘要、两边的 `by`），不含请求头、token 和外部属性的值（RFC 0006 §9.2） |
| 实例 | 实例 id、看到的基准修订、首末时间 |

- **报告按实例分 key**（`CTL-16`）：`<p>:shadow:report:<window>:<instance>`，加上只增的索引 `<p>:shadow:reporters:<window>`；实例 id 只允许 `[A-Za-z0-9._-]`。
  每个实例只写自己的 key，所以一个实例永远替换不了另一个的数字，ACL 可以把每个实例限制在自己的 key 上。窗口的数字是每个实例最新一份累计报告之和；
  同一实例的第二份报告、别的窗口的报告、负的计数，或在窗口上报告过的实例没有报告，都让窗口保持打开而不计入；任何一个实例的 `CANDIDATE_ERROR` 单独就阻止窗口。
  控制面把见过的实例记入变更的影子状态，之后被删出索引也照样要求它的报告。
- **进程 id 每次启动都新**（`CTL-45`）：一个进程的报告与状态写在此前没有任何进程用过的 id 之下，不论 `cosec.authorization.shadow.instance-id` 设成什么
  （配置值是前缀，每次启动加一个新的后缀）。否则重启后沿用旧 id 的进程会覆盖前一个进程的累计报告，并抹掉它记录的 `CANDIDATE_ERROR`。
- **一轮检查只写它看的那个窗口**（`CTL-56`，DR1-E-6）：一轮影子检查看到的东西只写进它所看窗口的记录，并与记录已有的报告者取并集，没有新增就不写；期间重新暂存的变更保持新窗口开着，
  两轮重叠的检查各自保留对方看到的实例。
- **绝不因缺少证据而通过**（`CTL-56`）：在某个窗口上报告过、现在读不到报告的实例要等；到最长时长时，窗口以"证据不足"关闭并说出是哪个实例，绝不凭其余实例的报告通过
  （`ShadowReportReader.readings(window)` 说出登记了报告却读不出的实例）。影子巡检跳过读不了的变更并计数，从最旧的开始。

**窗口何时关闭**（默认值可以配置，`cosec.control.shadow.*`）：

| 条件 | 默认 | 结果 |
|---|---|---|
| 已过最短时长，有效样本（不含 `BASE_MISMATCH`）达到最少样本数，**并且**参与影子的在线实例都已确认该窗口 | 15 分钟；1,000 条 | 窗口关闭 |
| 到达最长时长仍未满足上一行 | 24 小时 | 窗口关闭，标记 `insufficient`：发布时必须确认"证据不足" |
| 任一实例报告 `CANDIDATE_ERROR` | — | 立即关闭，**不能发布**：候选在某个实例上无法编译或评估，先修正（§6.3） |
| 头在窗口期间变化 | — | `CONFLICTED`（§5.5） |

- **确认**（`CTL-10`）：在最近一分钟有状态、并且参与影子的每个实例都在自己的状态里确认了该窗口，窗口才可能通过。不发确认的实例（旧版本，或没有读到暂存清单）
  什么也没确认；状态里说自己不做影子的实例（候选来源不是 CoSec 自己的）不等它，但 `propagation` 仍然数它。暂存这一步本身让清单开始被维护，所以在没有启动任务或
  影子周期跑过的存储上暂存的窗口同样能被确认。确认不增加样本；读不了状态时窗口保持打开。窗口打开期间，变更的应答说出多少在线实例已确认、哪些没有
  （`waitingFor`：至多二十个 id 与其余的个数）。
- **解不出的状态**（`CTL-73`）：一条列出来却解不出的实例状态不让整次读取失败：该实例算在线、什么窗口也没确认，所以没有窗口因它通过，变更的应答在 `waitingFor` 里
  点它的名，其余状态照读。它在自己的值过期时不再计数：每条状态写入时带恰好两分钟的存活期，不带抖动。每条这样的状态按实例至多每分钟记一次日志并计数
  （`cosec.control.shadow.status.unreadable`）。写在别的实例的键下的状态、不应答的存储，仍然让读取失败。

**发布时的确认**（`CTL-11`）：`publish` 带上 `ack = { window, counts }`，计数必须与窗口关闭时冻结的汇总一致（防止确认过期的数字）。`WIDENED`、`NARROWED`、
`BECAME_INDETERMINATE`、`BECAME_DENIED`、`OBLIGATIONS_CHANGED` 任一不为零，或者 `insufficient`，都必须确认；全部为零且样本充足时可以不带 `ack`。确认记入修订记录的
`provenance.shadow` 和审计。窗口关闭时冻结汇总并撤下候选文档；实例在候选撤回且最后一份报告写入后停止上报。

**影子窗口对数据面的约束**：沿用 RFC 0006 的监听器规则——`BEST_EFFORT`、有界队列、采样、绝不影响决策。样本包含主体 id 与路径，与审计事件同级；
读取影子报告需要 `cosec:shadow-read`（§7.1）。

**跳过窗口**（`CTL-13`）：创建或撤销 break-glass 绑定没有影子窗口；其他变更只有持有 `cosec:skip-shadow` 并写明原因才能跳过窗口。

**为什么默认强制**（Q1）：不能越权授权回答"这个人有没有资格这样改"，影子窗口回答"这样改了，真实流量会怎样"。前者挡不住"有资格但写错了"——
例如租户管理员把一条 DENY 的资源模式写宽了，把自己的整个应用锁死。没有影子窗口，这类错误只能在发布后被用户发现。

### 6.5 发布与传播

发布按 §5.4 写入。之后各实例在失效通知到达时重新加载（RFC 0003 §4.4），陈旧度有 RFC 0003 §4.5 的上界。`ControlPlane.publish` 在头写入成功后返回
新的修订号，不等待传播。

每个实例在写影子报告的同一个周期里写两条自己的记录（`CTL-74`、`CTL-75`）：

- **状态** `<p>:shadow:status:<instance>`：每个上报间隔写，恰好活两分钟、不带抖动；只有实例、时间、格式级别、是否做影子与已确认的窗口，不带文档，
  所以存活、确认与关窗路径每个实例读的东西不随它持有的文档增长。
- **驻留记录** `<p>:shadow:resident:<instance>`：实例持有的文档到修订号，先于状态写，只在与上一次写成功的内容不同时写，且至少每半小时写一次（恰好活一小时、
  不带抖动）；写失败不妨碍写状态，记为欠着，每个周期重试。

控制面据此提供只读的 `propagation(docKey, revision)`（`CTL-62`），应答 `{revision, installed, holding, recent, unknown, asOf}`：`recent` 是最近一分钟有状态的实例，
`holding` 是其中持有该文档（任意修订）的，`installed` 是其中已安装该修订或更新修订的，`unknown` 是在线但驻留记录缺失或解不出的。`installed == holding` 且
`unknown == 0` 时没有实例落后；`holding: 0` 表示没有实例持有该文档，第一个需要它的请求直接加载已发布的修订。状态与驻留记录每个控制面宿主至多五秒读一次
（`asOf` 说出何时读的），并发调用共用一次读；读失败不缓存、不用旧数据回答，按 `CTL-52` 答 503。它只用于观测，发布不等待它（Q29）。

影子报告与状态的端口（`ShadowReportSink`、`ShadowReportReader`）是实验性的。升级顺序：先控制面，后数据面。

### 6.6 什么会阻止发布

| 阶段 | 条件 | HTTP 状态（§10.2） |
|---|---|---|
| 授权 | 操作者没有目标上的动作；跨租户的硬性规则（§7.2） | 403 |
| 校验 | V1–V5 任一失败；锁死检查未经确认（V4） | 400 / 422 / 428 |
| 编译 | 候选或组合有任何编译错误；反向引用检查失败 | 422 |
| 授出分析 | 有 UNKNOWN 片段且没有有效的批准（§7.5） | 428 |
| 暂存槽 | 槽被别的变更占用（收窄的紧急变更与 break-glass 撤销除外，§5.5） | 409 |
| 影子窗口 | 窗口未关闭（且未经许可跳过）；`CANDIDATE_ERROR`；`ack` 缺失或与汇总不符 | 409 / 428 |
| 并发 | 基准已变化（条件写冲突） | 409 |
| 审计 | 任一 `REQUIRED` 的 `ChangeListener` 失败（§10.5）；break-glass 时没有配置 `REQUIRED` 监听器 | 503 |
| 存储 | `ControlStore` 读写失败；判断不了调用者能否读这个变更（`CTL-17`） | 503 |

每一种失败，头都没有变化：失败即不发布。每个 409 都在 problem 的 `conflict` 成员里说出是哪一种冲突（`CTL-80`，§10.2）。

### 6.7 声明式 `apply`

`apply(docKey, desired, mode)` 把"期望的文档内容"与当前头比较，算出条目级操作，创建一个普通的变更请求。`mode = MERGE` 只增改、不删除未提到的条目；
`REPLACE` 让文档与期望内容完全一致。它取代两样东西（N9，Q17）：

- `LocalPolicyInitializer` 的 `init-repository`：每个实例启动时写库的做法已删除。需要"策略随代码发布"的部署，在 CI 中用一个服务主体调用 `apply`，变更照常经过授权、
  影子与审批。本地策略文件仍然可以直接装进内存存储（`InMemorySnapshotDocumentStore`），供开发、测试和不用 Redis 的单实例部署。
- 生成器端点 `cosecServiceGenerator` 留在 starter，它只读宿主的 OpenAPI 并返回路由映射与 app 文档的 JSON；这些 JSON 是 `apply` 的输入。

- **`REPLACE` 基于文件所写的修订**（`CTL-36`）：对已有头的文档，`REPLACE` 的 `:apply` 按文档头所写的修订（读到它的那个修订）提出，不按当前头；那个修订不是头时
  以 409 拒绝，与 `POST /changes` 的基准过期相同，消息说明要重新读头、把变化带进文件、把修订设为头的修订后再 apply。尚未发布的文档不比较。
- **`MERGE` 保留略去的条目**（`CTL-37`）：文件略去了头的条目时保留它们，变更每一节（`$.policies`、`$.bindings`、`$.roles`、`$.rateLimits`）带一条 `WARNING` 发现
  （检查 `OPERATION`），点名保留的 id，并说明 `REPLACE` 会删除它们。`REPLACE` 不带：它删除的就是它的操作。
- **限流规则只经变更改**（`CTL-19`）：`putRateLimit`、`removeRateLimit`，或设定它们的 `:apply`（都按 `REPLACE`）；不点名限流规则的变更保留头上的规则。
- **变更的 `kind` 不属于 API**：`POST /changes` 带 `kind` 字段为 400，提议只接受 `PUBLISH` 与 `BREAK_GLASS`，`ROLLBACK` 只由 `rollback()` 设置，`MIGRATE`、`BOOTSTRAP`
  只存在于 `cosec-migrate` 直接写修订的路径；break-glass 请求走 `/break-glass`（§8）。

## 7. 控制面写操作的授权

### 7.1 动作与资源

控制面的动作是 RFC 0005 §5.1 的 `service:verb`，`service = cosec`；资源是带类型的段模式：

| 资源 | 例子 | 含义 |
|---|---|---|
| `doc/<layer>[/<id>]` | `doc/platform`、`doc/app/order`、`doc/tenant/acme` | 一份文档 |
| `doc/<layer>[/<id>]/<kind>/<entryId>` | `doc/tenant/acme/policy/editor-read`、`doc/tenant/acme/binding/b-17` | 文档里的一个条目，`kind` ∈ `policy`、`binding`、`catalog`、`boundary` |
| `scope/<tenant>/<app>/<space>` | `scope/acme/order/team-a`、`scope/acme/order/*` | 绑定授出到的作用域；通配维度写成字面量段 `*`；默认空间写成 `(default)` |

| 动作 | 资源 | 用途 |
|---|---|---|
| `cosec:read` | `doc/…` | 读头、历史、变更请求 |
| `cosec:write` | 条目 | 起草对条目的修改 |
| `cosec:grant` | `scope/…` | 创建或修改指向该作用域的绑定，以及让角色新派生出绑定的变更（与 `cosec:write` 都要有） |
| `cosec:publish` | `doc/…` | 发布这份文档的变更（含回滚） |
| `cosec:skip-shadow` | `doc/…` | 不经影子窗口发布；抢占暂存槽（§5.5） |
| `cosec:approve` | `doc/…` | 批准含越权项的变更（§7.5） |
| `cosec:boundary` | `doc/tenant/<t>/boundary`、`doc/platform` | 设置租户边界（`doc/tenant/<t>/boundary`）或默认边界（`doc/platform`）；只在平台持有，内置的 `cosec:tenant-admin` 不持有 |
| `cosec:breakglass` | `doc/platform` | 申请、发布、撤销 break-glass（§8） |
| `cosec:manage-roles` | `doc/tenant/<t>` | 角色类别：只写入或删除角色的变更不因"谁在授出"而等第二个人（§7.4.7） |
| `cosec:simulate`、`cosec:explain`、`cosec:analyze`、`cosec:shadow-read` | `doc/…` | 只读工具（§10.3） |

- 资源模式的段 `*` 匹配任意一段，包括字面量段 `*`：能在 `order` 的任何一个空间写绑定的人，也能写 `space = *` 的绑定。两者能授出的范围相同（后者还覆盖
  将来的空间）；需要区分时写一条 DENY：`{"eq": ["resource.var.space", "*"]}`。`wiki` 的控制面页面写明这一点。
- **默认空间的占位符**（`SCP-9`，RC1-37）是 `(default)`，一个空间 id 语法本来就不接受的形式：以 `(` 开头的空间 id 保留给 CoSec，编译器拒绝其中的绑定，
  `ScopeResolver` 把声明的保留空间判为 `SPACE_NOT_MEMBER`（403 `scope-rejected`）；数据面格式不变。

### 7.2 授权怎么执行

```mermaid
sequenceDiagram
    autonumber
    participant H as HTTP 适配器
    participant P as Pipeline（宿主的数据面）
    participant C as ControlPlane
    participant K as AuthorizationChecker
    participant S as 控制面的 SnapshotSource
    H->>P: HttpFacts（POST /cosec/control/v1/changes）
    P-->>H: Outcome（Permit，SecurityContext 带主体与作用域）
    H->>C: propose(operator, docKey, ops)
    C->>C: 硬性规则：租户隔离
    C->>S: 条件读确认用到的文档（不信任可能落后的本地副本）
    loop 每个目标（条目、作用域、文档）
        C->>K: check(operator, cosec:verb, resource)
        K-->>C: Permit / Deny / Indeterminate
    end
    C->>S: 再确认一次：文档有变化就从头再判定
    C-->>H: 403（任一不是 Permit）或继续检查
```

- **两层**：宿主的 Pipeline 认证请求、按路径做粗粒度授权（例如"控制面 API 只对已认证主体开放"）；细粒度的授权在 `ControlPlane` 内对每个目标调用
  `AuthorizationChecker`（RFC 0006 §7.6 的挂起形式），评估用的是宿主自己的引擎和快照。作用域：租户是操作者的租户，应用是 `cosec.control.app-id`
  （默认 `cosec-control`），空间是默认空间。
- **逐个目标判定**（`CTL-8`）：每个条目上的 `cosec:write`、绑定授出到的每个作用域上的 `cosec:grant`，以及这一步自己在文档上的动作，都在记下任何东西之前判定。
  一次变更使某个角色新派生出绑定时也需要 `cosec:grant`，不论是 `putRole`，还是让 `"*"` 角色多出权限的 `putCatalog` 或 `putPolicy`（`ROL-9`）。变更写入的条目 id
  不含 `/`（V2，422）：带 `/` 的 id 会给 `cosec:write` 的资源多出路径段，逃出以 `*` 结尾的规则。权限策略 `perm:<app>/<permission>` 只许 app 之后的那一个 `/`，
  `<permission>` 里不含，目录里的权限 id 也不含（DR1-E-5）。只检查这次变更新增的 id：目录是整份提交的，已存目录里原样带着的不拒，与已存的条目一样可以保留或删除。
- **先确认再授权**：控制面用一个独立的 `SnapshotSource`，对用到的文档做条件读（RFC 0003 §4.5，几十字节的往返）。数据面接受有界的陈旧，控制面不接受：
  一个刚被撤销的租户管理员不能在落后窗口里继续改策略。一次变更的全部目标在一次确认上判定，判定完再确认一次：其间文档变了就整批重新判定，所以变更进行中被撤销的
  操作者与每个目标之前都确认一次时同样被拒绝；确认不了或一直在变的文档拒绝这次变更（503）。
- **硬性规则**（不经策略，单元测试守护，作为策略写错时的最后一道线）：租户 T 的主体只能读写 `doc/tenant/T` 及其条目（`TNT-3`）；`doc/platform`、`doc/app/*`
  只有平台租户 `(platform)` 的主体能写；break-glass 只有平台租户的主体能申请和批准；设置租户边界只归平台（`BDY-2`，§7.6）。
- **失败即拒绝**：任何一个目标不是 Permit（包括 `Indeterminate`）就整个拒绝；`Indeterminate` 给 503，其余 403。判断不了调用者能否读一个变更时
  （存储或快照读失败），点名它的每一步都是 503，不论变更存在与否（`CTL-17`）。
- 平台边界也约束控制面动作（它们是普通的 Permit）：平台不给某个租户的边界里放 `cosec:*`，就等于关闭了这个租户的自助。

### 7.3 内置的控制面策略与信任根

| 策略 | 语句 | 由谁绑定 |
|---|---|---|
| `cosec:platform-admin` | ALLOW `cosec:*` 于 `doc/**`、`scope/**` | `bootstrap`（§5.9），之后由平台管理员；只能绑定在平台文档与平台租户自己的文档 `Tenant((platform))` 中 |
| `cosec:tenant-admin` | ALLOW `cosec:read`、`write`、`grant`、`publish`、`simulate`、`explain`、`analyze`、`shadow-read` 于 `doc/tenant/{t}/**` 与 `scope/{t}/**`；ALLOW `cosec:skip-shadow` 于 `doc/tenant/{t}`；两条都带条件 `{"eq": ["resource.var.t", {"attr": "subject.tenant"}]}` | 平台管理员在 `Tenant(T)` 中绑定给 T 的某个角色 |
| `cosec:tenant-viewer` | 同上第一条，只有 `read`、`simulate`、`explain`、`analyze`、`shadow-read` | 租户管理员（被 `tenant-admin` 包含，§7.4 允许） |

- 三条都是编译时注入的平台策略（与 RFC 0004 §4.7 的 `cosec:blacklist`、§4.8 的 `cosec:root` 同样的做法），每份平台文档都有，不存进 Redis，任何文档都不能定义、
  修改或删除它们；授出分析像读任何策略一样读它们的语句。
- `cosec:tenant-admin` 只能跳过自己租户文档的影子窗口（`CTL-27`）：流量少的租户上窗口会一直开到最长时长，而变更授出的东西照旧经过分析、超出管理员所持有的照旧要审批；
  这条策略不让任何人跳过别的租户的文档，绑定给平台主体也一样。
- `cosec:platform-admin` 只能绑定在平台文档与 `Tenant((platform))` 中，租户与 app 文档里的这种绑定编译失败（`TNT-2`，RC1-36）。`bootstrap` 把第一位管理员绑定在平台租户的
  文档中（§5.9）；那份文档的主体都是平台自己的主体。
- 指向它们的绑定用作用域 `(cosec.control.app-id, 默认空间)`：控制面只在这个作用域里检查自己的动作（§7.2）。写成 `(*, *)` 也能工作，但授出分析会要求授权者
  在 `*` 上拥有它（§7.4.3 的 `covers`），经角色得到的权限做不到。
- **信任根**（`APR-3`）是**平台租户中**对目标文档持有 `cosec:approve` 的人：他们本来就能批准任何越权的变更，所以他们自己的变更不做授出分析（§7.4.3 第 0 步），
  但照常校验、编译、影子和审计；`cosec.control.approval.four-eyes=true` 时，分析说不清的部分要另一位平台主体批准（§7.5）。有三类主体不是信任根：
  - 持有 `cosec:approve` 的**租户主体**：它能批准别人在本租户文档上的变更，它自己的变更照常分析（RC1-10）；
  - **工作负载的凭据**（API key，或服务以自己的主体调用控制面时声明的身份，凭据名为 `service`）认证的主体，不论它持有什么（`IDN-34`，§7.5）；
  - 经**服务配置**（控制面宿主的服务端口，或门面 `ControlService`，§10.2）发来的请求：那里的身份只是由网络放行的某个工作负载声明的，所以在那里做出或发布的变更
    不论声明的是谁都要分析，分析证明不了的等人在运维端口上批准（`CTL-81`）。这是请求的事实，不是身份的：同一个主体在运维端口上（包括转发的身份）仍保留豁免，
    在那里就绪的变更经服务配置发布时再分析一次。
- break-glass 例外：总是双人（§8）。

### 7.4 不能越权授权

#### 7.4.1 什么算"授出"

一次变更的操作先归一成"授出的语句片段"。不产生片段的变更只需要 §7.2 的写权限。所有读"文档授出了什么"的地方都读展开后的文档（`RoleExpansion.effective`，
RFC 0012 §6）：角色与短形式权限按它们派生出的绑定与策略计算。

| 变更 | 授出的片段 | 授出到 |
|---|---|---|
| 新增或修改绑定 `b → P` | `P` 的每条 ALLOW | `b.subject`，作用域 `b.scope` |
| 修改策略 `P`：新增 ALLOW，或把 ALLOW 改得不再被原语句包含（§7.4.4 的收窄判定不成立） | 新的或改过的那条 ALLOW（整条，不是差量） | 当前指向 `P` 的每条绑定（同一文档内的，以及经反向索引找到的）各自的主体与作用域 |
| 把 `P` 设为 `attachable`，或修改可附加策略的 ALLOW | `P` 的每条 ALLOW（或改过的那条） | T 的任何已认证主体，作用域 `(*, *)`（附加的作用域，RFC 0004 §4.4） |
| 写入角色，或让角色多出权限（RFC 0012） | 角色新派生出的每条绑定的每条 ALLOW，逐个权限分析（`ROL-9`） | 角色的成员，作用域为角色的应用与空间 |
| 租户删除自有的、平台也定义的同 id 策略 | 平台那条策略的每条 ALLOW（`GRT-4`，RC1-9） | 租户里仍指向该 id 的每条生效绑定；平台策略可附加时也授给附加 |
| 删除或放宽 DENY | 不产生片段，见 §7.4.4 | — |
| 删除绑定、删除 ALLOW、收窄 ALLOW、新增 DENY、修改 `Catalog` | 不产生片段（收窄，或不参与评估） | — |

- 一条 ALLOW 的动作列表与资源列表按笛卡儿积拆开：语句"`[order:read, order:list]` 于 `[order/*, invoice/*]`"是四个片段，每个片段单独判断。
- **指向不存在策略的绑定**是一个 UNKNOWN 片段（`UNRESOLVED`，RC1-32）：分析无从知道它会授出什么。
- **只比较改动的部分**（`CTL-50`）：被当作"此前已写入"而跳过的策略或语句，在授出所依赖的每个成员上都与上一版相同：逐个成员比较，或列明它为何不必比较；与上一版
  完全相同的语句算收窄，不论条件写了什么。
- **平台新增与租户同 id 的策略**：平台候选新增的策略 id 若已被某个租户文档使用（定义或绑定），拒绝发布并列出这些文档（RC1-9）：租户定义的 id 会在那个租户里二义
  （引擎对此 fail closed），只绑定不定义的会被重新指向平台的那条。读不到头的租户按使用处理（503）。精确副本的例外见 §9.4。

#### 7.4.2 语义

设授权者为 g（控制面请求的主体，带本次请求的成员关系），片段 G 授出到主体集合 S_G（T 中满足绑定主体的那些主体）与作用域集合 σ_G。

> **定义**：G 被 g 包含，当且仅当对任意请求 r——其主体 s ∈ S_G、作用域的 `(app, space)` ∈ σ_G、G 匹配 r——把 r 的主体换成 g（成员关系换成 g 的，其余
> 动作、资源、环境、`scope.tenant/app/space` 不变）得到的请求 r[s := g]，在当前发布的快照下对 g 是 Permit。

这就是 RFC 0001 §3.7"授权者本人在同一作用域内拥有的权限的子集"的精确含义：被授权者经 G 能做的每一件事，授权者本人在同一个资源、同一个作用域上也能做（`GRT-1`）。
这里的 Permit 只指策略求值，不含 RFC 0004 §4.6 的空间成员门：附加、主体绑定与 `Anyone` 绑定对 g 按 `(*, *)` 适用，g 在没有角色的 Space 里也算持有它们
（RFC 0012 §7.3 的租户 Owner 写法依赖这一点）。被授权者仍受同一道门约束。
下面的算法是这个定义的**可靠的**（不会误判为包含）但不完备的近似，判断不了就是 UNKNOWN，从不按"大概包含"放行（`GRT-2`）。

#### 7.4.3 算法

```
analyze(g, change) : List<(piece, YES | UNKNOWN(reason))>
  0. g 是信任根（§7.3）→ 全部 YES，记入审计
  1. pieces = §7.4.1 的拆分
  2. Allow(g) = g 的适用 ALLOW 语句，每条带 applicability：g 在哪些 (app, space) 上能用到它
        Anyone / Principal 绑定：绑定的 (app, space)
        附加（attachment）：(*, *)
        Role 绑定 (app_b, space_b)：app_b × (space_b ∩ { s | 绑定的角色 ∈ g.memberships.roles[s] })
  3. Deny(g) = g 的适用 DENY 语句中，**不是**经 Anyone 绑定得到的那些（Anyone 的 DENY 对被授权者同样生效，见下）
  for piece G = (action a, resource ρ, condition C_G, σ_G, S_G) in pieces:
      if g.tenant != T:                                         UNKNOWN(CROSS_TENANT)
      if G 授给租户 (0) 的 Anyone:                              UNKNOWN(ANONYMOUS)
      σ' = refine(σ_G, keys(C_G, scope.app), keys(C_G, scope.space))       // RFC 0005 §4.1：条件里对作用域的约束收窄 σ_G
      C_G' = C_G 中 subject.tenant、scope.tenant 代换为 T                   // 对 g 和被授权者都等于 T
      found = false
      for H in Allow(g):
          if not covers(H.applicability, σ'):        continue    // σ' 的每个 (app, space) 都在 H 的适用范围内；σ' 含 * 时 H 必须在该维也是 *
          if not expiresNoLater(H, G):               continue    // 见下"到期"
          if not (a ⊑ H.actions):                    continue    // RFC 0005 §5.5
          if not (ρ ⊑ H.resources with vars):        continue    // 见下"捕获变量"
          C_H' = specialize(H.condition, g)                       // 见下
          if C_H' == FALSE:                          continue
          if C_H' 含 ext.* 原子:                      continue    // 外部属性可能与主体有关，无法比较
          if C_H' == TRUE or implies(C_G', C_H') == YES:  found = true; break   // H 无条件（或代换后恒真）；否则 RFC 0005 §4.2
      if not found:                                  UNKNOWN(NOT_COVERED，附最接近的 H 与未满足的一项)
      else if ∃ D ∈ Deny(g) overlapping G on σ' and not disjoint(D, G):   UNKNOWN(DENY_OVERLAP, D)
      else YES
```

- **授权者的权利与引擎读的完全一致**：
  - `subject.attributes.*` 经引擎所用的同一个函数读取（任何 JSON 类型的值的 `toString()`），共用而不是复制（`GRT-5`，RC1-2）。
  - **app 文档全部读入**（`GRT-6`，RC1-4）：授权者的角色能触及的每个 app 文档都要读入，不论变更点名哪个 app。控制面经一份只列 app 的小列表
    `<p>:control:apps:all`（带 `complete` 标志）列出全部 app 文档逐个读头（反向引用索引不记录 app 绑定自己的 `perm:` 策略）。app 首次写索引时加入列表；
    列表缺失时以未完成状态创建；它在平台的首个修订写入成功之后、且没有列表缺少的有头 App 键时标为完成，`repair-references` 按同一判定标完成；
    控制面启动时与每次回收都对账，发现完整的列表缺少有头的 App 键就标回未完成；本实例首次对账成功之前不信任列表（分析在首次读列表前先对账，失败即不可信，
    最多每 30 秒再试一次；启动对账按退避重试，1 秒起翻倍，至多 1 分钟）。列表缺失、未完成、读不到、含无法解码的条目，或点名的 app 有头却不在列表中，
    触及变更没点名的 app 的片段一律 UNKNOWN（`UNREADABLE`），所以列表丢失后 fail closed；触及的 app 文档读不到，或授权者在该 app 的成员关系读不到，同样 UNKNOWN。
  - 平台与租户同 id 的策略在分析中是二义的：授权者经它什么也不持有。
  - 边界不是策略：授出分析不把边界当作策略读（`CTL-32`）。
- **到期**（`GRT-3`，RC1-3）：经带 `expiresAt` 的绑定持有的语句，只包含自身绑定不晚于它到期的片段；授给附加的片段、没有到期或到期更晚的片段不被它包含
  （`NOT_COVERED` 的不足项 `EXPIRY`）。
- **`specialize(C_H, g)`**：把 C_H 中只与授权者有关的属性代换成 g 的值并做常量折叠：`subject.id`、`subject.authenticated`（真）、`subject.tenant`（T）、
  `subject.roles`、`subject.scopedRoles`、`subject.attributes.*`（来自 g 的 token），以及 `scope.roles`（σ' 只有一个空间时代换为 g 在该空间的角色；多个空间时
  各空间的值不同就保留为原子，于是这条 H 只有在 C_G' 里有同样的原子时才能用上——而 C_G' 中的 `scope.roles` 指的是被授权者，所以实际上用不上，结果是
  UNKNOWN，可靠）。折叠后为真的原子从 `and` 中去掉，为假的让整个 `and` 为假。代换之后 C_H' 只剩与请求有关的属性（动作、资源、环境、`http.*`、
  `request.*`、`scope.app/space`），它们在 r 与 r[s := g] 上取值相同，这是可靠性论证的关键（§7.4.5）。
- **捕获变量**：C_H 引用 `resource.var.x` 时，ρ 必须在同一个段位置捕获变量（名字可以不同，比较前按位置重命名 C_G' 中的引用）；做不到就把这条 H 当作不包含。
  条件里的资源变量一次全部改名，不逐个替换（`GRT-8`）：逐个替换可能把两个不同的变量改成同一个，据此得出的"已包含"与"收窄"都是错的。
- **`disjoint(D, G)`**：动作没有公共元素（`service:verb` 集合在通配展开后不相交），或资源模式在某个前导字面量段上不同。只做这两种语法判断，其余视为重叠。
- **为什么排除 `Anyone` 的 DENY**（Q8）：经 `Anyone` 绑定（平台层，或 `Tenant(T)`）的 DENY 对每个被授权者按他们自己的属性同样生效，被授权者经 G 得到的访问
  仍受它约束。把它们计入，就会出现"平台规定没有安全许可的人不能导出；授权者没有许可，于是不能把导出授给有许可的人"这类误报，而这正是最常见的平台 DENY 形态。
  只与 g 个人有关的 DENY（主体绑定、角色绑定、附加）计入：g 被单独拒绝的事，不能转手授给别人。严格按 §7.4.2 定义的备选是全部计入（Q8）。
- **为什么 `(0)` 的 `Anyone` 总是 UNKNOWN**（`GRT-7`）：默认租户 `(0)` 是未认证调用方所在的地方，授给它的 `Anyone` 就是授给匿名请求，从不按包含放行。
- **只用一条 H**：一个片段必须被**某一条** H 整个包含，不做"被 H1 与 H2 的并集包含"的推理。拆片段（§7.4.1）已经覆盖了最常见的并集：多个动作、多个资源。
- **复杂度与预算**（`CTL-49`）：片段数 × |Allow(g)| 次 `implies`；条件节点数 ≤ 64（RFC 0005 §3.5），每次是多项式时间。一次分析至多做它的比较预算
  （`ComparisonBudget.MAX_COMPARISONS`，四百万次）那么多次比较，按分析的顺序花；超出预算绝不回答"已包含"：预算耗尽时正在比较的语句算授出，其后到达的每个片段
  算 UNKNOWN（`TOO_LARGE`），所以没比较过的部分需要审批。分析的代价随文档大小线性增长（10 万条目的变更约 4.7 秒）。§14 给出预算。
- 越权项的原因是一个枚举（`Escalation.Reason`）：`CROSS_TENANT`、`NOT_COVERED`、`DENY_OVERLAP`、`UNRESOLVED`、`UNREADABLE`、`ANONYMOUS`、`TOO_LARGE`、
  `NOT_ANALYZED`（只有信任根能单人做的平台、app 与边界变更，§7.4.4、§7.5）、`BREAK_GLASS`（§8）；信息性的 `TENANT_BINDINGS`（§7.5）、`ROLE_CLASS`（§7.4.7）、
  `DETECTION_TIMED_OUT`（§5.4）；以及 `UNKNOWN`（更晚的版本写下、本版本不认识的名字，从不是信息性的）。

#### 7.4.4 收窄与 DENY

- **收窄的判定**（语法）：新语句 S' 相对旧语句 S 是收窄，当且仅当 `effect` 相同、S'.actions ⊑ S.actions、S'.resources ⊑ S.resources、`implies(S'.condition, S.condition) = YES`
  （条件里的变量按 `GRT-8` 一次全部改名后比较）。一次修改不满足它，就按"新语句"处理（ALLOW 产生片段；DENY 是新增 DENY）。
- **新增 DENY**：在有 `cosec:write` 的范围内一律允许（RFC 0001 §7.1）。
- **删除或放宽 DENY**（§3 M6，Q9，`CTL-87`）：**租户文档**里的 DENY 在有 `cosec:write` 的范围内可以删除或放宽，不论它是谁写的，平台主体写的也一样。理由：租户层只能在平台层允许
  的范围内放宽——删掉租户文档里的 DENY 之后，访问仍要经过某条 ALLOW（它在写入时已经过授出分析，或者由平台写入）、平台层的全部 DENY 与边界。
  **没有受保护的条目**（DR1-E-3，维护者 2026-11-24）：平台写进租户文档的 DENY 是劝告性的；平台要租户解除不了的限制，用租户的边界（只有平台主体能设，`BDY-2`）或平台文档。
  `protected` 标志与 `cosec:unprotect` 留到 8.1：届时设置与去掉标志同样需要 `cosec:unprotect`，否则租户管理员给自己的条目打标之后就再也删不掉它。
  8.0 之前的代码里有过只做了一半的检查（分析一侧要求 `cosec:unprotect`，格式里却没有这个标志，于是从不运行）；它已删除，代码、规则与文档说同一件事。
  **平台与 App 文档**（维护者 2026-11-09 决定，`CTL-31`）之上没有更高一层的 DENY 或边界，删掉一条就放宽了每个租户能做的事，所以需要第二个人：删除含 DENY 的策略、
  删除所绑策略含 DENY（或读不到）的绑定，各记一条 `NOT_ANALYZED`；信任根可以单人完成，`four-eyes` 时信任根也要第二个人。按展开后的文档判断（RFC 0012 §6），
  所以删除角色、或用 `putRole` 去掉这样的权限，按它不再派生的每条绑定计算。撤销 break-glass 绑定不在此列（§8，单人）。文档读不到是 503，不跳过审批。
- **删除绑定、删除 ALLOW**：收窄，一律允许。撤销访问不应该比授予访问更难。

#### 7.4.5 可靠性与性质测试

**论证**（`implies` 与 `⊑` 可靠的前提下）：设算法对 G 给出 YES，取任意满足定义前提的 r。G 匹配 r，所以 C_G' 在 r 上为真；由 `implies(C_G', C_H') = YES`，C_H' 在 r 上为真。
C_H' 只含与请求有关的属性，它们在 r[s := g] 上取值相同，而 C_H' 是 C_H 对 g 的代换，所以 C_H 在 r[s := g] 上为真。a ⊑ H.actions、ρ ⊑ H.resources，所以 H 的动作与资源匹配
r[s := g]；r 的作用域在 σ' 中，`covers` 保证 H 在该作用域按策略求值适用于 g（不含成员门，见 §7.4.2）；H 的绑定不早于 G 的到期（`GRT-3`），所以 G 生效时 H 仍生效。
于是 H 对 g 命中。g 的 DENY 中，`Anyone` 的那些对 r 与 r[s := g] 的取舍按各自的属性进行，不在定义的保证之内（这是 Q8 的有意取舍）；其余的与 G 不相交，不命中。
边界对 g 与被授权者同样适用。所以 r[s := g] 对 g 是 Permit（除去 `Anyone` DENY 的情形）。

| 性质 | 内容 | 位置 |
|---|---|---|
| A5 **授出分析可靠** | 随机快照、随机授权者与成员关系、随机片段；算法给出 YES 时，随机生成大量满足前提的请求 r，断言 r[s := g] 对 g 不是 Deny（`Anyone` DENY 命中的样本除外）。生成器偏向"授权者语句 AND 额外条件"、子模式、子集作用域，以测到 YES 分支 | `control`：`GrantPropertyTest` |
| A6 **收窄判定可靠** | 判为收窄的修改，修改后语句匹配的请求集合 ⊆ 修改前的（随机请求） | `control`：`GrantPropertyTest` |
| A7 **模式包含可靠**（N7） | `a ⊑ b` 为真时，随机动作与路径中不存在匹配 a 而不匹配 b 的 | `engine`：`PatternContainmentPropertyTest`；`control`：`GrantPropertyTest` |
| A8 **不越权的端到端形式** | 随机生成一串由非平台管理员发起、全部得到 YES 的变更并依次发布，任何主体的 Permit 集合都 ⊆ 初始时"某个授权者的 Permit 集合"的并集（按 §7.4.2 换主体） | `control`：`GrantPropertyTest` |

#### 7.4.7 角色类别

对租户文档持有 `cosec:manage-roles` 的作者，其只写入或删除角色（`putRole`、`removeRole`）的变更不因"谁在授出"而等第二个人（`CTL-79`）。这样的变更能授出什么
由格式界定，不由作者界定：租户的角色只派生出本租户成员、在该角色的应用里、绑到该应用文档所定义的权限策略的绑定，而应用文档是人批准的；租户隔离把成员限制在
自己租户的文档上，租户边界封顶。

- 类别只放行对"谁在授出"的疑问（`CROSS_TENANT`、`NOT_COVERED`、`DENY_OVERLAP`），并且只在该变更的每一条越权项（分析的与其余的，例如 break-glass 绑定的）都属于这三种时
  才放行：`CROSS_TENANT` 是服务主体在租户之外投影角色的情形；`NOT_COVERED` 是租户内的持有者交出它自己不持有的目录权限，这正是管理角色的意思；`DENY_OVERLAP`
  在一条约束作者的 DENY 可能与角色授出的东西重叠时出现，而 DENY 在判定时照旧约束它约束的人。分析说不清的（读不到的应用文档、无处定义的策略、用尽的预算）照旧等人；
  混有其他操作的变更整体照旧分析。`cosec:write` 与 `cosec:grant` 照旧判定。
- 放行时以一条说明性的 `ROLE_CLASS` 记录取代被放行的各条，写明持有者与放行了什么。`:check` 给出同样的答案：持有者知道变更不会等人，其他人知道会等哪一条。
- 没有应用的角色、或属于控制面自己应用（`cosec.control.app-id`）的角色永远不属于类别，写入与删除都是，覆盖同 id 的角色时新旧两个角色都受这条约束：
  它的成员持有对自己租户文档的控制调用，谁治理控制面是人来任命的。别的应用的角色不让任何控制调用通过，不论其目录写了什么：控制请求在控制面的应用里判定。
- 应用文档与平台文档永远不属于类别。授权在发布时由发布者在当前的头上重新判定，与整个授出分析一样：变更已检查、在影子窗口中或已就绪时授权被收回，退回
  `AWAITING_APPROVAL`，什么也不发布。
- 经服务配置时类别照样适用（`CTL-81`）。

### 7.5 审批

- **越权项按语句分组**（`CTL-88`，第二轮 DR2-E-1、DR2-E-3）：授出分析不能证明被包含的片段按（策略、语句、原因）分组记录，每组一项，subject 写出组里的片段数与它们的 SHA-256，detail 写出前三个；
  至多 200 组，其余合为一项 `TOO_LARGE`，超出比较预算的片段那一项同样带片段数与摘要。审批覆盖的是 subject，所以组里多一个、少一个或换一个片段都要重新审批；分组不改变变更是否需要审批，
  被略去的部分算未分析，变更从不因此干净地通过。上界写在 `contract/control/escalations.json` 里。此前每个片段各记一项，一次提案能让变更记录与事件达到数百 MB。
- 含越权项的变更在影子窗口关闭后进入 `AWAITING_APPROVAL`。审批人看到：每一项越权、原因、最接近的授权者语句、影子报告。
- **谁能批准**（`APR-1`）：在目标文档上有 `cosec:approve` 的人，并且**不是**变更的作者。审批是人的行为：
  - 工作负载的凭据（API key，或服务自己的身份 `service`）认证的主体从不批准（403），不论它持有什么（`APR-7`，`IDN-34`）；工作负载按出处（CoSec 的 API key 认证器）
    与凭据上的保留方法名 `api-key`、`service` 认定，转发的身份也算。
  - 凭据不带 id 的主体也不能批准（403）：发布时无法核实它的吊销。
  - 设置租户边界的变更只有平台主体能批准，批准时与发布时都查；也只有平台主体能拒绝或放弃它（`BDY-2`）。
  - 四眼模式下，平台主体的变更由另一位平台主体批准。
  - 审批不是服务配置上的路由（`CTL-58`）：服务发起的、等人的变更在运维端口上批准（`CTL-81`）。
- **发布时再判一次**（`CTL-9`）：发布在当前的头上重新判定发布者对每个目标的授权与授出分析；它单独发布不了的等待审批，什么也不写。
- **批准绑定到内容**：批准记录候选摘要与越权项列表的摘要；变基、改动候选都让批准作废。批准 72 小时内有效（`cosec.control.approval.expire-after`，`APR-2`）。
- **发布时再核实批准人**（`APR-5`、`APR-8`、`APR-9`，RC1-11）：批准记录批准人的 token 属性（任何 JSON 类型）、成员关系、凭据 id（token 的 `jti`）、签发时间（`iat`）与凭据的种类（`approval.kind`，取自批准那一刻批准人自己的凭据）。发布时：
  - 只计入写明是人的批准（`APR-9`，2026-11-25）：没有种类的（记下种类之前的宿主写的）与写着别的种类的都不算数，变更回到 `AWAITING_APPROVAL` 并附发现，要重新批准。“工作负载从不批准”（`APR-7`）因此在发布这一刻可以核对，而不是靠“当初放行过”的假定；旧宿主改写记录时丢掉这个成员，后果只是重新批准；
  - 按记录的成员关系与属性重新检查批准人对当前文档的 `cosec:approve`，失败或无法判定则回到 `AWAITING_APPROVAL` 并附发现；
  - 那个 token 已被吊销、或批准人截至当时签发的全部 token 已被吊销（容差为 `cosec.authentication.revocation.skew`），批准不再算数；吊销读不到是 503，批准保留；
  - 没有记下凭据 id 的批准（升级前的、旧实例接受的）不算数，须重新批准；
  - 成员关系来自提供者的批准人判定两次，都须放行：一次用"批准时持有 ∩ 现在持有"的角色加提供者当前的附加策略，一次用提供者完整的当前答复。附加策略取当前答复
    而不取交集，否则批准之后附加的 DENY 会被丢掉（deny-first）。
  - starter 的控制面 Pipeline 带上应用的 `MembershipProvider` 与 `RevocationReader`（RC1-13）；没有控制面可用的 `RevocationReader` 时启动失败（`RevocationReader.NONE` 是显式的退出），
    `cosec.jwt.token-validity.refresh` 小于 `cosec.control.approval.expire-after` 时也启动失败。变更的应答不含批准人的成员关系、属性与凭据（`CTL-61`）。
- **信任根之外的边界改动**（设置、替换、移除）是越权项 `NOT_ANALYZED`，要第二个人批准：它可能放宽租户的所有 Permit，而 §7.4 的分析看不到这一点；四眼模式下的信任根同样处理。
- **应用变更触及的租户**（`CTL-48`，RC1-34）：应用变更放宽了一条被各租户的角色或绑定列出的权限策略时，变更按策略各带一条信息性条目 `TENANT_BINDINGS`，列出租户文档键
  与绑定，数目取自反向引用索引，不读任何租户文档。这条信息性条目绝不代替需要审批的越权项：只有它是信息性的，审批仍须覆盖其余每一项，放宽策略本身仍有 `NOT_ANALYZED`；
  它的变化不使批准失效。
- **四眼原则**（Q10）：信任根自己的变更不做授出分析（§7.3），默认不需要第二个人；`cosec.control.approval.four-eyes=true` 时，信任根的变更中分析说不清的部分也需要另一位
  平台主体批准。break-glass 总是四眼（§8）。
- 批准、拒绝都是 `ChangeEvent`，按 §10.5 投递。

### 7.6 平台边界 `withinBoundary`

**数据**：

```jsonc
// Platform 文档
"boundaries": { "default": "boundary-standard" },          // 可省略：没有默认边界
"policies": [ { "id": "boundary-standard", "boundary": true, "statements": [ /* 只有 ALLOW */ ] }, … ]
// Tenant(acme) 文档：只有 cosec:boundary 能写这个字段
"boundary": "boundary-restricted"                            // 可省略：用默认边界
```

- 有效边界 = `Tenant(T).boundary ?: Platform.boundaries.default ?: 无`。租户文档不存在（`Absent`）时用默认边界；租户文档不可用时本来就是 `unresolved`（RFC 0004 §6.1），
  不会走到边界。
- 边界策略只能在 `Platform`，标 `boundary: true`，只含 ALLOW 语句，至多 64 条；不能被绑定或附加：绑定指向边界策略在控制面是 422 `REFERENCES`，数据面找不到该 id 的策略
  （`CTL-32`）。租户的 `boundary` 若指向的不是平台的边界策略，是 `$.boundary` 处的 `REFERENCES` 错误；租户的边界进入反向引用索引（§5.8）。平台租户 `(platform)` 不能设边界。
- 边界约束租户 T 的主体的**全部** Permit，包括经平台层绑定得到的（M8）。平台层要给某个租户更多，就换一个更宽的边界。
- 设置租户边界只归平台（`BDY-2`）：非平台主体提议即 403，不论它持有什么。

**引擎**（`engine`，扁平算法唯一的改动）：

```
    for (s, via) in candidates(applicable) where s.effect == ALLOW:
        when matchWithGuard(s, req):
            MATCH -> return withinBoundary(Permit(ref(s, via)), req, view)
            …
withinBoundary(p, req, view):
    B = view.boundary ?: return p                       // 没有边界：恒等，不分配
    when matchAny(B.statements, req):                   // 与普通 ALLOW 相同的匹配，含 onMissing（RFC 0006 §5.4.3）
        MATCH    -> p
        NO_MATCH -> Deny(StatementRef.Boundary(B.id))   // trace 与审计的 by；via = BindingRef.Boundary(T)
        ERROR    -> Indeterminate(BoundaryUnavailable(B.id))
```

- 边界是请求的性质，与哪一条 ALLOW 命中无关，所以只检查一次。`matchAny`：任一语句 MATCH 即 MATCH；否则任一 ERROR 即 ERROR；否则 NO_MATCH。
  没有任何边界数据（租户没有边界、也没有默认边界）时引擎整段跳过检查（`SnapshotView.bounded`）。
- 边界语句缺少外部属性且写了 `onMissing: nomatch` 时按普通的未命中处理，其他失败为 `Indeterminate(BoundaryUnavailable)`。边界的语句条件与策略条件读的外部属性进入属性计划，
  由提供者照常取得，按取到的值判断边界（`ATR-8`）。
- 结果只可能把 Permit 改成 Deny 或 Indeterminate，从不产生 Permit：deny-first 与失败即拒绝不受影响（`BDY-1`：P-B2；没有边界时恒等，P-B1）。
- 状态码沿用 RFC 0006 §6.1：`Deny` 401/403，`Indeterminate` 503；响应体不区分边界，边界拒绝的 problem 是 `unauthorized`/`forbidden`，边界不可用是 `unavailable`（RFC 0006 Q27）。
  审计的原因码有 `BOUNDARY`（`cosec-api` 的 `AuditReasonCode`），原因里带边界 id；指标 `cosec.authorization` 的 `source` 与 `cause` 标签为 `boundary`。
- break-glass 的主体只能是平台租户的主体（§8），平台租户没有边界，所以 break-glass 不受边界约束，也不需要特例。

| 方面 | 规则 |
|---|---|
| 谁能申请 | 平台租户中对 `doc/platform` 有 `cosec:breakglass` 的主体。申请、发布已批准的申请、撤销都只需要它，不需要别的控制动作；它只在 `BREAK_GLASS` 变更上代替 `cosec:publish`。申请先授权、后读平台文档：没有它的申请在读平台文档之前得到 403，不论那个 id 的绑定存在与否，所以被拒绝的人学不到已有哪些绑定（`BRK-12`） |
| 谁能批准 | 平台租户中有 `cosec:approve` 的另一个主体（总是四眼，不受 `four-eyes` 配置影响：新的或改动的 break-glass 绑定总要第二个人批准，不论谁提议，`APR-4`）；工作负载的凭据从不批准（§7.5） |
| 绑定的主体 | `Principal((platform), <id>)`，可以是申请人自己；只有经 CoSec 自己的 token 验证的主体能经它得到权限（`BRK-8`，RFC 0009 §4.2） |
| 绑定 id | 由系统派生，调用方不能指定；已被占用即 409。break-glass 绑定从不替换另一条绑定（`V5` 发现）（`BRK-3`，RC1-29） |
| 指向 | 任一平台策略，默认 `cosec:root`；鼓励授出比 root 窄的应急策略 |
| 期限 | 必须有 `expiresAt`；`expiresAt - 发布时刻` ≤ `cosec.control.break-glass.max-duration`（默认 4 小时，最多 24 小时），发布时再查一次 |
| 流程 | `kind = BREAK_GLASS` 的变更：授权 → 校验 → 编译 → 批准 → 发布；**免影子窗口**（按种类）。变更的种类由入口决定：提议只能是 `PUBLISH` 或 `BREAK_GLASS`；创建或改动 break-glass 绑定的变更，不论种类，都需要 `cosec:breakglass` 与 `REQUIRED` 审计（`BRK-5`）。规则按内容判断（`BreakGlassRules.touches`），从不只看种类 |
| 审计 | 申请的 `ChangeEvent(BREAK_GLASS_REQUESTED)`、批准的 `BREAK_GLASS_APPROVED` 与发布的 `PUBLISHING` 必须被至少一个 `REQUIRED` 的 `ChangeListener` 写入成功；没有配置 `REQUIRED` 监听器时拒绝（503），与 RFC 0006 Q20 对使用的要求对称。批准先核对候选摘要，再要求 `REQUIRED` 监听器，并在保存状态转移之前写 `BREAK_GLASS_APPROVED`（`BRK-3`，RC1-30）。`REQUIRED` 监听器抛出的 `CancellationException` 只在调用方的协程已取消时重抛，否则按监听器失败处理（503，RC1-31） |
| 出处 | 修订的出处（§5.3）记录作者与批准人。数据面编译器不要求绑定带任何元数据：写在文档里的元数据挡不住能写文档的人，两人原则由控制面对每种变更强制（RC1-27） |
| 使用 | 经 break-glass 的 Permit 至少要有一个 `REQUIRED` 的 `DecisionListener` 成功（RFC 0006 §9.4.3）；事件的 `via` 是这条绑定，可与出处中的变更对上 |
| 冻结 | 生效的 break-glass 绑定（未过期，或没有期限）所授出的策略在绑定生效期间不变：改动它的变更需要 `cosec:breakglass` 与 `REQUIRED` 审计，并且从不干净地通过检查（`BRK-6`）。过期绑定所授出的策略按普通策略处理 |
| 回滚 | 回滚受全部 break-glass 规则约束：会创建、改动或带回 break-glass 绑定，或改动生效绑定所授出的策略的回滚，与上一行同样处理；只删除 break-glass 绑定的回滚两者都不需要，也没有影子窗口（`BRK-7`，§5.6） |
| 撤销 | `revoke(bindingId)`：有 `cosec:breakglass` 的任何平台主体，单人，免影子（收窄）。撤销仍生效的绑定抢占文档的暂存槽（§5.5，`BRK-9`）。`revoke` 先授权（与申请同一个检查）再读槽。`DELETE /break-glass/{bindingId}` 只在调用之后该绑定在平台头上不再生效时答 2xx，不论是谁删除的；头上没有该 id 的绑定、也没有调用方可见的停住的撤销占着槽时 404；该 id 的绑定不是 break-glass 绑定（生效或已过期）时 409；其余 409，写明调用方变更的状态。404 与"不是 break-glass 绑定"的 409 都不提议任何变更。撤销以 `CONFLICTED` 结束，或在提议、暂存之前头移动了，只要绑定仍是生效的 break-glass 绑定，就在新的头上再做一次，至多再做 3 次。输给另一个删除同一绑定的调用时可能答 409，此时绑定已不生效，重试答 404。对同一绑定再撤销一次会发布停住的撤销，事件记下第二位撤销人与理由（`BRK-11`） |
| 放弃 | 撤销仍生效的 break-glass 绑定的变更只有其作者能放弃（其他人 403，看不到的人 404），被撤销的主体也不能。每次放弃写一条 `ChangeEvent(ABANDONED)`，备注以 `author <tenant>/<principal>` 开头；`BREAK_GLASS` 变更的放弃需要 `REQUIRED` 监听器（否则 503），并在保存状态转移之前写入；其他变更的放弃尽力投递，在转移之后（`BRK-10`，RC1-51） |
| 过期 | 由引擎按 `environment.time` 判定（RFC 0004 §4.2），不需要发布；每个实例按自己的时钟判定（DR1-E-15）。控制面不发布 `kind = EXPIRE` 的变更：过期的绑定留在平台文档里，直到一次撤销删除它，这样的撤销像任何变更一样等暂存槽（`BRK-9`）；`EXPIRE` 作为出处的一种保留在格式里 |
| 续期 | 不提供；重新申请，重新批准 |

- **"只能由控制面创建"怎么成立**（§3 M7，Q12）：快照文档的写入方只有控制面的存储（控制面与 `cosec-migrate`）。不运行控制面的进程把快照文档与候选文档声明为只读，
  所以只有读权限的 Redis 用户就够用，Redis 拒绝它的写入（`SNP-18`）；`storage.md` 给出把每一方限制在这个范围的 ACL 示例。剩下的写入方是拿到控制面 Redis 凭据的人，
  在威胁模型之外（§1.2）。
- **`cosec-migrate` 不写任何 break-glass 绑定**（RC1-27）：`convert` 不生成，`publish` 与 `bootstrap` 拒绝含 break-glass 绑定的输入；break-glass 在切换之后经控制面按两人流程申请。
  一个长期有效的 root 正是 break-glass 要取代的东西。
- **`four-eyes` 关闭时**（RC1-28）：break-glass 的两人保证约束的是 break-glass 流程，不约束单个信任根管理员：信任根的变更不做授出分析（§7.3），他可以用一次普通变更
  绑定任何平台策略。8.0 把这一点写进文档；平台文档的每次发布都要求 `REQUIRED` 审计放到 8.1。

## 9. 租户自助

### 9.1 租户能写什么

| 对象 | 租户主体（经 `cosec:tenant-admin`） | 约束 |
|---|---|---|
| `Tenant(T)` 的策略 | 能 | id 不与平台层重名，平台策略的完全相同副本除外（N2，`CTL-14`，§9.4）；不用保留前缀；设为可附加或修改可附加策略的 ALLOW 要经授出分析（§7.4.1） |
| `Tenant(T)` 的绑定，主体 `Principal(T, ·)`、`Role(T, ·)`、`Anyone` | 能 | 主体必须属于 T（RFC 0004 的编译检查）；授出分析 |
| `Tenant(T)` 的角色（RFC 0012） | 能 | 角色派生出的绑定按 §7.4.1 分析（`ROL-9`）；只写角色的变更见 §7.4.7 |
| 绑定指向 `Platform` 的策略 | 能 | 被引用的策略存在且不是边界策略（`CTL-32`）；进入反向索引 |
| 绑定指向 `App(a)` 的权限策略 | 能（N1，Q14） | 绑定的作用域 `app = Exactly(a)`（`TNT-4`）；进入反向索引 |
| `boundary` 字段 | 不能 | `cosec:boundary`，平台（`BDY-2`） |
| 租户文档里的 DENY | 能，在写权限范围内 | 平台写进去的也一样，是劝告性的；要强制用边界（`CTL-87`，§7.4.4） |
| break-glass 绑定 | 不能 | RFC 0004：只在 `Platform`；§8 |
| `Platform`、`App` 文档（含 `Catalog`） | 不能 | 硬性规则（§7.2） |

### 9.2 隔离检查

在 RFC 0004 已有的编译检查（租户文档只引用本租户或平台层、主体属于本租户、主体绑定上限、break-glass 只在平台）之上：

| 检查 | 在哪里 | 违反时 |
|---|---|---|
| 文档绑定到它的 key：`Tenant(T)` 文档里出现的租户 id 都是 T（与 RFC 0003 对 `App` 文档的要求相同） | 数据面编译器 | 编译错误 |
| 允许的跨文档引用只有 `Tenant → Platform`、`Tenant → App 权限策略`（N1）、`App → Platform` | 数据面编译器 | 编译错误 |
| 租户策略 id 不与平台层重名，完全相同的副本除外 | 控制面 V2（`CTL-14`）；数据面遇到同名按 N2 处理 | 422；数据面 `Indeterminate(AmbiguousPolicy)`（内容相同除外） |
| 租户主体只能写自己的文档 | 控制面硬性规则（`TNT-3`） | 403 |
| 影子报告、历史、解释按租户隔离 | 控制面授权（`cosec:read`、`cosec:shadow-read`、`cosec:explain` 的资源是文档） | 403 |
| 以变更 id 为参数的每一步（`get`、`approve`、`reject`、`publish`、`stage`、`skipShadow`、`rebase`、`abandon`）先判可见：调用者不能读的变更与不存在的同为 404 `no change <id>`，在读状态、把过期变更写成 `EXPIRED` 之前就返回。可读 = 租户隔离加该文档的 `cosec:read`，或是变更的作者 | 控制面（`CTL-15`） | 404 |

性质 P12（RFC 0004 §9.5，"修改 U 的租户文档不改变 T 的主体的任何决策"）扩展为经控制面发布：随机的租户管理员对 U 的任意一串变更，T 的主体的决策不变（`control`：
`ControlTenantIsolationTest`）。

### 9.3 租户引用应用目录（N1）

`App(a)` 的权限策略（`perm:a/<permissionId>`）是应用提供的"可以授出的东西"。租户在自己的文档里写 `Role(T, editor) → perm:a/order.read`，作用域 `(a, team-a)`：

- 评估时，`scope.roles` 非空且 `scope.app = a` 时本来就加载 `App(a)`（RFC 0004 §7.4）；租户文档把 `a` 的权限策略绑给 `Anyone` 或主体时，`a` 中的请求也读 `App(a)`，
  不论有没有角色（`TNT-4`，RC1-17）。查找按 RFC 0004 §6.4 在 `Tenant` 的 `byRole` 中进行，被指向的策略从同一视图的 `App(a)` 中解析；在其他地方这样的绑定不编译。
- `simulate`、`explain` 与影子比较读执法会读的文档，不多也不少（`ViewDocuments.appOf`，`CTL-3`）：多读的文档会带进它的限流规则。
- 悬空（应用删除了这个权限）：`unresolved`（`MissingPolicies`），失败即拒绝。控制面的反向索引让应用删除被租户引用的权限之前就被拦住（§5.8）。
- 授出分析把它当作普通的授出：租户管理员要拥有 `perm:a/order.read` 的语句所授的东西（通常经 `cosec:tenant-admin` 之外的数据面角色）。
- 候选顺序：这类绑定排在 RFC 0004 §6.3 的第 5 组（角色绑定），在平台层的 `App(a)` 角色绑定之后、同组内按租户文档中的顺序。

### 9.4 `--partition by-owner` 与同名角色

RFC 0004 §5.2 方案 A 把 7.x 的数据全部放进平台层；控制面让运维逐步收窄它，而不需要停机或重新签发 token：

| 步骤 | 变更 | 影子窗口预期 |
|---|---|---|
| 1 | 对每个租户 T：在 `Tenant(T)` 中加入 `owner = T` 的可附加策略的**完全相同**的副本（`cosec-migrate partition plan` 生成这些变更，经 `apply` 提交） | 零差异：两层同名且内容相同，N2 规则正常解析 |
| 2 | 冻结：平台的那条还在时，控制面拒绝改动租户里的副本（`CTL-14`），租户持有副本时也拒绝改动平台的那条并点名租户（`CTL-29`），所以两层不会同名而内容不同 | — |
| 3 | 在 `Platform` 中删除它们（平台管理员）；删除副本或平台的那条都不被拒绝 | 别的租户的主体附加了它们：`BECAME_INDETERMINATE`。这就是 RFC 0004 C5 描述的语义变化，发布者按数字确认 |
| 4 | 租户此后自己维护副本 | — |

- V2 只接受与平台策略**编译结果完全相同**的副本（维护者 2026-11-07 决定，审计 issue #1224，选项 A）：N2 的"租户不能用平台已有的 id"与第 1 步原先互相矛盾，
  按本节原本的设计解决。平台删除自己那条时，租户里的副本就是绑定重新解析到的目标，按新授予分析（内容相同即没有新授予）。另一个选项（8.0 不提供分区流程，迁移一开始
  就用 `--partition by-owner`）没有采用：它收回一项已文档化的迁移路径。
- 同名角色跨租户（RFC 0004 §5.4）用同一套方法：在 `Tenant(T)` 中加 `Role(T, admin) → perm:a/…`（N1），再从 `App(a)` 中删除 `Role(null, admin)`。每一步都是普通发布，
  都有影子窗口和修订，回滚就是回滚。`cosec-migrate partition plan` 只生成变更请求，不写头。

### 9.5 DENY 上的 `onMissing: nomatch`

- 写这样一条 DENY，变更必须带确认：`confirmations: [{ "policy": "...", "statement": 3, "kind": "deny-nomatch", "digest": "<语句的摘要>" }]`。语句摘要包含策略的条件
  （`StatementDigest.of(statement, policyCondition)`）、不含确认本身：语句或策略条件变了，确认就不再匹配。回滚与提议一样携带 `confirmations`：恢复这样的 DENY 时要重新确认，
  旧修订的确认属于另一个人、另一次变更。
- 发布时控制面把确认写进语句：`"onMissingConfirmed": { "by": { "tenant", "principal" }, "change": "…" }`。确认只由控制面写入，作者写进文档的确认被丢弃。数据面编译器在
  **任何**文档里都要求 DENY + `nomatch` 带这个确认，否则编译错误（`ATR-6`；N6，Q13）。限流规则没有确认流程，它的 `onMissing: nomatch` 只能写在平台文档里（`ATR-7`）。
- 确认记入 `ChangeEvent`。`wiki/guide/security-model.md` 的失败即拒绝一节写明：这是策略作者显式选择的降级，不是运行时默认。

## 10. API

### 10.1 库

```kotlin
/** cosec-control（control/api/）。全部挂起，不阻塞调用线程；operator 来自宿主 Pipeline 的认证结果（含成员关系与来源）。 */
interface ControlPlane {
    suspend fun read(operator: Operator, key: SnapshotKey, revision: Long? = null): PolicyDocument
    suspend fun history(operator: Operator, key: SnapshotKey, before: Long? = null, limit: Int = 20): List<RevisionSummary>
    val listing: DocumentListing                                                        // GET /documents?kind=（CTL-68）
    suspend fun diff(operator: Operator, key: SnapshotKey, from: Long, to: Long): DocumentDiff

    suspend fun propose(operator: Operator, key: SnapshotKey, base: Long, operations: List<Operation>, note: String,
                        confirmations: List<Confirmation> = emptyList(), commit: Boolean = true): ChangeRequest
    suspend fun apply(operator: Operator, key: SnapshotKey, desired: PolicyDocument, mode: ApplyMode, note: String,
                      commit: Boolean = true): ChangeRequest                          // commit = false：只校验（CTL-78）
    suspend fun rollback(operator: Operator, key: SnapshotKey, toRevision: Long, note: String,
                         confirmations: List<Confirmation> = emptyList()): ChangeRequest
    suspend fun rebase(operator: Operator, change: ChangeId): ChangeRequest
    suspend fun startShadow(operator: Operator, change: ChangeId): ChangeRequest
    suspend fun skipShadow(operator: Operator, change: ChangeId, reason: String): ChangeRequest
    suspend fun approve(operator: Operator, change: ChangeId, candidate: String): ChangeRequest
    suspend fun reject(operator: Operator, change: ChangeId, reason: String): ChangeRequest
    suspend fun abandon(operator: Operator, change: ChangeId): ChangeRequest
    suspend fun publish(operator: Operator, change: ChangeId, ack: ShadowAck? = null, lockout: Boolean = false): ChangeRequest
    suspend fun get(operator: Operator, change: ChangeId): ChangeRequest
    suspend fun changes(operator: Operator, document: SnapshotKey?, state: ChangeState?, after: String?, limit: Int,
                        documents: (SnapshotKey) -> Boolean): ChangePage                // GET /changes（CTL-55）

    val breakGlass: BreakGlass                       // request / approve / revoke（§8）
    suspend fun simulate(operator: Operator, request: SimulatedRequest, candidate: ChangeId? = null): Simulation
    suspend fun explain(operator: Operator, request: SimulatedRequest, at: ViewVersion? = null): Explanation
    suspend fun analyze(operator: Operator, query: AccessQuery): AccessReport
    suspend fun propagation(operator: Operator, key: SnapshotKey, revision: Long): Propagation
}

sealed interface Operation {                         // 条目级；ifMatch 是条目当前内容的摘要，可选；章节操作不接受 ifMatch（400）
    class PutPolicy(val policy: PolicyDefinition, val ifMatch: String? = null) : Operation
    class RemovePolicy(val id: PolicyId, val ifMatch: String? = null) : Operation
    class PutBinding(val binding: Binding, val ifMatch: String? = null) : Operation
    class RemoveBinding(val id: BindingId, val ifMatch: String? = null) : Operation
    class PutRateLimit(val rule: RateLimitSource, val ifMatch: String? = null) : Operation
    class RemoveRateLimit(val id: String, val ifMatch: String? = null) : Operation
    class PutRole(val role: RoleDefinition, val ifMatch: String? = null) : Operation        // RFC 0012
    class RemoveRole(val id: RoleId, val ifMatch: String? = null) : Operation
    class PutCatalog(val catalog: Catalog?) : Operation                                    // 只在 App
    class SetLimits(val limits: ConditionLimits?, val budgets: DocumentBudgets? = null) : Operation   // 只在 Platform（N3）
    class SetAttributes(val attributes: List<Attribute>?) : Operation                     // 只在 Platform（N3）
    class SetBoundary(val boundary: PolicyId?) : Operation                                // Tenant 的字段；Platform 的默认边界
}
```

- `DefaultControlPlane` 实现这些操作；每次调用都经 `ChangeAuthority`，硬性规则在先。读操作（`read`、`history`、`diff`、`propagation`）需要目标文档的 `cosec:read`，
  `apply` 与 `rollback` 也先读头；`simulate`、`explain`、`analyze` 各需被模拟的租户文档上自己的动词（§10.3）。`cosec:shadow-read` 在 `ControlActions` 中定义，没有路由读影子报告
  （窗口的汇总在变更上，`cosec:read` 已覆盖）。`publish` 的 `lockout` 是发布者对 V4 发现的确认（§6.2）：候选会把发布者自己关在控制面之外时，没有它即 422。
- 客户端提议的变更至多携带平台 `limits.maxChangeOperations`（默认 20,000）个操作，超过即 400，写明数目与上限，在任何操作被授权或应用之前（`CTL-41`）；`apply` 与
  `rollback` 的操作由文档派生，受条目预算约束（`CTL-40`）。
- 章节操作（`PutCatalog`、`SetLimits`、`SetAttributes`、`SetBoundary`）的字段按文档格式的读取器校验：类型不对或越界即拒绝，从不变成另一个值，设定的每个上限都要写出（`CTL-28`）；
  它们不接受 `ifMatch`（400）；各项检查在解码后的候选上运行。
- `diff` 的 `sections` 列出策略、绑定与角色之外有差别的部分的名称（`catalog`、`boundary`、`limits`、`attributes`、`rateLimits`，按此顺序），每个部分按全部内容比较；
  都相同时是空列表。文档的每个成员必须恰好属于"头部"、"按 id 列出的条目"、"有名字的部分"三者之一，否则测试失败：给格式加成员的人不会漏掉差异（`CTL-39`）。
- `ControlStore`（`control/` 定义，`cosec-cocache` 实现）只有读写 §5.2 那几类数据的挂起方法，没有业务规则；内存实现供测试与单实例使用。

### 10.2 HTTP、服务端口与门面

starter 在类路径上有 `cosec-control`、且 `cosec.control.enabled` 不为 `false` 时运行控制面，`cosec.control.http.enabled`（默认真）时在宿主上注册函数式路由（WebFlux 或 WebMvc，
按宿主），位于 `{cosec.control.http.base-path}/v1`（默认 `/cosec/control/v1`）。`ControlHttp` 不依赖 Web 框架（`ControlBoundaryTest`）；每个路由要求宿主 Pipeline 放行的
`RequestSecurity`，没有就是 401，什么也不做；`RequestSecurity.of(SecurityContext)` 只对管道自己构造的上下文返回放行的安全信息。JSON 是控制面自己的线上格式；`docKey`
在路径中写作 `platform`、`app:order`、`tenant:acme`。

| 方法与路径 | 对应 |
|---|---|
| `GET /documents?kind=` | 列出租户或应用文档（`CTL-68`） |
| `GET /documents/{key}`、`GET /documents/{key}/revisions/{rev}`、`GET /documents/{key}/revisions?before=&limit=`、`GET /documents/{key}/diff?from=&to=` | `read`、`history`、`diff` |
| `GET /documents/{key}/revisions/{rev}/propagation` | `propagation`（§6.5） |
| `POST /documents/{key}:apply`、`POST /documents/{key}:rollback`、`POST /documents/{key}:check` | `apply`、`rollback`、只校验的 `apply`（`CTL-78`） |
| `POST /changes`（201）、`POST /changes:check`、`GET /changes/{id}`、`GET /changes?document=&state=&after=&limit=` | `propose`、只校验的提议、`get`、`changes` |
| `POST /changes/{id}:rebase`、`:shadow`、`:skip-shadow`、`:approve`、`:reject`、`:abandon`、`:publish` | 状态转换（§6.1） |
| `POST /break-glass`（201）、`POST /break-glass/{change}:approve`、`DELETE /break-glass/{bindingId}?reason=` | §8 |
| `POST /simulate`、`POST /explain`、`POST /analyze` | §10.3 |

| 状态 | 含义 |
|---|---|
| 200 / 201 | 成功；201 表示创建了变更请求 |
| 400 | 请求或文档格式错误（V1、V2），操作数超限，请求体超过上限，游标解不出 |
| 401 / 403 | 宿主 Pipeline 拒绝；或控制面的授权、硬性规则拒绝 |
| 404 / 410 | 不存在，或调用者看不到（`CTL-15`）；修订已被回收（`explain` 的历史版本） |
| 409 | 冲突，problem 的 `conflict` 写明是哪一种（`CTL-80`） |
| 412 | 条目级 `ifMatch` 不满足 |
| 422 | 编译错误、语义规则、反向引用、V4 未确认 |
| 428 | 缺少确认（`ack`、`nomatch` 确认）或缺少批准 |
| 500 | 存下的文档或记录解不出来 |
| 503 | 存储、审计、授权的 `Indeterminate` |

这是控制面 API 自己的状态表，与数据面的 `StatusMapping`（RFC 0006 §6）无关；"一条决策路径"的不变量只约束数据面。

- **问题体**（`CTL-24`，RC1-39）：控制面的问题类型沿用 RFC 0006 的词汇（`invalid-request`、`unauthorized`、`forbidden`、`unavailable`、`internal-error`），另有 `not-found`、
  `conflict`、`gone`、`precondition-failed`、`unprocessable`、`precondition-required`。**401、403、404、500、503 不带 `detail`**：拒绝不泄露文档、变更或 DENY 是否存在，
  被拒绝的步骤为何被拒绝记在 INFO 日志里。400、409、410、412、422、428 只解释调用者自己的请求：400 的 `detail` 只带控制面自己的请求校验消息，或点名解析失败的字段，
  从不带异常消息或类名；解析失败的时间（含超出毫秒范围的）是 400。路径、查询或请求体里有不成对 UTF-16 代理项的字符串，在任何路由读它之前就是 400（RC1-52，`IDN-10`）。
  存下的文档或记录解码失败（含分析读不懂的存储形式）是不带 detail 的 500，按 key 记 ERROR。控制存储答不上来时（`ControlStoreException`），每条控制路由对有权调用的人
  回答不带细节的 503，绝不读成空答案（`CTL-52`）。
- **冲突的类型**（`CTL-80`）：每个 409 在 problem 体里用 `conflict` 写明是哪一种：`BASE_MOVED`、`SLOT_HELD`、`STATE`、`CANDIDATE_MOVED`、`WINDOW_OPEN`、`WINDOW_BLOCKED`、
  `CONTENDED`、`EXISTS`（`contract/control/conflict.json`、`vocabularies.json`）；别的状态不带这个成员，没有不带它的 409。`SLOT_HELD` 另带 `heldBy`（占位变更的 id），只在 `detail`
  本来就写出它的地方。`detail` 是给人看的，不是契约。
- **可见性**：以变更 id 为参数的每一步，调用者看不到的变更与不存在的变更答得完全一样（404，`CTL-15`，§9.2）；`POST /changes` 带 `kind` 字段为 400（种类由入口决定，`BRK-5`）。
  存下的变更记录读不出来是 500（上一条），不再有单独的 `409 change-unreadable`（#1286）。
- **列表**（`CTL-55`、`CTL-68`）：`GET /changes` 只显示按 id 读也会显示给调用方的变更，先滤掉调用方看不到的再切页，对滤掉的部分什么都不透露，只有一处例外写明在案：游标里带着它所指变更的 id，调用方能借此数出各状态的变更数（DR1-E-8，不透明的游标留到 8.1）。按状态列变更先判定、后读取：
  租户的主体只扫自己的租户，平台的主体只扫它在其上有 `cosec:read` 的层，其余 403 且什么也不扫；每个请求至多读四页，被上限截断的扫描答它找到的，并给出停下位置的游标，
  那个位置可以是调用方看不到的条目。`GET /documents?kind=` 从存储的索引列出有哪些租户或应用文档，绝不读文档：在该层上有 `cosec:read`（`doc/tenant`、`doc/app`）的调用方
  得到该层的全部，租户的主体只得到自己租户的那一个，其余 403；不对列出的每个文档各做一次判定。游标是客户端原样传回的令牌（`contract/control/cursor.json`），解不出或
  属于别的列表的令牌是 400，绝不从头列起。
- **路由的形状**：控制路由只服务确切的路径：末尾的 `/`、空段、叶子路由之后多出的段都答 404，所以按精确路径写的限流规则成立（`rate-limiting.md` 的控制 API 一节）。没有放行主体的
  请求在读请求体之前答 401。控制路由至多读取文档上限加 2 MB 的请求体（`ControlDerived.MAX_BODY_BYTES`，默认 10 MB；不是属性），WebMvc 与 WebFlux 一致，更大的在问控制面之前答 400
  （`CTL-41`）。这个上限只有带文档的四条路由读到：提议、`:apply` 与它们的校验；其他路由至多读取 64 KB
  （`ControlDerived.SMALL_BODY_BYTES`，Spring Boot 服务器默认请求头大小 8 KB 的八倍：最大的这类请求体是一个模拟请求），
  更大的在解析之前答 400，所以还没有人授权过的请求只花它自己的大小（审查发现 DR1-F-3）。
- **应答模型**（`CTL-61`，R2C-11、R2C-13）：控制 API 从自己的响应模型应答。变更的应答只含编码器逐个写出的成员，绝不是存储记录的拷贝：记录里为存储自己的工作保留的东西
  （检查时用过的头、报告过窗口的实例、记录的格式、批准人持有的东西）不出现在任何应答里，记录新增的成员在写进编码器之前到不了客户端。`simulate`、`explain` 与轨迹里的封闭取值
  （`decision`、`cause`、`reason`、`effect`、`outcome`）各出自一张穷举的表，不取类名；被拒绝的作用域的 `APP_MISMATCH`、`SPACE_NOT_MEMBER` 在 `reason` 下。成员、取值以及每条路由
  写哪种审计事件，钉在 `contract/control/`（`:control:updateClientContract`）。
- **来源**（`CTL-57`、`CTL-70`）：变更记下作者是怎样被识别的，每个变更事件记下该步操作者是怎样被识别的（`origin`）：`asserted` 表示宿主相信了调用方声明的身份（`CoSec-Identity`，
  `STA-9`）而不是自己验证凭据；`via` 是凭据的方法与 id（绝不是值）和请求 id；`peer` 是请求到达的连接的对端地址，从 Reactor Netty 的通道读，在任何转发头处理之下，调用方
  声明不了它；读不到的宿主不记。没有请求驱动的步骤（维护周期）不记。变更的应答对每个读者说出 `asserted` 与 `via.method`；凭据 id、请求 id 与 `peer` 只给在该变更的文档上
  有 `cosec:approve`、或能读平台文档的读者。
- **服务配置与服务端口**（`CTL-58`、`CTL-71`）：直接调用控制面的服务只能用一个窄的集合（服务配置）：租户与应用文档的读、租户文档的 `:apply`，以及租户与应用文档上不需要人的
  变更流程（提出与校验、读、列表、rebase、放弃、开始或跳过影子窗口、发布）；平台文档以及以后新增的任何一种文档都在其外。服务配置在自己的端口上提供
  （`cosec.control.http.service-port`，仅 WebFlux；谁能用它由网络说了算）；其余路由在控制面被问到之前就是 404：平台文档、批准与拒绝、回滚、break-glass、查询与 propagation。
  集合只收窄提供什么，绝不放宽调用方能做什么：每条路由仍按所声明的主体由策略授权，经服务配置没有信任根（`CTL-81`，§7.3）。服务端口不是另一台服务器：它由一个新的服务器工厂
  建成，Spring Boot 的定制器像配置应用服务器那样配置它（TLS 与客户端认证、绑定地址、HTTP/2、各种上限与超时），自己没有属性；靠应用端口的双向 TLS 使
  `only-trusted-callers-can-reach` 成立的宿主，服务端口同样是双向 TLS。
- **CoSec 自己的路由只在该在的端口上应答**（`CTL-69`）：控制 API 与登录路由只在应用端口（从服务器读出实际绑定的端口，不只看属性）上应答，控制 API 另加服务端口；宿主的其他端口，
  包括管理端口，对这些路径一律 404。WebFlux 的管理服务器是子上下文，会收集应用的路由；在相信声明身份的宿主上，那等于把整个控制 API 交给任何能到达管理端口的人。
- **门面**（`CTL-65`、`CTL-77`、`STA-11`）：应用经 `cosec-control-sdk` 的 `ControlService` 调用控制面（`ControlCaller`、`ControlRefusedException` 也在那里，包名
  `me.ahoo.cosec.control.sdk`；它不依赖 runtime 与控制面）。两种实现答得一样：进程内的 `LocalControlService`（`cosec-control`）与经控制面宿主服务端口的 `HttpControlService`
  （`cosec-control-http`）。两者把服务配置的每个调用做成同一个请求（一张路由表，`RoutedControlService`），各用一套映射声明调用方：请求的主体按网关转发身份的方式写
  （`IdentityIssuer`），应用自己的主体写成同一个服务身份（`ServiceIdentity`，凭据名 `service`，§7.3）。转述带上调用方完整的成员关系（`IDN-39`，RFC 0006 §7.3；被转述的身份没有写成员关系时不写，进程内的门面对这样的调用方同样答 400，`IDN-42`），转述的头不超过 CoSec 写方的上限 6 KiB（`IDN-43`），所以附加到调用方的 DENY、或读它在另一个空间里的角色的 DENY，经两种实现判定一致。经门面的每次调用都由管线按 `ControlCaller` 所声明的主体、按策略判定，
  并按该主体记录，走路由自己的代码路径，没有绕过它的路；门面恰好到达服务配置提供的路由，两者共用一个定义；进程内的调用记为 `via.method: in-process`。`ControlCaller.of`
  接受任何 `SecurityContext`，不是 CoSec 的 gate 或管线所造的上下文在调用时被拒绝，在控制面被问到之前，两种实现用同样的异常与措辞（同 `PIP-29`）；HTTP 实现另外拒绝没有凭据的
  请求主体，而不是把它当匿名发出。已结束请求的调用方不被陈述：`IdentityIssuer` 只为进行中的请求签发身份，`HttpControlService` 因此在发送任何东西之前以 403（不带细节）拒绝这次调用，
  与进程内实现对已结束请求的拒绝一致（`PIP-26`）；宿主看不到它，所以应用侧记一条限频的 WARN，点名主体、租户与调用，不含令牌（DR1-F-2）。请求结束之后还要调用控制面的工作以应用自己的主体调用。
  同一套调用脚本、两种调用方，在两种实现里对控制面的每个应答与拒绝都答得一样（`ControlServiceParityTest`）。经 HTTP 时只有 2xx 是应答；HTTP 实现不跟随重定向，并在构造时拒绝会跟随的客户端（跟随会把不带签名的 `CoSec-Identity` 送到重定向指向的地方）；
  应答至多读“控制路由读的最大请求体的两倍”（20 MB），超过即失败（DR1-F-17）。`ControlCaller.service` 所声明的主体与角色按 `CoSec-Identity` 的规则检查，进程内与经网络一致（DR1-F-18）。
 
  一次调用至多等它的超时（默认 30 秒），之后以 `HttpTimeoutException` 失败，写操作的结果未知；其余传输失败原样抛出，这是唯一的差别。starter 只装配一个 `ControlService`：本实例
  跑控制面时是进程内的，`cosec.control.service-url` 指明宿主时是 HTTP 的，两者同时出现则拒绝启动。
- **类型化层**（`CTL-76`）：`ControlClient` 在 `ControlService` 之上把服务配置写成类型化的请求与应答，只写一份，两种实现共用。类型跟随线上格式并由测试钉住（`TypedWireTest`）：
  每种条目的成员是 `schema/<line>/` 的；变更应答的成员是 `contract/control/change.json` 的，每个成员要么被读、要么被点名为不读；封闭集合等于词汇表与 schema 的枚举。读文档条目
  是严格的：有本版本不认识的成员就拒绝，因为读了再写回会丢掉它，而文档是判定的输入；读应答是宽松的：未知成员忽略，未知取值保留原文。便捷调用"提出、跳过影子窗口、发布"
  需要 `cosec:skip-shadow`；基线移动则重读重做，暂存槽被占则等待，都在一个等待期之内；同一主体的并发写入互相等待，死掉的写入方留下的变更占一个等待期，之后由下一次写入接管；但只接管没有审批、也没有影子窗口的变更：带着其中任何一样的，是人或真实流量给出的证据，从不为腾出暂存槽而放弃（DR1-F-15）。
  类型化的读取只认 `schema: 2` 的文档（DR1-F-16）。
- **只校验、不提出**（`CTL-78`）：`POST /changes:check` 与 `POST /documents/{key}:check` 取 `POST /changes` 与 `:apply` 的请求体，走提出的同一个函数直到最后一步之前：授权、基线、
  草稿、候选的各项检查及其 findings 与 escalations 都照做，但不存储、不占暂存槽、不写变更事件、不取变更 id。应答是 `state`、`base`、`findings`、`escalations`
  （`contract/control/change-check.json`），不含 `candidate`：候选里可能写入变更的 id，校验答不出与正式提出相同的值。不能提出的调用方也不能校验。它只是建议：基线之后仍可能移动。
- **控制请求没有自己的期限**（`CTL-82`）：期限是调用方的，经取消到达。宿主上共享的存储读取（文档列表、实例状态）同一时刻只有一次在途加载，这期间到达的调用都等它，成功或失败一并交给它们：
  一个调用至多等一次加载，不随排在前面的调用数增长（DR1-F-10）。进程内由调用方的协程执行请求，调用方用 `withTimeout` 限定。经网络时，`HttpControlService` 在调用方被取消或
  调用超时时中止交换（对 `sendAsync` 返回的 future 调 `cancel(true)`：HTTP/1.1 关闭连接，HTTP/2 重置流）；WebFlux 宿主（运维端口与服务端口）在连接结束时取消处理该请求的协程。
  Servlet 宿主只在运维端口上提供控制 API，容器不告诉处理方客户端已经离开，请求在那里走完，其中每个等待各自有界（§14.2）。发布在写头之前被取消什么也不发布（§5.4）。
- **控制面宿主**（`STA-10`，维护者 2026-11-21 决定）：控制面可以嵌入管理服务，也可以作为独立的控制面宿主运行：`cosec-control-server`（`platform/control-server`）是只做这件事的应用，
  运维端口给经网关验证过凭据的人，服务端口给服务；它是应用，不发布为库。gRPC 与 CLI 写入工具不提供（`cosec-migrate` 的 `bootstrap`、`publish`、`partition plan`、`restore`、
  `repair-references` 除外）：CI 调 HTTP（Q18）。

### 10.3 `simulate`、`explain`、`analyze`

| 操作 | 做什么 | 权限 |
|---|---|---|
| `simulate(request, candidate?)` | 在当前头与（可选的）某个变更的候选上各评估一次，`TraceLevel.FULL`，返回两边的决策、trace 与差异。请求里描述主体与成员关系，所以可以模拟任意主体 | `cosec:simulate` |
| `explain(request, at?)` | `at` 为空时等于在当前头上 `simulate`；给出 `ViewVersion`（审计事件里的那个，RFC 0006 §9.2）时，从修订记录装载记录的修订、编译、评估。任一修订已被回收 → 410 | `cosec:explain` |
| `analyze(query)` | 给定动作、资源与作用域，列出在作用域内有语句匹配它的绑定，分 ALLOW 与 DENY，条件只标记不求值 | `cosec:analyze` |

- **同一个求值器**（`CTL-3`）：三者都调用执法的 `Engine.evaluate`（P3），解释由执法流程自己的部件构造（`ScopeResolver`、数据面的 `PolicyDocumentCompiler` 配平台的 `limits` 与
  `attributes`、`CoSecFlatEngine.evaluate` 的 `FULL` trace），没有第二个求值器。`simulate`、`explain` 与影子比较读执法会读的文档，按它的唯一规则（`ViewDocuments`）：平台的、租户的，
  以及作用域在该 app 有角色、或用于判定的租户文档（头、候选或被解释的修订）把该 app 的权限策略绑给 `Anyone` 或主体时，该 app 的；不多读，因为多读的文档会带进它的限流规则
  （RC1-17，`TNT-4`）。`explain` 按记录的租户修订判断；报告的版本与候选检查都取自视图实际读到的文档。被模拟、解释或分析的 `http` 资源经同一个 `PathNormalizer.normalize`，执法答 400
  的路径这里也答 400；请求把视图中某份文档读的头以不同的值重复发送时答 400（`PIP-12`）。
- **授权在决定所用的租户上**（`CTL-23`，RC1-40）：`cosec:simulate`、`cosec:explain` 在被模拟的作用域实际解析到的租户上授权，即其文档决定这个请求的租户，不在请求只是点名的租户上；
  没有主体的请求按执法在 `(0)` 上判定，所以点名其他租户的匿名请求在 `(0)` 上授权之后答 400。
- **脱敏**（`CTL-51`）：锁死检查的提示遵守同一条规则：只向能读“定义该策略的文档”的发布者点名语句或边界，否则只说哪个请求会被拒（DR1-F-13）；410 的详情不点名文档与修订。决策与 trace 只向能读"定义该策略的文档"的调用者点名语句（策略、序号、名字，以及轨迹里的效果与是否匹配），不论让它生效的绑定在哪份文档里：租户绑定了平台
  策略或某个应用的权限策略时，租户管理员既看不到做出判定的语句，也看不到轨迹里那条策略的任何语句，它们只计入"已隐去"的数目。`analyze` 只列可读文档，并统计隐藏的文档数，
  以及策略位于隐藏文档中的绑定数（不透明）。
- `simulate` 只看到调用者给出的属性：请求不带外部属性，读外部属性的语句在模拟中是 `Indeterminate`，与影子窗口相同。
- **编译缓存**（RC1-41）：编译后的文档按 key 与存储摘要缓存，每个编译形态再按平台文档的摘要区分，`simulate`、`explain` 与 `analyze` 共用：一台宿主只有一个这样的缓存（`DocumentCache`），锁死检查也用它；它的上界是文档那四分之一堆的三分之一（`STA-12`，DR1-F-5：管道的快照源、控制面自己的快照源与它各占三分之一，
  2 GiB 的堆是约 170 MB），不设条数，也没有属性。一份文档的重量是存储字节 × 4（解码）加每个编译形态 × 8，再加量出来的固定开销（每条 1,024 字节、每个形态 512 字节：多数租户文档很小，只按字节估会低估），
  角色派生的绑定另计；最久未用的先出；候选在一次调用里只编译一次。保留修订像头一样按摘要缓存；文档的重量在缓存锁之外计算（DR1-F-4）。超过上界一半的文档每次调用按需编译，不进缓存。平台文档的任何改动都产生新的编译形态（与 `SNP-4` 同义）。
- `analyze` 不列出用户：成员关系不在快照里（P11），"哪些用户有角色 editor"要问身份源（§3 M14）。7.x 的 `cosecExplain` actuator 端点已删除（N8）：它能解释任意主体，却只受
  actuator 暴露配置保护。

### 10.4 从格式描述生成 JSON schema

- **格式描述**：`cosec-document` 的 `me.ahoo.cosec.document.format`（`DocumentFormats`），一个很小的 Kotlin DSL，逐个声明文档、策略、语句、条件运算符、属性目录类型、绑定、
  角色、目录、限流规则、`provenance` 等的字段、类型、枚举、必填项，以及与编解码器一致的"不允许未知字段"。它是纯数据，不用反射。
- **生成**：`:document:generateSchemas` 把描述写成 `schema/<line>/*.schema.json`（`<line>` 是 `DocumentFormats.SCHEMA_LINE`，发布线 `8.0`；键排序、确定性输出）；`verifySchemas`
  挂在 `check` 上，提交的文件与生成结果不同即失败；`SchemaLineTest` 把发布线钉在项目版本上。站点在 `https://cosec.ahoo.me/schema/<line>/` 提供它们，这是每个文件的 `$id`；
  已发布的发布线的目录不再改写。
- **与编解码器绑定**（`SchemaConformanceTest`）：① 由描述生成的文档，schema 与编解码器都接受；② 对它们做单点变异（删必填字段、加未知字段、改类型、取值越出枚举或范围），schema
  拒绝，编解码器除列明的宽松之处外也拒绝；③ 仓库资源与文档里的全部 JSON 两边结论一致。schema 不如编译器严格：通过它是必要条件，不是充分条件。编解码器仍是手写的流式代码
  （热路径与 AOT 的理由不变，RFC 0004 Q10），描述只用于生成和测试。
- **生成哪些文件**：`cosec-snapshot-document`（三种文档）、`cosec-binding`、`cosec-catalog`、`cosec-identity`（`CoSec-Identity` 头）、`problem`、`definitions`。
- **为什么不反射模型类**（M11，Q19）：`model/` 不能有反射，也没有与 JSON 一一对应的数据类；用 KSP 或注解处理器要给每个类型加注解、加构建步骤，生成的仍然不是编解码器实际接受的
  东西。一份声明式描述加一致性测试，两者的偏差会被测试发现。

### 10.5 控制面审计

```kotlin
/** control/audit/ 的 SPI。投递语义沿用 RFC 0006 的 Delivery。 */
interface ChangeListener {
    val name: String
    val delivery: Delivery get() = Delivery.BEST_EFFORT          // 或 REQUIRED
    suspend fun onChange(event: ChangeEvent)
}
class ChangeEvent(
    val id: String, val time: Instant, val kind: Kind,
    // PROPOSED / CHECKED / SHADOW_STARTED / SHADOWED / APPROVED / REJECTED / PUBLISHING / PUBLISHED / FAILED
    // / BREAK_GLASS_REQUESTED / BREAK_GLASS_APPROVED / REVOKED / HEADS_MOVED / REVIEW_NEEDED / ABANDONED / SHADOW_SKIPPED / REBASED
    val operator: Actor, val change: ChangeId, val document: SnapshotKey,
    val base: RevisionRef?, val candidate: RevisionRef?,           // 修订号 + 摘要
    val escalations: List<Escalation>, val confirmations: List<Confirmation>, val shadow: ShadowSummary?, val note: String,
    val moved: List<MovedHead>,                                    // HEADS_MOVED、REVIEW_NEEDED（§5.4）
    val origin: ChangeOrigin?,                                     // CTL-57
)
```

- 事件从不带文档内容。`Kind` 是会增长的集合：次版本可以加成员（RFC 0010 Q6），对它的 `when` 要有 `else`。
- **设门的步骤**：`PUBLISHING` 与创建 break-glass 的两步（`BREAK_GLASS_REQUESTED`、`BREAK_GLASS_APPROVED`）等全部 `REQUIRED` 监听器写下事件才生效（§5.4 第 1 步、§8）；
  break-glass 变更的放弃也等（`BRK-10`）。其余事件按各监听器的 `delivery`。
- **改动变更记录的每一步都写事件**（`CTL-63`）：`:skip-shadow` 与免影子的 break-glass 路径写 `SHADOW_SKIPPED`，备注里带跳过的理由，不论变更最后是否发布；`:rebase` 写 `REBASED`；
  被拒绝的步骤什么也不改，什么也不写。`SHADOW_SKIPPED` 尽力投递、不设门：跳过只在发布时才有影响，而发布是设门的。写后检测发尽力投递的 `HEADS_MOVED` 或 `REVIEW_NEEDED`（§5.4）。
- **顺序**（`CTL-66`）：同一个控制面实例之内，监听器按实例写入的顺序收到一个变更的事件：每个监听器一个队列、一个消费者，等待队列空位的按到达顺序服务。设门的步骤在超时之内
  等它的 `REQUIRED` 监听器记下事件（排在之前的之后），否则失败（503）；`REQUIRED` 监听器的队列满、调用失败或不应答时，丢的是已存储步骤的事件，计数并记 ERROR，绝不让该步骤失败；
  `BEST_EFFORT` 监听器的队列满了就丢新来的，所以到达的是有序的前缀。队列合计至多占堆的三十二分之一（`HeapBudget`）；不应答的监听器只上报，不切断。一个控制请求的 `REQUIRED`
  变更监听器合计至多用 `cosec.pipeline.timeout`；停机时在 `spring.lifecycle.timeout-per-shutdown-phase` 的六分之一之内投递完队列里的（`OBS-10`，没有属性）。跨实例的顺序由消费者
  按事件的时间与变更的记录来排。
- 默认没有 `REQUIRED` 监听器：修订记录本身就是"发布了什么、谁发布、谁批准"的持久记录，普通发布不强求外部审计。break-glass 必须有（§8）。Q21。
- 实现：`LoggingChangeListener`（`BEST_EFFORT`）、`KafkaChangeListener`（`cosec-kafka`，主题 `cosec.control.audit.kafka.topic`，默认 `cosec-control-audit`，可配置为 `REQUIRED`，
  与 `KafkaAuditListener` 相同的做法）。两个 Kafka 监听器共用一个有界发送器，停机时排空已排队的发送。
- 控制面复核审批人时，吊销表读不到即 503，不发布（§7.5）。

## 11. 不变量

| 不变量 | 本阶段如何成立 | 守护 |
|---|---|---|
| **Deny-first** | 引擎只多了 `withinBoundary`，它只能把 Permit 改成 Deny 或 Indeterminate | P1′（RFC 0004）；P-B2（§12，`BDY-1`） |
| **Fail closed** | 数据面：边界出错 → `Indeterminate`；F5 不变（§6.3）。控制面：任何检查失败、UNKNOWN 未获批准、存储或 `REQUIRED` 审计失败 → 不发布，头不变；授权中的 `Indeterminate` → 拒绝 | `ControlFailClosedTest`（逐阶段注入失败，断言头不变）；引擎的 `BoundaryTest` |
| **One decision path** | 数据面的 `StatusMapping` 不变；控制面 API 有自己的状态表（§10.2），不构造 `Outcome` | `OneDecisionPathTest`、`WebAdapterParityTest` |
| **No blocking on the event loop** | 控制面不在请求路径上；`ControlStore` 用 CoCache 的异步与挂起 API。数据面的候选加载在 `SnapshotSource` 的维护线程上 | `PipelineBlockHoundTest`；`ControlBoundaryTest`（不引用 Redis 客户端、`runBlocking`、`Dispatchers.IO`） |
| **Authorization is a pure decision** | `withinBoundary` 是引擎内的纯函数 | `EnginePurityTest` |
| **快照与控制面的缓存永不过期、读失败抛出** | 快照文档的缓存不变；控制面的缓存除影子报告与实例状态外同样是"记录"（§5.2） | `CacheTtlPolicyTest`、`StrictCacheFailureTest` |
| **Hot-path changes come with a JMH before/after** | §14 | `EngineAuthorizationBenchmark` 的 `boundary` 参数 |
| （新）**快照只有控制面写** | 7.x 的写入路径已删除；不运行控制面的进程把快照与候选声明为只读，Redis 拒绝它的写入（§8） | `ReadOnlyDeclarationTest`（`SNP-18`） |
| （新）**发布的文档都能编译** | 控制面严格编译（§6.3） | `PublishCompileTest`：含任何 `Broken` 条目的候选不会被写入 |
| （新）**不能越权授权** | §7.4 | A5–A8（`GrantPropertyTest`）；`GrantAnalyzerTest` 的正例与反例（§7.4.6 的每一行）；`GRT-*` 场景 |
| （新）**控制面的租户隔离** | 硬性规则（§7.2）与编译检查（§9.2） | `ControlTenantIsolationTest`；P12 的控制面形式 |
| （新）**修订可追溯** | 记录先于头写入；头带 `parent` | `RevisionChainTest`（逐步注入崩溃，断言链可以重建、头总有记录） |
| （新）**break-glass 双人且有期限** | §8 | `BreakGlassControlTest`；`BRK-*` 场景 |
| （新）**观察不改变决策**（RFC 0006） | 影子候选来源的任何故障只影响影子 | `ListenerIsolationTest` |

`AGENTS.md` 的 Mental model 写了控制面一层，Invariants 表与 "Where a change has to land" 带着控制面的各行。

## 12. 门槛 D：本阶段不改变数据面的决策

门槛 D 原定以离线回放证明本阶段与第 5 阶段在同一批数据上零差异；8.0 不考虑与 7.x 的兼容（RFC 0008），回放与"与第 5 阶段零差异"取消，
由 [RFC 0008](0008-conformance-and-direct-build.md) 的规范一致性套件取代。本阶段的性质作为规范性质保留。

### 12.1 要证明什么

本阶段对数据面的改动只有平台边界与控制面需要的格式；在没有边界数据的文档上，数据面的决策与没有这些改动时相同。

### 12.2 为什么应当恒等

| # | 改动 | 在没有边界数据的文档上 |
|---|---|---|
| E1 | `withinBoundary` | `view.boundary == null`，函数第一行返回 `p`；引擎整段跳过检查（`SnapshotView.bounded`） |
| E2 | 文档格式：`provenance`、`limits`、`attributes`、`boundary`（N3、N4） | 编译结果与 `provenance` 无关（§5.3）；`limits` 缺省时等于 RFC 0005 Q9 的默认值，`attributes` 缺省时等于本实例注册的提供者声明的 |
| E3 | 编译规则：`Tenant → App` 引用（N1）、两层同名（N2）、`nomatch` 需要确认（N6） | N1 只让以前的编译错误变为合法；N2 只在两层同名时起作用；没有外部属性的文档也就没有 `nomatch` |
| E4 | 影子候选来源 | 只影响影子监听器；"观察不改变决策"（RFC 0006 §10.2） |

### 12.3 性质与守护

| 性质 | 内容 | 守护 |
|---|---|---|
| P-B1 边界恒等 | 随机快照与请求：边界为"一条 ALLOW `*`"时，决策与没有边界完全相同 | `EnginePropertyTest`，`BDY-1` 的场景 |
| P-B2 边界只收窄 | 随机快照与请求：加上任意边界，结果不会从 Deny / Indeterminate 变成 Permit | `EnginePropertyTest`，`BDY-1` |
| P-B3 边界与候选顺序无关 | P8（RFC 0004）加上边界仍成立 | `EnginePropertyTest`，`BDY-1` |
| 发布往返 | 对一份文档 D，经控制面 `apply`（`REPLACE`，空存储）发布得到 D′；D 与 D′ 编译出**结构相同**的快照（RFC 0003 P5 的结构比较），并在随机请求上决策相同 | **没有专门的测试**：这是目标，不是守护。`cosec-migrate` 的写入经控制面的存储有测试，往返本身没有 |

三条 P-B 性质随 `check` 以固定的例数运行；`propertyStress` 以更多的例数运行它们（`-PpropertyIterations`，百万例只在 CI 上跑），RFC 0008 §3.6。

## 13. AOT 与 JDK

| 约束 | 本阶段的做法 |
|---|---|
| `model/`、`engine/` 不用反射 | `withinBoundary`、模式包含都是普通函数；`EnginePurityTest` 守护 |
| `control/` 不用反射 | 普通类、sealed 接口和挂起函数；SPI 实现以 Spring bean 注入，没有 `ServiceLoader` 或类路径扫描 |

| schema 生成 | 构建期任务，不进运行时类路径 |
| 缺少提示必须导致失败和拒绝 | 控制面：请求体解码失败 → 400，不发布；数据面：不变（RFC 0006 §12） |
| JDK | 项目的基线是 Java 21，没有用到更新的 API |
| JDK 25 AOT cache | 宿主的部署问题，不在本文；`cosec-gateway-server` 不嵌入控制面 |

## 14. 性能与延迟预算

### 14.1 数据面（硬性要求）

| 基准 | 比较 | 目标 |
|---|---|---|
| `EngineAuthorizationBenchmark` 的参数 `boundary` ∈ {`none`, `1`, `8`}（边界语句数） | `none` 与同一构建中去掉边界检查的对照实现比较（RFC 0008 §3.8）；整体吞吐按 7.0 的绝对预算判定 | `none`：吞吐不低于 100 %（交替三轮的平均，任一轮不低于 97 %），B/op 不高于；`1`、`8` 只记录 |
| 影子候选评估 | `sample-rate` ∈ {0.01, 1.0}，有一个候选 | 只记录 BEST_EFFORT 队列的每请求开销与 CPU；它不在请求延迟里（RFC 0006 §9.3） |
| 内存 | 候选来源的 LRU（1,024 份，§6.4） | 只记录 |

- **测得的**（#1075，Q24）：CI 的 JMH A/B（[run 40477072342](https://github.com/Ahoo-Wang/CoSec/actions/runs/40477072342)，三轮，JDK 25，同一作业内交替跑基准与候选），`boundary = none`
  相对 `main`：`global` 100.9 %、`none` 101.0 %、`role` 99.2 %（最低 98.4 %）、`role-heavy` 100.5 %，B/op 没有增加。维护者接受：没有边界适用时引擎跳过整段检查
  （`SnapshotView.bounded`），`role` 低于 100 % 线但在共享机器的误差内。有边界时的代价（`global`：1 条语句 97.2 %，8 条语句 83.4 %）和原始 JSON 在 `docs/perf/rfc-0007-boundary/`。
- 测量方法沿用 RFC 0002 §7.2：JDK 25、`-PjmhWarmupIterations=5 -PjmhIterations=10 -PjmhFork=3 -PjmhProfilers=gc`、空闲机器、交替三轮；日常对比用 `jmh-ab.yml`。

### 14.2 控制面（预算）

控制面不在请求路径上，预算的目的是让 CI 与人工操作的体验可预期。数字是 p99，文档 1 MB / 8 MB（RFC 0003 Q14 的上限）：

| 步骤 | 预算 | 依据 |
|---|---|---|
| 授权（每个目标一次 `check`，含一次条件读） | ≤ 5 ms | 引擎微秒级；条件读是几十字节的往返 |
| 校验 + 编译（候选与组合） | ≤ 300 ms / ≤ 1 s | RFC 0003 Q14：编译 p99 ≤ 200 ms |
| 授出分析 | ≤ 100 ms（≤ 1,000 个片段 × ≤ 1,000 条授权者语句） | `implies` 在 ≤ 64 个节点上是多项式时间；比较预算见 §7.4.3（`CTL-49`） |
| 写入（记录 + 头 + 索引） | ≤ 50 ms / ≤ 300 ms | 两次整份文档的写入 |
| `publish` 端到端（不含影子窗口与审批） | ≤ 1 s / ≤ 3 s | 上面几项之和 |
| 传播到数据面 | 通知送达时毫秒级；最迟 RFC 0003 §4.5 的落后上界（默认约 10 秒） | RFC 0003 |
| `history`、`read` | ≤ 100 ms | 一次索引读 + 按需读记录 |

- **测得的**：`ControlPlaneBenchmark`（`control/` 的 `jmh` 源码集）与 `ControlPlaneLatencyTest`（真实 Redis，`cosec-cocache`）在 #1091 时都在预算内：内存、13 KB 租户文档 `propose`
  p99 0.63 ms、`publish` 端到端 p99 40.6 ms；内存、0.95 MB 为 41.3 ms 与 104.6 ms；Redis、0.95 MB 为 125 ms 与 313 ms（`git show 67c1955c0:docs/perf/rfc-0007-control/README.md`）。
  Redis 测试断言 p99 低于 3 s（8 MB 的预算），以免拥挤的 CI 主机误报；8 MB 的文档没有测。检查一个变更随文档大小的代价（到 10 万条目）在
  [架构页](../../wiki/architecture/overview.md#what-checking-a-change-costs)：越权分析原先随文档大小按平方增长，10 万条目的变更超过一分钟并耗尽 512 MB 的堆，#1722 把它改成线性
  （44.7 秒 → 4.7 秒）。授出分析不读全部文档：每次租户分析读 app 列表与各 app 的头（§7.4.3）。
- **工作内存的预算**（`CTL-85`，DR1-F-3、DR1-F-4）：控制调用为自己解析、解码或编译、且没有缓存保留的工作内存，限定在堆的八分之一之内（`HeapBudget` 留下那一半的四分之一；它不是 `HeapBudget` 的份额：
  界住的是处理中的工作，不是为性能而持有的内存）。每块在开始前按已知的大小称重：携带文档的请求体按字节乘以实测的树因子（64）加候选的八倍，在解析之前一次取走；缓存不收的文档按存储大小乘以十二。
  一次调用合计至多算整个预算：已经占满的调用再取不计（它此刻就是独占），所以最重的调用总能独自跑完。放不下的调用按租户轮转、租户内先进先出地等待，后来的不越过等待者，
  另有租户在等时一个租户至多占一半（它什么都没持有时除外）；至多等管道超时的一半（`StageBudgets.workWait`），否则在读取或决定任何东西之前以 503 和 `Retry-After` 拒绝；已经持有预算的调用从不等待。
  路径里点名文档的路由先做租户隔离（403），再持预算、读请求体。一台宿主只有一个预算，由控制面对象携带，运维端口的 API、服务配置的 API 与进程内门面都从它那里取。没有属性；启动时说出算出的值。
  一次调用为自己解码的文档记在**调用方**的租户名下，不论读的是哪个文档：租户对平台或应用文档修订的 `explain` 在它自己的轮次里等待，不占平台运维的（第二轮 DR2-F-2）。
  读一份文档的未结束变更时逐条读，每条只留下要用的，从不同时全部解码（DR2-E-4）：每条在解码之前按它存储的字节数乘四记进调用的预算，调用只持有迄今最重的那一条，不累加；
  不超过免计额度的记录什么都不占；在解码之前给不出大小的存储（`ControlStore.eachOpenChange` 的默认实现）每条按变更记录上限计。正在读的那一条的原始字节有一瞬间未被称重，每个调用至多一条。
- **预算不是期限**（`CTL-82`，维护者 2026-11-23）：8.0 不为控制请求设期限属性（§10.2）。每个等待各自有界：鉴权与 `REQUIRED` 变更监听器的合计各由 `cosec.pipeline.timeout`；
  确认检查所用文档由快照源的存储读超时（30 秒）；写后检测 1 秒（§5.4）；每个比较并设置的循环由尝试次数（16；授权批次 4）；Redis 控制存储的每条命令由 CoCache 的命令超时
  （`cocache.redis.command-timeout`，默认 2 秒；CoSec 不设置也不锁定它，这是部署的选择），连接断开时立即拒绝。没有哪个等待要等别的请求释放：被占的槽答 409，被占的租约是跳过
  这一遍，进程内的锁至多为一次有界的读持有。一条请求最长能跑多久是这些有界步骤之和，只有调用方能说它愿意等多久。
- **运维要求**：影子报告、实例状态与驻留集合只由数据面实例写（§6.4 的键），能写的人能伪造报告；控制面汇总时按实例分键读，所以一个实例改写不了别的实例的报告。数据面的凭据对
  快照文档与候选文档只读（`SNP-18`），对 `control:*` 没有权限；`wiki/operations/storage.md` 给出 ACL。

## 17. 决定

以下各项已于 **2026-10-26** 由维护者确认，全部按本文的推荐决定（含 Q25 的 SPI 变更）。此后的决定写在它们所改的章节里，带日期与决定人；下表"决定"一栏写的是现状，
与 2026-10-26 不同之处在"理由"一栏之后注明。

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| Q1 | **影子窗口强制还是可选**（§3 M1、§6.4） | 默认强制；`cosec:skip-shadow` 可以跳过并记录原因；break-glass 的创建与撤销免除；样本不足时最长 24 小时后关闭并要求确认。默认最短 15 分钟、1,000 条样本 | 授出分析挡不住"有资格但写错了"；紧急情况需要一条有记录的快速通道；低流量文档不能永远卡住 |
| Q2 | **编译失败与旧版本**（§3 M2、§6.3） | 控制面严格编译，失败即不发布（头不变）；数据面 F5 不变，失败即拒绝 | 发布前编译之后，数据面的失败只来自版本或配置不一致，那时退回旧版本同样会忽略已发布的 DENY |
| Q3 | **修订的单位与历史**（§3 M3、§5.3） | 按文档；记录按摘要寻址、先于头写入、头带 `parent`；按策略的历史是差异视图；7.x 的历史不转换 | 发布的单位就是文档；按版本解释需要整份文档；先写记录才不会丢内容 |
| Q4 | **权威存储**（§3 M10） | 已发布的快照文档就是头，是唯一的权威；修订、变更、索引都是可以重建或丢弃的辅助数据 | 两份权威数据就要同步；不变量只需覆盖一个缓存 |
| Q5 | **并发**（§5.5） | `putIfMatch(expected = 基准摘要)`；冲突不自动重做，`rebase` 后重做全部检查；每份文档一个暂存槽；只含收窄操作且有 `cosec:skip-shadow` 的变更可以抢占 | 检查结果绑定基准；两个都通过影子的变更依次发布会让第二个的影子失真；紧急封禁不能排队 |
| Q6 | **保留**（§3 M13、§5.7） | 最近 50 个**且**不少于 7 天；孤儿满一个回收周期；不提供归档 SPI | 按体积删除会让最近的决策不可解释；归档等有需求再加。体积告警（256 MB）没有实现（§5.7） |
| Q7 | **控制面怎样授权自己**（§3 M9、§7.2） | 宿主 Pipeline 认证并做路径级授权；控制面内对每个目标调用 `AuthorizationChecker`，检查前对文档做条件读；另加不经策略的租户隔离硬性规则；三条内置控制面策略 | 路径表达不了请求体里的目标；控制面不接受数据面那样的有界陈旧；硬性规则是策略写错时的最后一道线 |
| Q8 | **包含的语义与算法**（§3 M4、M5、§7.4） | §7.4.2 的定义；单条 H 包含；先把授权者自身属性代换为常量；含 `ext.*` 的授权者条件视为不可比较；不计入经 `Anyone` 绑定的 DENY。备选：计入全部 DENY（严格按定义，误报多） | 可判定、可靠；`Anyone` DENY 对被授权者同样生效，计入它会拦住最常见的平台规则形态 |
| Q9 | **删除或放宽 DENY**（§3 M6、§7.4.4） | 租户文档在有写权限的范围内允许，没有受保护的条目（`CTL-87`）；平台与 App 文档要第二个人（`CTL-31`）；收窄一律允许。备选：按 §7.1 字面，删除 DENY 一律审批 | 租户放宽后仍受平台层的 DENY 与边界约束；撤销访问不应比授予更难。`protected` 标志留到 8.1（§7.4.4） |
| Q10 | **审批**（§7.5） | 有 `cosec:approve` 的另一个人批准；批准绑定候选摘要，72 小时有效；信任根自己的变更默认不需要第二人（`four-eyes` 可开启）；break-glass 总是双人；工作负载的凭据从不批准 | 平台管理员是信任根，强制双人会让平台日常运维依赖两个人在线；break-glass 是例外 |
| Q11 | **平台边界**（§3 M8、§7.6） | `Platform` 放默认边界，`Tenant(T).boundary`（只有平台能写）覆盖；约束租户主体的全部 Permit；只含 ALLOW、只在 `Platform`；平台租户没有边界 | 平台文档不随租户数增长；边界是平台给租户的总包络，平台层自己的授出也应在其中 |
| Q12 | **break-glass**（§3 M7、§8） | 主体只能是平台租户的主体；双人；期限上限默认 4 小时、最多 24 小时；免影子；发布前必须有 `REQUIRED` 的控制面审计；`cosec-migrate` 不写 break-glass 绑定 | "只能由控制面创建"靠唯一写入者与 ACL 实现；长期 root 正是 break-glass 要取代的。2026-10-30 起不再由编译器检查元数据（RC1-27，§8） |
| Q13 | **DENY 上的 `nomatch`**（§3.1 N6、§9.5） | 按语句确认（带语句摘要），确认写进语句，编译器在任何文档里要求它 | 风险在于"依赖故障时 DENY 失效"，而不在于谁写；显式、可审计的确认才是 RFC 0001 §3.3 要的 |
| Q14 | **租户引用应用目录**（§3.1 N1、§9.3） | 允许 `Tenant(T)` 的绑定指向 `App(a)` 的权限策略，作用域必须是 `app = a`；反向索引保护 | 没有它租户自助只能复制语句；悬空引用已有失败即拒绝与控制面检查 |
| Q15 | **跨层同名**（§3.1 N2、§9.4） | 控制面拒绝租户使用平台已有的 id，平台策略的精确副本除外（2026-11-07，#1224）；数据面两层同名时内容相同则解析，否则 `Indeterminate(AmbiguousPolicy)`；分区按 §9.4 的四步 | 租户层优先会让租户使平台 DENY 失效；平台层优先则无法分区；"内容相同"给迁移留出安全的过渡 |
| Q16 | **必须一致的配置**（§3.1 N3） | 外部属性目录与成本上限写进 `Platform` 文档；删除 `cosec.policy.limits.*`；实例在安装 `Platform` 时检查提供者覆盖 | 控制面与数据面必须用同一份依据编译，否则"控制面接受、数据面拒绝"成为常态 |
| Q17 | **本地策略与本地影子文件**（§3.1 N9、§6.7） | 删除 `init-repository`/`force-refresh` 与本地影子文件；本地策略文件只装进内存存储；提供声明式 `apply` | 每实例启动时写库是一条不经授权、不留修订的写入路径 |
| Q18 | **API 形态**（§10） | 库 + 宿主上的 HTTP 路由 + 门面 `ControlService`；不提供 gRPC 或写入用的 CLI。2026-11-21 起另有控制面宿主镜像 `cosec-control-server`（§10.2） | RFC 0001 §4 的"可以嵌入管理服务的库"；最小的表面就是一个挂起接口加它的 HTTP 映射 |
| Q19 | **schema 生成**（§3 M11、§10.4） | `cosec-document` 中的声明式格式描述 → `generateSchemas`；`verifySchemas` 进 `check`；一致性测试绑定描述与编解码器 | 模型类不能反射，也不等于 JSON 形状；描述 + 测试让偏差可见 |
| Q20 | **"不依赖 Reactor"的最终形式**（§3 M12） | 公开签名规则 + `model/`、`engine/`、`runtime/`、`control/` 不引用 `reactor.*`；不做类路径检查 | Lettuce 依赖 `reactor-core`，类路径检查永远无法通过；签名规则守住的是下游真正受影响的东西 |
| Q21 | **控制面审计**（§10.5） | `ChangeListener`，投递语义沿用 RFC 0006；`PUBLISHING` 与 break-glass 事件先于头写入投递给 `REQUIRED` 监听器；默认没有 `REQUIRED`，break-glass 必须有 | 修订记录本身是持久的发布记录；break-glass 与 RFC 0006 Q20 对使用的要求对称 |
| Q22 | **`simulate`/`explain`/`analyze`**（§3 M14、§10.3） | 三者都调用同一个 `Engine.evaluate`；`explain` 可以指定 `ViewVersion`；`analyze` 以绑定的主体表达；删除 `cosecExplain` 端点 | P3；RFC 0001 §3.3 要求按版本解释；P11 之后无法列出用户；actuator 端点没有按租户的授权 |
| Q23 | **门槛 D 的标准**（§12） | 由 RFC 0008 的规范一致性套件取代（2026-10-26）；P-B1–P-B3 与发布往返作为规范性质保留 | 8.0 不考虑与 7.x 的兼容 |
| Q24 | **性能**（§14） | 数据面：`boundary = none` 吞吐不低于对照的 100 %，B/op 不高于；整体按 RFC 0008 §3.8 的绝对预算；控制面：§14.2 的预算，超出须在 PR 中说明 | 没有边界时不应有任何代价；控制面不在请求路径上，预算是体验目标而不是门槛 |
| Q25 | **SPI 与 API 变更**（AGENTS.md 要求先问） | 新增 SPI `ControlStore`、`ChangeListener`、`ShadowReportSink`；删除 `SnapshotPublisher`、`ShadowPolicyProvider`、`PolicyRevisionStore`；`cosec-api` 不变 | 8.0 没有发布过，删除的接口没有外部使用者；写入只剩一条路径 |
| Q26 | **自举**（§3 M15、§5.9） | `cosec-migrate bootstrap`，只在没有平台管理员绑定时执行，`--force` 用于恢复；写修订记录 | 存储为空时没有人有权写；拿到 Redis 凭据的人本来就能写，命令只让这类写入留下记录 |
| Q27 | **复制与确认**（§5.4） | 不加 `WAIT`；修订链让丢写可诊断；`storage.md` 建议 `min-replicas-to-write` | RFC 0003 §4.6 的理由不变；控制面没有让 `WAIT` 变得更有效 |
| Q28 | **文档格式与升级顺序**（§3.1 N4） | `schema: 2`；先升级数据面，再让控制面发布新格式 | 现有编译器拒绝未知字段；顺序错误会让实例失败即拒绝，告警指出原因 |
| Q29 | **传播的可见性**（§6.5） | 实例在影子报告的周期里写已安装的修订，控制面提供只读的 `propagation`；发布不等待它 | 运维需要知道"新策略生效了没有"；等待所有实例会让一个失联实例卡住发布 |
