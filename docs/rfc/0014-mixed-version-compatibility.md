# RFC 0014：混跑兼容性——滚动升级、回滚与长期混跑

> 状态：**方向已定**（维护者 2026-11-24：“有一段答 400 的窗口是不能被接受的”“先对抗性审查，设计方案”，对“新限制等读方全部升级才启用、只保证相邻次版本”答“按这个方向”）；

> 相关：[RFC 0010](0010-ga-extension-points.md) C5（发布门控，本文的 R5 把它的“活着的实例”换成读方集合）、[RFC 0009](0009-identity-and-credentials.md)（身份头与凭证）、

## 0. 起因

`8.0.0-beta.8` 给 `CoSec-Identity` 加了成员 `memberships`（`IDN-39`）。beta.7 的读方解码严格，不认识的成员答 `400`；beta.8 里按转发身份判定的宿主又要求这个成员。
于是 beta.7 到 beta.8 没有无窗口的滚动顺序。同一版里还有第二例：租户切换出的会话记录写成新格式，beta.7 实例读不了。

GA 发出去的读方怎么对待它不认识的东西，之后改不了；所以这些规则必须在 RC1 之前定，§5 的各项必须在 GA 之前做完。

## 1. 得不到的（先说）

新版本要引入一条**新的限制**（一个旧读方忽略了就会放宽的东西）时，下面三件只能要两件：

| 要的两件 | 放弃的一件 |
|---|---|
| 旧读方不拒绝 + 不放宽 | 新限制要等所有读方都升级后才启用 |
| 新限制立即启用 + 不放宽 | 旧读方拒绝（`400` 的窗口） |
| 新限制立即启用 + 旧读方不拒绝 | 旧读方放宽（错误放行） |

维护者的要求（没有 `400` 窗口）加上 CoSec 的根本规则（不错误放行），选的是第一行：**新限制等读方集合全部升级才启用**。
这要求写方在运行时知道读方集合；它有缺口（见 §4），缺口处只能退到第二行（拒绝），那是在“拒绝”与“错误放行”之间选拒绝。

“8.x 内任意两个版本、任意顺序”也得不到：只要有旧版本读不懂的新格式，就只能保证**相邻次版本**，回滚只回一个次版本。

## 2. 目标（改写后）

- **G1′** 两个纯版本都接纳的请求，混跑时也接纳。范围：相邻次版本；回滚一个次版本。
- **G2** 混跑不放行两个纯版本都拒绝的请求。
- **G5（新）** 混跑结束后，存储的状态不比同一段历史在纯新版本下留下的更宽（旧实例改写记录时会丢掉它不认识的成员）。
- **G3** 混跑看得见：由新的一侧看见旧的一侧，不要求旧读方做任何事。
- **G4** 不加“对端是哪个版本”的配置项。

G2 真正有风险的只有三条路：多跳（一个请求经过两个版本）、共享的读改写记录、累积状态（计数、拒绝名单、缓存）。设计按路径组织，不按 v0 的三类。

## 3. 规则

**R1 读方：忽略未知成员，除非它在“必须理解”的列表里。** 线上带一个必须理解的成员名列表（JWS `crit` 的形状）；列表里而不认识即拒绝。
整个格式的版本号（`v`、`format`）留给真正不兼容的改动，只在大版本里变。身份头、存储记录（`StoredFormat`）同一条规则。
令牌读法相同，用的是标准的机制（`IDN-47`，2026-11-25，取代原先写的“用 CoSec 自己的声明实现”）：JWS 的 `crit` 头参数（RFC 7515 §4.1.11）列出读方必须理解的头参数。校验器在签名校验通过之后读它；`crit` 列了它不理解的参数，就不读这个令牌，答 `503` `unavailable`（校验器比签发方旧，升级后同一个令牌通过，客户端不应当成会话结束）；格式不对的 `crit` 是无效令牌。8.0 不理解任何关键头参数，所以以后的 8.x 签发方要加一个限制令牌所授内容的参数时，把它标为关键，每个 8.0 的校验器都拒绝那个令牌而不是多给。校验器不认识的声明照旧忽略：限制要放进关键头参数，不放进新的声明。自己实现 `TokenVerifier` 的应用承担同样的义务（JWT 库未必替它做：`java-jwt` 不处理 `crit`）。
存储记录的必须理解列表与头同形（顶层 `crit`，从根起的点分路径，经过数组时作用于每个元素，空不写，8.0 的写方都不写）。列表里而读方不认识的项使这**一条**记录被当作更新的版本写的而拒绝：不读，因而不改写，其余记录照常（`SNP-27`）。
会话在刷新、登出、切换时答 503 并保留；控制面与影子窗口的记录被这样拒绝时，控制 API 答不带详情的 503（不是读不了的记录那样的 500），进程内的门面答得一样；记录按种类与原因计数（`cosec.stored.refused`，`OBS-12`）。
没有成员的记录（裸列表）装不下 `crit`，它的演进只有换键空间一条路（R6）。格式号在 8.x 内冻结：会话 2，其余 1（`SNP-29`）。

**R2 每个成员登记“缺失是什么意思”。** “缺失 = 更宽”的成员只能以必须理解的方式加入。转写者（`HttpControlService` 的 relay）是写方：**保留缺失**，不声称它没收到的东西。
记录还要登记“被旧读方改写丢掉会不会放宽”，与“被忽略会不会放宽”分开（记录会被改写，头不会）；两项任一为真的成员只能以必须理解的方式加入（`SNP-28`）。

**R3 判定只读封闭集合。** 开放集合（`auth.method`）只作标签；决定“人还是工作负载”的是一个封闭成员，缺失或未知按工作负载。

**R4 文档永远严格读。** 文档特性级别对“会改变旧读方判定、或使其拒绝的任何东西”加一，包括编译限额与语义。将来可能成为语法的字符今天就是编译错误，否则旧编译器会把新语法**当字面量接受**，一条 DENY 静默失效。
API key 记录同样永远严格读（`ApiKeyCodec`，`format: 3`，成员集合必须正好相等，否则 `503`）：它是认证的输入，缺了的上限绝不能读成“不受限”。
文档不带级别成员（`schema: 2`，级别只存在于实例报告的 `formatLevel`）：以后的版本要改变旧读方的判定，只能用旧读方拒绝编译的形式（它不认识的成员、保留字符），绝不给旧读方已经能编译的写法另一个意思；正因为文档严格读，8.1 可以加一个 8.0 会拒绝的顶层成员来承载级别。唯一的例外在预览版之间：beta.8 把反斜杠当普通字符，beta.9 把它当转义符，所以 beta.8 存下的 `\(` 一类写法到 beta.9 照常编译而意思不同（`MIX-11` 的用例写明；升级前由 `cosec-migrate check-patterns` 找出，升级说明给出顺序）。
所以 8.x 的写方只在**用到新成员的那把 key** 上写它：没用新东西的 key 在两个版本里是同一条记录（G1′ 成立）；用了的 key 被读不懂它的实例拒绝，属于 §4 的不支持项（全部实例升级后再签发，回滚前先停用或重签）。

**R5 读方集合。** 每个读共享存储的 CoSec 进程无条件报告自己的发布版本（今天只有开了影子的实例报告）。写方据此决定何时开始写新东西：
文档的发布门控（RFC 0010 C5，放在 `Revisions.publish`，覆盖变更、回滚、`cosec-migrate`）与记录的新写法共用这一个机制。级别未知、状态解不开的实例按最低算。

**R6 累积状态冻结。** 限流的桶名派生、键布局、脚本字段，以及一切“读不到 = 允许”的键（撤销、吊销、一次性状态）的派生，在大版本内冻结；新的计数方式走新键空间。

**R7 大小余量。** 读方至少接受 R，CoSec 的写方最多写 W < R，以后加的成员从余量里出。

**T 守卫。** 用上一个发布版的制品做三种测试：链路（旧网关 → 新服务 → 旧控制面宿主的各种组合）、改写（新写、旧改写、新再读，断言没有变宽）、累积（两版各发一半请求，断言合计不超过配额）。
只做单次编解码互读测不到这三样。每种跨版本的格式在规则登记表里有一条规则。
实现：`test/compat`（规则族 `MIX`）把上一个发布版按发布的制品装进它自己的类加载器，与当前构建同在一个测试进程里，两边只交换 JDK 的类型，共用一个 Redis；
经过真实宿主的链路是系统测试的一段（`previous=<tag>`）。只有更晚的读方才成立的用例照样运行并且必须失败（`Baseline.from`），所以把基线挪到新发布版的那个 PR 会被告知哪些用例已经成立。
beta.9 之前，需要本文读方形状的用例（`crit`）对着 beta.8 按“已知缺口”断言。

**已定的细节**（2026-11-24，身份头一批的设计评审）：必须理解的列表是顶层成员 `crit`，项是从根起的点分路径，空列表不写，8.0 的写方都不写它；
列表里合语法而读方不认识的项答 `503 unavailable`（缺口里的暂时状态：`401` 会让客户端结束会话，`400` 说的是请求错了），畸形的列表答 `400`；
身份头的读方上限 R 为 8 KiB、8.x 内只升不降，CoSec 写方的上限 W 为 6 KiB；有读方的宿主在运维没写时把 Web 服务器的请求头上限取为由 R 推出的值
（Spring Boot 的默认是全部请求头合计 8 KB，今天 8 KiB 的身份头在默认配置下到不了读方）。取舍的原则是维护者的：“规则要硬，策略要灵活。”

## 4. 写明的缺口与不支持

- 读方集合看不见：发布之后才出现的旧实例（回滚、用旧镜像扩容）、与 Redis 断开超过报告寿命（1 小时）仍在服务的实例、冷启动先读后报（首次报告已先于读文档，剩下的是启动与首次报告之间的毫秒）、没有 `cosec-cocache` 的进程（不报告，写方看不见它，也就无从把它算进任何级别；本文早先写的“按 GA 基线算”没有代码也没有规则支撑，2026-11-25 删去）。这些实例读到必须理解而不认识的东西时拒绝。
- 发布了新级别的文档之后，数据面回滚到读不懂它的版本：不支持，先回滚文档。
- 客户端（`control-sdk`、`cosec-fetcher`、Kafka 的外部消费者、自己写身份头的应用）不报告、不能门控：只靠 R1 与回答的宽松读。旧 SDK 严格读文档条目是为了“读回再写”不丢成员，保留。
- 依赖的线上格式（CoCache 的失效帧与条件写的 digest）没有读，是未决项；CoCache 包在值外面的那一层由 `MIX-22` 测着（两边各用自己的 CoCache 读写每一种记录，今天都是 8.2.0，哪天不一致当天变红）；`java-jwt` 4.6.2 不处理 JWS 的 `crit` 头（审查 C 查了它的 jar），CoSec 的校验器在签名校验之后自己读（`IDN-47`）。

## 6. 审查查出的现存问题（`main`，与本文无关也要修）

- **F1（S3）** 只有开了影子的实例写状态；将来按 C5 加发布门控时，其余实例不在“活着的实例”里，控制面会发布它们编译不了的文档，平台文档失败时整个实例拒绝服务。
- **F2（S4，混跑下 S2）** relay 把“没有 `memberships`”转写成“`memberships` 为空”，按转发身份判定的宿主因此接受一个丢了附加 DENY 的身份。同构的 `main` 部署到不了。
- **F3（S4）** 身份头写方与读方的上限相等（都是 8 KB），没有余量。
- 预览版之间已经发生、不在承诺内但说明了规则的必要：限流桶名的派生在 beta.8 变了（长键值改用散列），两版混跑时同一个客户端可拿到两倍配额；成员关系缓存从共享改为本地，混跑时旧实例会读到没人删的旧缓存。
