# CoSec 8.0 RC security review

The record of the reviews RFC 0008 §3.9 requires before an 8.0 release candidate (RC prerequisite 6, revised
2026-10-29): round 1, a threat-model review of the integrated system, and round 2, a correctness review per module.
Every finding is fixed before RC with a regression test, or deferred by the maintainer with the reason written here.

## Round 1: threat model of the integrated system

| | |
|---|---|
| Commit reviewed | `origin/main` at `76f3b43b` (`v8.0.0-alpha.1` and #1157) |
| Date | 2026-10-28 |
| Reviewers | one lead and six read-only sub-reviewers, none of them an author of the code reviewed |
| Method | per area: attackers, trust boundary, code paths, then a verdict per threat. Every finding below was checked against the code by the lead; two were also reproduced with local probe tests, which are not committed |

**Attackers considered.** An anonymous caller; an authenticated tenant user; a tenant administrator (who writes their
own tenant's documents through the control plane); a platform operator; a compromised service behind the gateway;
someone with write access to Redis.

**Severity.** Critical or High: a request is permitted that should be denied, cross-tenant access, privilege
escalation, or fail open. Medium: weakened defence in depth, or a denial of service with a cheap trigger. Low:
hardening or documentation.

**Status.** Every finding is `open` until the PR that fixes it is merged; the fix PR column is then filled in. A
finding about a rule gets a conformance scenario (`test/conformance/src/test/resources/scenarios/`); one about an
invariant also gets a mutant (`test/conformance/mutants/`), as RFC 0008 §3.7 requires.

**Findings handled privately.** Findings that also affect a supported release line (`7.x`, `release/6.1.x`) are
reported and fixed under [`SECURITY.md`](../../SECURITY.md) and are not described here. They are added to this record
once fixed and released on every affected line.

**Decisions.**

- **RC1-48:** a startup check on a gateway host (STA-1 style) refuses an exposed actuator endpoint other than health
  (the `gateway` endpoint in particular) unless the operator allows it explicitly; the failure names the property
  and links the documentation. `cosec-gateway-server` keeps exposing health only.
- **RC1-49:** identity forwarding becomes opt-in by scheme. The verified `CoSec-Identity` goes downstream by default
  only to `lb://` routes; any other route receives it only with route metadata `cosec-identity: true`; `false` still
  turns it off everywhere. A breaking change for previews, recorded in `upgrading.md`.
- **RC1-6:** an app per route, from route metadata, takes precedence over the global host app; a client-declared
  `CoSec-App-Id` applies only where neither the route nor the host names one. `HostScope`'s documentation says so.
- **RC1-5:** the gateway forwards no credential downstream by default: not the API key header (under whatever name
  `cosec.pipeline.api-key-header` gives it) and not a query token, as it already does not forward `Authorization`.
- **RC1-19:** `CoSec-Identity` stays unsigned in 8.0 (the trust boundary is the network between gateway and
  services, documented in `security-model.md`). Adding a signature or an audience is a new member, so it bumps the
  header's `v` (RFC 0010, 2026-10-29 supplement).
- **RC1-42:** negative caching of unknown principals is deferred to 8.1; it is additive (RFC 0010, 2026-10-29
  supplement).

**Decisions for batch B** (maintainer, 2026-10-30; recorded in RFC 0007's 2026-10-30 revision). B1 and B2 are two
PRs from one implementation session; B2 starts from `main` after B1 merges. Findings not listed take the fix written
under them.

- **RC1-2:** the analysis reads the grantor's attributes through the function the engine reads them with
  (`toString()` of every value), shared, not copied.
- **RC1-4:** read every app document the grantor's roles reach; a document, or the grantor's memberships in its app,
  that cannot be read makes the fragment UNKNOWN. Not a blanket UNKNOWN for fragments over every app. *Amended the
  same day (coordinator, after B1 found it):* the reverse index does not record an app's bindings of its own `perm:`
  policies, so the app documents are listed with `ControlStore.documents()` (never fewer than exist) and every app
  head is read; no new SPI, index entries or upgrade step. *Amended again the same day (coordinator, after the
  independent review of #1181):* the single document list fails open when it is lost (it reads as empty or short,
  and indexed documents are never listed again), and every tenant change hashed its 5.2 MB value in Redis, which a
  tenant admin could loop. The analysis reads a small app list instead (a `ControlStore` addition): one value with
  the apps and a `complete` flag. An app's first index write adds it, creating the list as incomplete when it is
  missing; the platform's first index write and `repair-references` make it complete. A missing, incomplete or
  unreadable list, an entry that does not decode, or a named app whose head exists but is not listed, makes every app
  unread (UNKNOWN). A lost list therefore fails closed whoever recreates it, and an upgraded deployment needs approval
  for grants over every app until `repair-references` has run. `checkedWith` records the list's digest.
- **RC1-9:** both halves: bindings and attachments that re-resolve after a tenant `RemovePolicy` are analyzed as new
  grants, and a platform policy whose id a tenant document already uses is refused, the error naming those documents.
  *Amended the same day:* a tenant document's own policy ids are recorded as referrers of `(platform, id)` and
  confirmed by reading the referrer's head; a tenant that only defines the id never blocks the platform from removing
  its own policy of that id. Existing tenant documents enter the index through `repair-references` after the upgrade
  (`upgrading.md`); until then a collision is only ambiguous, which the engine fails closed on. `repair-references`
  had no entry point, so it becomes a `cosec-migrate` command (an addition): it walks `ControlStore.documents()`,
  repairs each document's references, and exits non-zero naming every head it could not read. Not a maintenance task:
  every round would pay for a one-off upgrade step.
- **RC1-12:** "narrowing only" is a whitelist: removing a binding or an attachment, adding a blacklist entry, adding a
  DENY-only policy and its binding. Nothing else preempts. A break-glass revoke always preempts; the preempted change
  becomes CONFLICTED.
- **RC1-27:** implement the RFC 0007 §8 metadata check in the compiler and cap `--break-glass-max-duration` at 24 hours.
  If `cosec-migrate` cannot supply truthful metadata, stop and ask.
- **RC1-28:** documentation only in 8.0; a REQUIRED-audited publish of platform documents is additive and moves to 8.1.
- **RC1-29:** drop the `binding` parameter of `BreakGlass.request`.
- **RC1-33:** *Amended the same day (maintainer: "文档加写后检测").* An atomic compare-and-set over every recorded head
  is not possible: the heads are separate keys without a shared hash tag and Redis Cluster is supported, so no
  multi-key script can cover them (a multi-key conditional write in CoCache, which we maintain, would not change that).
  One hash tag for all snapshot keys (every document on one shard, a new key layout) and a control-plane lease
  (fencing) were rejected. The publish
  keeps its compare-and-set on the target head and documents the window; after the write it re-reads every head in
  `checkedWith` and, when one moved, re-runs the analysis on the current heads and writes a change audit event with the
  new verdict. No rollback. The window is safe to document because restricting a grantor never withdraws a grant it
  already made, so a concurrent outcome is the serial order "grant, then restriction"; the one outcome no serial order
  gives is two changes that each remove a right the other's grant relies on, landing within the same window.
- **RC1-35 (b):** an `Anyone` grant in tenant `(0)` always needs approval.
- **RC1-37:** the default space's stand-in becomes a form the space-id grammar already refuses; the data-plane format
  does not change.

**Observations for batch D** (roadmap §7): `SnapshotStoreBlockHoundTest#aColdLoadOverTheStoreNeverBlocksTheCaller`
caught Lettuce's `SharedLock` parking under contention once; never relax that test to make it pass.
`RedisSnapshotDocumentStoreTest#passesOnInvalidationsOfItsNamespaceFromEveryInstance` failed three times, each on a
PR that changed no code. A read-only investigation on 2026-10-30 found a test race, not a lost invalidation: the
failing assertion runs after `subscription.close()` and `clear()`, so `[platform]` is one delivery *after* the
close. The wait for "the instance's own write" is met by the synchronous `notifyChanged` while the Redis echo is
still in flight, and CoCache's `dispatch` snapshots its listeners when a message arrives. Batch D fixes the test
without relaxing it: wait until the echo has arrived, then use a second subscription as a positive barrier instead
of `Thread.sleep`. CoCache 6.9.0 does not change `dispatch`. In production the channel is at-most-once by contract;
CoCache resets every listener on each (re)subscription and failed heartbeat, but a failed non-atomic publish, a
broken cluster bus link or a malformed frame loses a message with no reset. The bound is `SnapshotSource`'s
periodic conditional read of every installed document (`revalidate-interval`, 10 s by default), the same for
platform, app and tenant documents; the control plane does not depend on invalidations. That bound can be switched
off: RC1-50.

### 1. Multi-tenant isolation

**Trust boundary.** The tenant comes only from the verified credential; the app from the host configuration, else
from the client; the space from the client, checked against the principal's roles. A gateway forwards what it
verified in `CoSec-Identity`, and a service in gateway mode believes it.

| Attacker | Threat | Verdict |
|---|---|---|
| Authenticated user | Select another tenant with a `CoSec-*` parameter | Mitigated: no tenant parameter exists; `ScopeResolver` takes the credential's tenant (`TNT-1`) |
| Authenticated user | Act in a space without a role there, or fall back to the default space | Mitigated (`SCP-1`, `SCP-6`) |
| Authenticated user | Disagreeing header and query values read differently by CoSec and the backend | Mitigated for differing non-blank values (`SCP-4`); blank values: RC1-16 |
| Authenticated user | Choose the app, and with it whose role bindings apply | By design without a host app; on a gateway: RC1-6 |
| Holder of a capped API key | Use the key to escape a restriction placed on its principal | **RC1-1** |
| Tenant admin | Make a tenant document apply to another tenant | Mitigated: documents bind only their own tenant's subjects; `SnapshotView.checkScope` refuses foreign documents (`TNT-2`, `TNT-4`) |
| Client of the gateway | Forge `CoSec-Identity` | Mitigated at the gateway (stripped first and at the last hop); not at enforce-mode adapters (RC1-18) |
| Compromised downstream | Replay or forge `CoSec-Identity`; harvest credentials | Identity unsigned by design (RC1-19); API keys forwarded (RC1-5) |
| Caller of a gateway host | Reach what no route matches: the gateway's own endpoints, its actuator | Not under CoSec (RC1-48); documented |
| Whoever adds a route at run time | Send users' traffic and identity to a host they choose | Through an exposed `gateway` endpoint: RC1-48; identity forwarded unless the route opts out: RC1-49 |
| Tenant admin (control) | Write another tenant's document | Mitigated: `TenantIsolation` runs before every policy check, and resources carry the target tenant (`TNT-3`) |

**Conclusion.** Tenant isolation on the data plane and `TNT-3` on the control plane hold. The gaps are the role cap
(RC1-1), the gateway's single host app (RC1-6), and what the gateway forwards and to whom (RC1-5, RC1-48, RC1-49).

#### RC1-1 · High · A role cap drops the DENYs bound to the principal

- **Status:** fixed in #1164.
- **Attacker:** a principal under a personal restriction who holds, or can issue, a capped API key.
- **Scenario:** the tenant binds `Principal(acme, alice)` to a DENY `order:export`; alice's role `ops` holds ALLOW
  `order:*`. With her JWT, `order:export` is denied by the principal binding. With an API key capped to `ops`, the
  same request is permitted: a capped credential matches no principal binding (`BND-9`, `IDN-2`), and the one
  enumeration of candidates feeds both the DENY and the ALLOW pass, so the DENY is never a candidate. Attachments are
  dropped under a cap in the same way, with any DENY statements they carry. This breaks `IDN-1` ("a key is never more
  than its principal") and the deny-first invariant. A local probe (an engine-level scenario with a principal DENY
  and an `Anyone` ALLOW) gives Deny with `principalBindings: true` and Permit with `false`.
- **Evidence:** `core/engine/src/main/kotlin/me/ahoo/cosec/engine/flat/CandidateOrder.kt` (`principal` returns before
  the principal bindings when `principalBindings` is false), `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/MembershipResolver.kt`
  (the cap empties attachments), `core/control/src/main/kotlin/me/ahoo/cosec/control/grant/GrantorRights.kt`
  (`applicability` mirrors it, so a capped grantor's own DENYs do not limit what it grants).
- **Fix:** a cap removes ALLOW candidates only. Principal bindings and attachments still contribute their DENY
  statements under a cap; the grant analysis keeps the grantor's DENYs the same way. Amend the text of `BND-9` and
  `IDN-2` (RFC 0009's 2026-10-29 revision says "no principal binding", which reads as both effects).
- **Regression test:** `BND-9` and `IDN-1` scenarios "a principal-bound DENY still applies to a capped credential"
  and "an attached DENY still applies"; a `GRT` scenario for the capped grantor; a mutant that skips principal-bound
  DENYs under a cap.

#### RC1-5 · Medium · The gateway forwards the client's API key to the services behind it

- **Status:** open.
- **Attacker:** a compromised service behind the gateway, or a third-party backend on a route with
  `cosec-identity: false`.
- **Scenario:** with `cosec.gateway.identity.forward-authorization=false` (the default), `PipelineGatewayFilter.filter`
  removes only `Authorization`. The API key header (`X-API-Key`, or `cosec.pipeline.api-key-header`) and, with
  `cosec.pipeline.allow-query-token`, the `authorization` query parameter go downstream unchanged, on every route,
  including routes opted out of the identity "as for a third party". The receiver can replay the key at the gateway
  from outside as that principal; API keys need not expire. `wiki/integration/web.md` says the service behind
  "never sees a token"; only the cookie case is documented.
- **Evidence:** `edge/gateway/src/main/kotlin/me/ahoo/cosec/gateway/PipelineGatewayFilter.kt`.
- **Fix:** under the same switch, also strip the configured API key header and the `authorization` query parameter
  (and say what happens to the cookie). Update `wiki/integration/web.md` and `wiki/operations/configuration.md`.
- **Regression test:** a gateway test that a permitted request reaches the backend without the API key header and
  query token; an `IDN` rule for credential stripping at the gateway, with a scenario.

#### RC1-6 · Medium · One host app for the whole gateway

- **Status:** open.
- **Attacker:** an authenticated user of a gateway that fronts several apps.
- **Scenario:** RFC 0004 §4.6 has a gateway take the host app from the route's metadata (`cosec-app-id`). The
  implementation has one value for the whole gateway (`cosec.authorization.scope.app-id`), so a gateway that fronts
  several apps leaves it unset, and every request's app is the client's `CoSec-App-Id`. An app document contributes
  only its role bindings, and only on a request in that app. A client calling app `billing`'s routes with
  `CoSec-App-Id: shop` (or with none) skips every DENY `billing`'s document binds to its roles, while ALLOWs from the
  tenant document or the platform that are not scoped to an app still apply: the request is permitted. The
  documentation calls the client-chosen app "the weak spot" and describes widening, but not that an app's DENYs are
  skipped. The KDoc of `HostScope` and `HttpFacts.host` still says "for the gateway, the route's".
- **Evidence:** `edge/gateway/src/main/kotlin/me/ahoo/cosec/gateway/PipelineGatewayFilter.kt`,
  `host/spring-boot/src/main/kotlin/me/ahoo/cosec/spring/boot/starter/pipeline/CoSecPipelineWebAutoConfiguration.kt` (`hostOf`),
  `core/model/src/main/kotlin/me/ahoo/cosec/model/scope/ScopeResolver.kt`,
  `core/engine/src/main/kotlin/me/ahoo/cosec/engine/flat/CandidateOrder.kt`, `wiki/guide/security-model.md`.
- **Fix:** read the host app from the route metadata `cosec-app-id` as RFC 0004 specifies, falling back to the
  property; document in `security-model.md` that without a host app an app's DENYs apply only when the client
  declares that app. Fix the KDoc.
- **Regression test:** an `SCP-2` scenario at the pipeline level for a route-scoped host app; a gateway test with two
  routes of different apps.

#### RC1-48 · Medium · Requests no route matches are not under CoSec on a gateway host

- **Status:** open.
- **Attacker:** anyone who can reach the gateway, when the operator exposes the `gateway` actuator endpoint on the
  application port (one of the ways to change Spring Cloud Gateway routes at run time).
- **Scenario:** on a gateway host the starter registers no `WebFilter` (`@ConditionalOnMissingClass` of
  `GlobalFilter`); `PipelineGatewayFilter` is a `GlobalFilter` and runs only for requests a route matches. Everything
  else on the host, its actuator included, is not authorized by CoSec. With the `gateway` endpoint exposed, an
  anonymous caller creates a route (`POST /actuator/gateway/routes/{id}`, then `POST /actuator/gateway/refresh`) that
  matches users' paths and points at a host the caller controls. Users' requests are then authorized as before and
  forwarded there, with the verified `CoSec-Identity` (RC1-49) and, with `forward-authorization` on, their bearer
  tokens. `wiki/integration/web.md` says actuator is not protected and to use the management port or a network policy;
  nothing enforces it. `cosec-gateway-server` exposes only `health`, the Spring Boot default. 7.x wires the gateway the
  same way.
- **Evidence:** `host/spring-boot/src/main/kotlin/me/ahoo/cosec/spring/boot/starter/pipeline/CoSecPipelineWebAutoConfiguration.kt`
  (`WebFlux` is `@ConditionalOnMissingClass(GATEWAY_GLOBAL_FILTER)`),
  `edge/gateway/src/main/kotlin/me/ahoo/cosec/gateway/PipelineGatewayFilter.kt`, `wiki/integration/web.md`.
- **Options weighed:**
  - *A startup check* (recommended): on a gateway host in enforce mode, fail startup when an actuator endpoint other
    than `health` is exposed over HTTP on the application port (`management.server.port` unset or equal to
    `server.port`), naming the endpoint, unless a property such as `cosec.gateway.unprotected-endpoints` lists it; never
    accept `gateway` there, since it writes routes: it belongs on a separate management port behind a network policy.
    It closes the hijack at once, in the style of `STA-1`, and costs nothing on the request path.
  - *Putting non-routed requests under the pipeline:* a `WebFilter` runs before route matching, so it cannot tell a
    routed request from an unrouted one without repeating the route lookup; and every health probe would then need
    an `Anyone` ALLOW in the platform document and would fail with Redis, so liveness would flap during an outage.
    Worth considering after 8.0 for application controllers on a gateway host; not needed for the actuator.
  - *Documentation only:* already there, and it did not stop this from being a one-line misconfiguration.
- **Fix:** the startup check; keep the documentation and link it from the failure message.
- **Regression test:** a starter test (`ApplicationContextRunner`) per case: `gateway` exposed on the application port

#### RC1-49 · Medium · Identity forwarding is opt-out per route

- **Status:** open.
- **Attacker:** a third party on a route that lacks `cosec-identity: false`, typically one added at run time (property
  refresh, a `RouteDefinitionRepository` such as the actuator's in-memory one or the Redis one, a custom
  `RouteLocator`), which gets none of the review a configuration change gets.
- **Scenario:** `PipelineGatewayFilter.read` disables forwarding only when the matched route's metadata says
  `cosec-identity: false`; it reads the metadata per request from `GATEWAY_ROUTE_ATTR`, so a route added at run time
  takes effect at once. A route to `https://partner.example` without that metadata receives every permitted user's
  tenant, principal id, roles, credential id and expiry, and the claims `cosec.gateway.identity.claims` names;
  `forward-authorization`, when on, is global, so that route also receives every user's bearer token. The repository's
  own sample forgets the metadata (RC1-20), which shows how easily the opt-out is missed.
- **Evidence:** `edge/gateway/src/main/kotlin/me/ahoo/cosec/gateway/PipelineGatewayFilter.kt` (`read`, `filter`),
  `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/identity/IdentityIssuer.kt`.
- **Options weighed:**
  - *Opt-in by scheme* (recommended): forward the identity when the route's `cosec-identity` metadata is exactly `true`,
    or when it is absent and the route's URI scheme is `lb` (`lb://service`, `lb:ws://service`); never otherwise;
    `false` always wins. In-cluster routes through service discovery keep working unchanged, and an `lb` target is a
    registered service, so whoever controls it is already inside the trust boundary. A route to any other URI gets no
    identity until someone marks it, which fails closed: the service behind sees an anonymous request. Apply the same
    per-route decision to `forward-authorization`, so a bearer token goes only where the identity goes.
  - *Pure opt-in* (`true` required on every route): the simplest rule, but every route needs metadata, including the
    routes the discovery locator generates, with no security gain over the `lb` default.
  - *Keep opt-out:* RC1-20 shows the failure mode.
- **Breaking change:** routes to internal services by `http(s)://` lose the identity until they say
  `cosec-identity: true`; their services see anonymous requests. Alpha.1 has no compatibility promise; the fix PR
  takes `!` in its title and a line in `wiki/operations/upgrading.md`, and updates `wiki/integration/web.md`.
- **Regression test:** gateway tests for each case (`lb` without metadata forwards; `https` without metadata does not;
  `true` forwards; `false` never does; `Authorization` follows the identity); an `IDN` rule with a scenario.

### 2. Control-plane privilege escalation and grant analysis

**Trust boundary.** The control plane is the only writer of documents. A write is authorized through the host's
pipeline on confirmed-current documents; `TenantIsolation` is a hard rule; the grant analysis (RFC 0007 §7.4) must
never answer "contained" for a fragment the grantor does not hold, and whatever it cannot prove goes to approval.
The trust root is the platform administrators holding `cosec:approve` (§7.3).

| Attacker | Threat | Verdict |
|---|---|---|
| Tenant admin | Write another tenant's, an app's or the platform's document | Mitigated (`TNT-3`) |
| Tenant admin | Grant a right it does not hold, without approval | **RC1-2, RC1-3, RC1-4**, RC1-9 |
| Temporary admin | Outlive its `expiresAt` | **RC1-3** |
| Tenant principal given `cosec:approve` | Act as the trust root; leave its platform boundary | RC1-10 |
| Tenant admin | Bind or redefine the built-in control policies | Mitigated: built-ins cannot be defined by a document; binding `cosec:platform-admin` is UNKNOWN (RC1-36 hardens it) |
| Approver | Approval reused after an edit, or self-approval | Mitigated: approval bound to the candidate digest; author and publisher cannot approve |
| Approver whose rights were withdrawn | Approval still counts | RC1-11 |

**Conclusion.** The structure (hard tenant rule, authorization of every target on confirmed documents, digest-bound
approvals, fail-closed analysis on UNKNOWN) is sound. The soundness argument of §7.4.5 does not hold in four places
where the analysis reads the grantor's rights differently from the engine: attribute types (RC1-2), binding expiry
(RC1-3), the set of app documents read (RC1-4) and policy re-resolution (RC1-9). `GrantPropertyTest`'s generator
covers none of the four.

#### RC1-2 · High · The analysis drops the grantor's non-string attributes

- **Status:** fixed in #1181.
- **Attacker:** a tenant admin whose token carries `attributes: {"suspended": true}` (a JSON boolean).
- **Scenario:** the admin holds, through role `ops`, ALLOW `order:*` on `order/**` with the condition
  `not(eq(subject.attributes.suspended, "true"))`; at run time the engine reads the attribute with `toString()`, so the
  statement does not apply to them. `Operator.of` keeps only `String` attribute values, so for the analysis the
  attribute is absent: `eq` is false, `not` is true, and the statement counts as held unconditionally. The admin binds
  the same ALLOW, without the condition, to their own principal; the verdict is contained, no approval is needed, and
  after the shadow window they publish it. Any negated or `exists` atom over a non-string subject attribute behaves
  the same; positive atoms fail safe (UNKNOWN). The approver path already records every attribute type.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/authz/ControlAuthorization.kt` (`Operator.of`),
  `core/control/src/main/kotlin/me/ahoo/cosec/control/change/ChangeAuthority.kt` (`escalations` builds the `Grantor`),
  `core/control/src/main/kotlin/me/ahoo/cosec/control/grant/GrantAnalyzer.kt` (`grantorConstants`),
  `core/engine/src/main/kotlin/me/ahoo/cosec/engine/flat/FlatEvaluator.kt` (`string`).
- **Fix:** give the analysis the grantor's attributes exactly as the engine reads them (`toString()` of every value),
  from one shared function; or treat any non-string value as incomparable (UNKNOWN).
- **Regression test:** a `GRT` scenario with a boolean attribute under `not`; extend `GrantGenerator` to non-string
  attributes; a mutant that drops non-string attributes again.

#### RC1-3 · High · Rights held through an expiring binding count as permanent

- **Status:** fixed in #1181.
- **Attacker:** a principal given administration, or any data-plane right, for a limited time.
- **Scenario:** the platform binds `cosec:tenant-admin` to `Principal(acme, contractor)` in the control app with
  `expiresAt` in 8 hours. The contractor proposes the same binding without `expiresAt`. The analysis collects the
  grantor's rights from every binding that has not expired yet, and fragments carry no expiry, so every fragment is
  contained. The shadow window shows no difference while the old binding lives, nothing needs approval, and the
  contractor publishes. After 8 hours they are still tenant admin. Time *conditions* are kept as residuals, so they do
  not have this problem; binding expiry does.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/grant/GrantorRights.kt` (`Collector.document`,
  `HeldStatement` has no expiry), `core/control/src/main/kotlin/me/ahoo/cosec/control/grant/GrantAnalyzer.kt`.
- **Fix:** a statement held through a binding with `expiresAt` contains only fragments whose own binding expires no
  later; an attachable policy, a binding without expiry, or a later one is UNKNOWN.
- **Regression test:** a `GRT` scenario for the contractor case; a generator case with expiring bindings; a mutant
  that ignores the held binding's expiry.

#### RC1-4 · High · Role-bound DENYs in app documents the change does not name are not read

- **Status:** fixed in #1181.
- **Attacker:** a tenant admin, granting to another principal (possibly one they control).
- **Scenario:** the grantor has role `ops`; the tenant binds `Role(acme, ops)` to ALLOW `order:*` on `order/**` in
  `(*, default)`. App `billing`'s document binds `Role(*, ops)` to DENY `order:delete`, so in `billing` the grantor
  cannot delete. The grantor binds the same ALLOW to `Principal(acme, bob)` in `(*, default)`. The analysis loads only
  the apps the candidate's bindings name exactly, plus the control app; `billing` is not read, its DENY is not among
  the grantor's DENYs, and the verdict is contained. Bob, without `ops`, may `order:delete` in `billing`. RFC 0007
  §7.4.3 step 3 requires every DENY applicable to the grantor to be considered. Attachable policies (scope `EVERY`)
  and conditions that narrow to an app have the same gap. Role bindings live only in app and tenant documents, so
  this is where the grantor's role-bound DENYs are.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/change/ChangeAuthority.kt` (`escalations`: the
  `apps` set), `core/control/src/main/kotlin/me/ahoo/cosec/control/grant/GrantorRights.kt`.
- **Fix:** for a fragment whose app dimension is every app, or an app not loaded, read every app document the
  grantor's roles reach (the reverse index knows them), or answer UNKNOWN.
- **Regression test:** a `GRT` scenario with an app DENY and an app-wildcard grant; a mutant that reads only named
  apps.

#### RC1-9 · Medium · Removing a tenant policy re-points its bindings to a platform policy

### 3. Approvals and break-glass

**Trust boundary.** Break-glass is requested and approved by two different platform principals, bounded in time,
written to a REQUIRED audit before it is published and before every use, and applies only to CoSec's own token
(`BRK-*`, RFC 0007 §8, RFC 0009 §4.2).

| Attacker | Threat | Verdict |
|---|---|---|
| One platform user | Create break-glass alone | Mitigated: approve refuses the author; always two people regardless of `four-eyes` |
| Requester | Exceed the expiry cap, by renewal or a far-future or missing `expiresAt` | Mitigated: checked at propose and again at publish; no renewal; data plane needs `expiresAt` |
| API key, capped credential, forwarded identity | Reach a break-glass binding | Mitigated (`BRK-8`): only `Identity.Method.JWT`; RC1-26 hardens how that is decided |
| Anyone | Use break-glass without the REQUIRED audit | Mitigated: 503 without a REQUIRED listener; a listener failure turns the permit into 503; `check` refuses break-glass-only permits |
| Approver whose rights were withdrawn | Approval still counts | RC1-11 |
| Defender | Revoke a live grant at once | RC1-12 |
| Single trust-root admin | Equivalent standing access through an ordinary change | RC1-28 |

**Conclusion.** The two-person rule, the cap and the audit-first ordering hold. Revoking is not always possible at
once (RC1-12), and the approver's standing is checked on stale data (RC1-11).

#### RC1-11 · Medium · Publish re-checks the approver on recorded memberships only

- **Status:** fixed in #PRNUM.
- **Scenario:** an approver approves a change. Their role `approver` is then removed in the membership provider, or
  every token of theirs is revoked (`revokeSubject`), perhaps because the approval was made with a stolen token. At
  publish, `decideAs` asks the provider whether the approver still stands, discards its fresh memberships, and decides
  on the memberships recorded at approval; no revocation is read. The change publishes within the 72-hour approval
  lifetime. The #1095 note documents this only for roles carried in token claims.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/change/ChangeAuthority.kt` (`approverProblem`),
  `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/AuthorizationChecker.kt` (`decideAs`).
- **Fix:** record the approver's credential id and `iat` on the approval and check revocation at publish; decide on
  the provider's fresh memberships when they come from the provider.
- **Regression test:** `APR` scenarios for a revoked approver and a provider approver who lost the role.

#### RC1-12 · Medium · A break-glass revoke cannot preempt a busy staging slot

- **Status:** fixed in #PRNUM.
- **Scenario:** a platform change is in its shadow window (up to 24 hours) or awaiting approval, holding the
  platform document's staging slot for up to `cosec.control.changes.expire-after` (7 days). A break-glass grantee's
  account is compromised; `DELETE` on the break-glass binding answers 409 because `revoke` stages like any change.
  The operator must first abandon the holder, which needs `cosec:publish`, and races anyone who stages again. RFC
  0007 §5.5 and Q5 let a narrowing change by a holder of `cosec:skip-shadow` preempt the slot ("an emergency ban must
  not queue"); nothing implements it. Emergency DENYs and blacklist changes are blocked the same way. The grant still
  expires within the cap, and token revocation still works.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/change/BreakGlass.kt` (`revoke`),
  `core/control/src/main/kotlin/me/ahoo/cosec/control/change/Changes.kt` (`takeSlot`).
- **Fix:** implement preemption for narrowing-only changes by a holder of `cosec:skip-shadow`, the preempted change
  becoming CONFLICTED; break-glass revoke always preempts.
- **Regression test:** a `BRK` scenario (revoke while the slot is held) and a `CTL` scenario for an emergency DENY.

- **Scenario:** a platform administrator holding `cosec:approve` (the trust root) publishes their own changes without
  analysis or a second person (`four-eyes` is off by default), and holds `cosec:skip-shadow` through `cosec:*`. Alone,
  they can bind a non-expiring ALLOW `*` to themselves with BEST_EFFORT audit: everything break-glass would have given,
  without its two people, cap or REQUIRED audit. RFC 0007 Q10/Q21 chose this; the user docs do not say it.
- **Fix:** say in `wiki/guide/security-model.md` and `wiki/policies/testing.md` that break-glass's guarantees bind
  the trust root only with `four-eyes` on; consider a REQUIRED-audited publish for platform documents.
- **Regression test:** none (documentation).

#### RC1-29 · Low · `BreakGlass.request` can replace any platform binding

- **Status:** fixed in #PRNUM.
- **Scenario:** the public `request(..., binding: BindingId)` puts a break-glass binding under a caller-chosen id. An
  existing binding of that id, an `Anyone` DENY say, is replaced; authorization of a `BREAK_GLASS` change checks only
  `cosec:breakglass`, and the approver sees "break-glass binding X". When the grant expires the DENY is gone for good.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/change/BreakGlass.kt`.
- **Fix:** refuse a break-glass `PutBinding` that replaces a binding that is not break-glass, or drop the parameter.
- **Regression test:** a `BreakGlassControlTest` case.

#### RC1-30 · Low · The approval's REQUIRED audit is written too early, and not required

- **Status:** fixed in #PRNUM.
- **Scenario:** `Changes.approve` writes `BREAK_GLASS_APPROVED` before the compare-and-set that checks the candidate
  digest, so a stale approve leaves a record of an approval that never happened. It also does not call
  `requireAudit`: on an instance without a REQUIRED listener (configuration drift), the approval is recorded with
  BEST_EFFORT audit only, and publish then succeeds on another instance.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/change/Changes.kt` (`approve`).
- **Fix:** require a REQUIRED listener for a break-glass approval, and write the event after the digest is checked
  and before the transition is stored.
- **Regression test:** a `BRK-3` scenario for an approve without a REQUIRED listener.

#### RC1-31 · Low · A listener's `CancellationException` escapes

- **Status:** fixed in #PRNUM.
- **Scenario:** `ChangeListeners.deliverRequired` rethrows any `CancellationException`, including one a listener
  throws while the step is active (a cancelled future in the Kafka listener). The step does not happen, but the caller
  gets an unmodelled cancellation instead of 503. `DecisionListeners.deliver` already tells the two apart.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/audit/ChangeAudit.kt`.
- **Fix:** rethrow only when the caller's coroutine is cancelled; otherwise a failure.
- **Regression test:** a `ChangeListenersTest` case.

### 4. Snapshot and cache poisoning

**Trust boundary.** Redis is the store of record. Only the control plane and `cosec-migrate` write snapshot
documents; the data plane only reads. Someone with Redis write access decides every request (documents are not
signed, RFC 0007 §1.2); the defences are against loss, corruption and races, not against that writer.

| Attacker or event | Threat | Verdict |
|---|---|---|
| Malformed or crafted document | Decoded leniently: duplicate keys, unknown fields, wrong types, default typing | Mitigated for documents (`DOC-3`); three cocache formats accept duplicate keys (RC1-44) |
| Racing loads | An older revision installed over a newer one | Mitigated: one load per key, installs in load order (`SNP-2`); replica reads: RC1-47 |
| Eviction, `FLUSHDB`, failover | A lost document read as empty, dropping its DENYs | Mitigated for the platform document (`platformRequired`) and for any document this instance has seen (LOST fails closed); `noeviction` checked at startup only (RC1-47) |
| Unreadable or uncompilable document | Served as empty or as the previous revision | Mitigated: installed as failed, Indeterminate unless a DENY matches; `VirtualMachineError` is the exception (RC1-43) |
| Application customizer | Re-enable TTL or a lenient read on store-of-record caches | Mitigated through the starter; not for caches built outside it (RC1-45) |
| Second deployment on the same Redis | Shared keys | RC1-46 |
| Authenticated user | Load and evict app documents at will | RC1-7 |

**Conclusion.** The snapshot path fails closed on everything it reads and keeps revisions in order. The findings are
about caches built outside the starter, prefixes, and operations.

#### RC1-7 · Medium · Random app ids evict real app documents

- **Status:** open.
- **Attacker:** any authenticated principal with a role in the requested space, on a host without
  `cosec.authorization.scope.app-id` (every multi-app gateway, see RC1-6).
- **Scenario:** each request declares a new `CoSec-App-Id`. The view loads `App(id)` (two Redis reads), installs an
  `Absent` entry, and that entry counts toward `max-apps` (1024): `evictBeyond` then evicts the least recently used
  slot, which may be a real app document. At one or two thousand requests per second, real documents of other
  tenants' apps are evicted continuously; their requests cold-load and recompile on the two compile threads (queue
  of 64) and answer 503 when the queue is full or `cold-load-timeout` passes. It fails closed, across tenants.
  Anonymous callers cannot do it (no roles, so no app document is loaded), and tenant ids come only from credentials.
- **Evidence:** `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/snapshot/SnapshotSource.kt` (`onAbsent`,
  `evictBeyond`), `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/snapshot/SuspendingSnapshotSource.kt` (`ViewKey.of`).
- **Fix:** keep `Absent` entries in their own small bound so they never evict a present document; optionally answer
  an app id that has no document without installing it.
- **Regression test:** a `SnapshotSource` test that a flood of absent app ids leaves present documents installed;
  an `SNP` rule if it is made normative.

#### RC1-43 · Low · A `VirtualMachineError` while compiling keeps the previous revision

- **Status:** open.
- **Scenario:** `compileState` rethrows `VirtualMachineError` (a `StackOverflowError` from a document that compiles on
  the control plane but not on a data-plane thread with a smaller stack). The load then ends as a transient failure,
  which keeps the installed revision: a new DENY never applies, and only the lag alarm shows it.
- **Evidence:** `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/snapshot/SnapshotSource.kt` (`compileState`).
- **Fix:** install the revision as failed before rethrowing.
- **Regression test:** a `SnapshotSource` test with a compiler that throws `StackOverflowError`.

#### RC1-44 · Low · Three stored formats accept duplicate keys

- **Status:** open (needs Redis write).
- **Scenario:** `ApiKeyCodec`, `MembershipsCodec` and the shadow `ReportersCodec` parse without duplicate detection,
  unlike every other stored format: `{"format":2,…,"roles":["viewer"],…,"roles":null}` decodes as an uncapped key.
  The revoked-token and revoked-subject codecs use the application's `ObjectMapper` rather than `CoSecJson.mapper`.
- **Evidence:** `backends/cocache/src/main/kotlin/me/ahoo/cosec/cache/ApiKeyCodec.kt`, `MembershipCache.kt`,
  `backends/cocache/src/main/kotlin/me/ahoo/cosec/cache/shadow/CoCacheShadow.kt`, `CoSecCacheSpecs.kt`.
- **Fix:** strict duplicate detection everywhere; one mapper.
- **Regression test:** codec tests with a duplicate key.

#### RC1-45 · Low · The cache pins depend on the starter

- **Status:** open.
- **Scenario:** the public `createPolicySnapshotCache(spec)` pins nothing, and `cosecPolicySnapshotCache` is
  `@ConditionalOnMissingBean`, so an application bean built from a spec with a TTL bypasses `ttl = null` (`SNP-3`).
  `CoSecCacheAssembler.assemble` pins the policy but not `ttlOf`, `keyFilter`, `loader` or `codec`: a customizer's
  `keyFilter` on `RevokedTokenCache` can hide revocations.
- **Evidence:** `backends/cocache/src/main/kotlin/me/ahoo/cosec/cache/snapshot/PolicySnapshotCache.kt`,
  `host/spring-boot/src/main/kotlin/me/ahoo/cosec/spring/boot/starter/authorization/cache/CoSecCacheAssembler.kt`.
- **Fix:** apply `pinPolicySnapshot` inside `createPolicySnapshotCache`; pin the other fields in the assembler.
- **Regression test:** extend `CacheTtlPolicyTest` to a cache built outside the starter.

#### RC1-46 · Low · Two deployments on one Redis share more than they think

- **Status:** open.
- **Scenario:** only the snapshot, control, candidate and shadow keys follow
  `cosec.authorization.snapshot.key-prefix`. API keys (`cosec.api-key.key-prefix`), memberships and revocations
  (`cosec.authorization.cache.key-prefix`) and rate-limit counters (fixed) do not. A second deployment that changes
  only the snapshot prefix issues an API key that the first deployment accepts, and fills memberships the first one
  serves. `storage.md` lists the prefixes, but nothing checks them.
- **Fix:** derive every prefix from one deployment prefix, or fail startup when the snapshot prefix is changed and
  the others are not.
- **Regression test:** a starter test of the prefix check.

#### RC1-47 · Low · Operations documentation

- **Status:** open (documentation).
- **Scenario:** (a) `EvictionPolicyCheck` runs at startup only; a later `CONFIG SET maxmemory-policy`, a failover to
  a differently configured node, or `FLUSHDB` is not seen, and an instance started afterwards reads a lost app or
  tenant document as empty. (b) If Redis is read from replicas, revalidation may alternate between a primary and a
  lagging replica and flap a just-published DENY (PLAUSIBLE; depends on CoCache's read routing). (c) The hardening
  checklist does not say that Redis write access, or a man in the middle on a plaintext Redis connection, decides
  every request. (d) The KDoc of `CoSecCacheSpecs.policySnapshot` still says a lost platform document means "no
  global policies".
- **Fix:** re-check the eviction policy in the snapshot health indicator; require primary reads; add Redis TLS and
  the per-role ACLs of `storage.md` to the checklist in `wiki/guide/security-model.md`; fix the KDoc.

#### RC1-50 · Medium · `revalidate-interval: 0` removes the bound on a lost invalidation

- **Status:** open. Added 2026-10-30 from the investigation of the invalidation test (Observations above).
- **Scenario:** CoCache's invalidation channel is at-most-once. When a message is lost without a reset (a failed
  non-atomic publish in sharded mode, a broken cluster bus link, a malformed frame), or a reload after a notification
  fails, only `SnapshotSource`'s periodic pass brings the instance up to date. `cosec.authorization.snapshot.revalidate-interval: 0`
  is allowed and documented, and it turns that pass off, along with lag reporting. The instance then serves the old
  document, for example a platform document without a just-published DENY, until that key changes again, the
  channel resets, the slot is evicted (app and tenant only) or the instance restarts, with nothing reported.
- **Evidence:** `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/snapshot/SnapshotOptions.kt` (`revalidateInterval`
  may be zero), `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/snapshot/SnapshotSource.kt` (`tick` is not
  scheduled; `reportLag` runs only inside it), `wiki/operations/configuration.md`.
- **Fix (coordinator, 2026-10-30):** the periodic pass is mandatory: a zero or negative interval fails startup, and
  batch D sets an upper bound. A breaking change for previews, recorded in `upgrading.md`; `configuration.md` and
  `troubleshooting.md` follow. Optionally, retry a reload that failed after a notification instead of waiting for the
  next pass.
- **Regression test:** a new rule `SNP-6` ("a change whose invalidation is lost, or whose reload failed, is installed
  within `revalidate-interval`") guarded by the existing `SnapshotRevalidationTest` and `SnapshotInvalidationOrderTest`
  cases; mutants that do not schedule the periodic pass, ignore `onReset`, or revalidate through the local copy; a
  starter test that `0` fails startup.
- **Regression test:** a health-indicator test for (a).

### 5. problem+json disclosure

**Trust boundary.** Everything in a response is visible to the caller. Status codes and bodies come only from
`StatusMapping`; a body never carries a policy, statement, attribute value or exception; explicit and implicit denies
look the same (RFC 0006 §6.1, §6.2). Explain and simulate show only the documents the caller may read (RFC 0007
§10.3).

| Attacker | Threat | Verdict |
|---|---|---|
| Anonymous caller | Read policy, statement or exception details from a refusal | Mitigated: fixed members only, ASCII-escaped; 500 has no message |
| Anonymous caller | Tell an explicit from an implicit deny | Mitigated by status, body and headers; a repeated header can turn a DENY into 503 (RC1-38) |
| Client | Forge `CoSec-Request-Id` into logs | Mitigated: checked for charset and length |
| Control API caller | Internal messages in a 400 `detail` | RC1-39 |
| Tenant admin | Read other documents through explain and simulate | Mitigated by redaction per readable document; RC1-40 for the tenant decided on |

**Conclusion.** The data plane discloses nothing beyond the problem type. The control API's 400 is too talkative
(RC1-39).

#### RC1-38 · Low · A repeated header turns a DENY that reads it into 503

- **Status:** open (fails closed by design).
- **Scenario:** a DENY reads `http.header.x-foo`; an anonymous caller sends `X-Foo` twice. `HttpAttributes.header`
  throws `AmbiguousHeaderException`, an erring DENY makes the decision Indeterminate, and the answer is 503 instead of
  401/403/200, which reveals that such a DENY exists and names its header. It is also a cheap way to make 503s.
- **Evidence:** `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/http/HttpAttributes.kt`,
  `core/engine/src/main/kotlin/me/ahoo/cosec/engine/flat/FlatEvaluator.kt`.
- **Fix:** answer an ambiguous header as 400 `invalid-request` before evaluation, like `SCP-4`, for every header any
  statement of the view reads; or document the trade-off.
- **Regression test:** a `PIP` scenario.

#### RC1-39 · Low · The control API's 400 `detail` carries internal messages

- **Status:** open.
- **Scenario:** `ControlHttp.handle` puts `e.message` of any `IllegalArgumentException`, `SnapshotFormatException` or
  `JacksonException` into the 400 `detail`. `ApplyMode.valueOf` exposes a class name; a stored head that fails to
  decode (one written by a newer version during a rolling upgrade) comes back as a caller-side 400 with the stored
  document's JSON path, including platform and app documents read by simulate without `cosec:read`. Conversely,
  `Instant.parse` throws `DateTimeParseException`, so bad client input becomes a 500.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/api/ControlHttp.kt` (`handle`).
- **Fix:** only messages of the control plane's own request-validation exceptions go into `detail`; a stored
  document that does not decode is a 500 without detail; parse errors of client fields are 400.
- **Regression test:** `ControlHttpTest` cases.

#### RC1-40 · Low · Simulate without a principal decides on tenant `(0)`

- **Status:** open.
- **Scenario:** `simulate` and `explain` authorize `cosec:simulate` on `Tenant(request.tenant)`, but with no
  `principal` the scope resolves to the default tenant, so the decision is made on tenant `(0)`'s document (statements
  redacted). An admin of tenant A gets a decision oracle over tenant `(0)` with caller-chosen time, IP and headers.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/api/ControlPlane.kt` (`simulate`),
  `core/control/src/main/kotlin/me/ahoo/cosec/control/api/Simulator.kt` (`scope`).
- **Fix:** authorize on the tenant the scope resolves to, or refuse an anonymous simulation outside tenant `(0)`.
- **Regression test:** a `CTL` scenario.

### 6. Denial of service

**Trust boundary.** Anonymous and authenticated callers choose paths, headers and `CoSec-*` parameters; tenant
admins choose patterns and conditions in their documents; external attribute providers, the membership provider and
the rate-limit backend can be slow or down.

| Attacker or event | Threat | Verdict |
|---|---|---|
| Anonymous caller | Long paths, many or long segments | Mitigated: 2048 characters, 256 per segment (`PathNormalizer`) |
| Tenant admin | Costly conditions | Mitigated: `CND-2` cost bounds; no regular expressions; `in` and `cidr` are lookups |
| Tenant admin | Costly path patterns; statements that are candidates for every request | RC1-8 |
| Authenticated user | Snapshot loads and eviction with chosen app ids | RC1-7 |
| Slow external attribute | Hold requests | Per-provider timeout, `onMissing` fails closed; non-cooperative providers: RC1-14 |
| Slow or failing membership provider | Hold requests, or no memberships read as no roles | Timeout is 503, never "no roles"; unknown principals not cached (RC1-42) |
| Rate-limit backend failure | Fail open | Non-strict rules are skipped, strict ones are 503, as documented |
| Control API caller | Burn CPU | RC1-41 |

**Conclusion.** The request path bounds what clients send. What tenant admins author is bounded for conditions but
not for patterns (RC1-8), and SPI timeouts rely on cooperative cancellation (RC1-14).

#### RC1-8 · Medium · Path patterns have no cost bound

- **Status:** open.
- **Attacker:** a tenant admin.
- **Scenario:** `HttpPathPatternParser` keeps every `*` as its own token, and nothing bounds a pattern's length or
  token count, nor a document's number of statements, except the 8 MB document size. A DENY bound to `Anyone` with
  resource `http:/{v}` followed by a million `*` and an `a`, with a condition on `resource.var.v`, has no literal
  prefix, so the index makes it a candidate for every path of the tenant. A request to a 255-character path costs
  `tokens × length` steps in `SegmentGlob.accepts`, and with captures allocates a `BooleanArray(tokens × (length + 1))`
  (about 257 MB) and recurses a frame or two per token until `StackOverflowError`. The request itself fails closed
  (an `Error` reaches the host, 500), but the evaluation runs on the event loop and the garbage and stalls hit every
  tenant on the JVM. Evaluation never suspends, so `cosec.pipeline.timeout` does not bound it. The same candidate also
  runs on data-plane instances during the change's shadow window.
- **Evidence:** `core/engine/src/main/kotlin/me/ahoo/cosec/engine/pattern/HttpPathPatternParser.kt` (`tokens`,
  `SegmentGlob`), `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/document/PolicyDocumentCompiler.kt`.
- **Fix:** collapse consecutive `*`; bound tokens per segment, pattern length and statements per document, next to
  RFC 0005 §3.5's condition limits; make `step` iterative.
- **Regression test:** a rule next to `CND-2` ("a pattern over a cost bound does not compile") with a scenario; a unit
  test of the matcher on a long glob.

#### RC1-14 · Low · SPI timeouts are cooperative

- **Status:** open.
- **Scenario:** `withLazyTimeoutOrNull`, used for every SPI call and for `cosec.pipeline.timeout`, waits for the
  cancelled block to finish, as `withTimeoutOrNull` does. `wiki/architecture/extending.md` advises moving a blocking
  client off the event loop with `withContext(myDispatcher)`, which cannot interrupt the call: a provider whose JDBC or
  HTTP call hangs for 30 seconds holds every request for 30 seconds, not its 300 ms timeout. It still answers 503, but
  WebMvc request threads run out first.
- **Evidence:** `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/LazyTimeout.kt`,
  `core/runtime/src/main/kotlin/me/ahoo/cosec/runtime/MembershipResolver.kt`.
- **Fix:** recommend `runInterruptible(dispatcher)` in `extending.md`; or stop waiting for a cancelled SPI call
  after its timeout (answer 503 and let it finish in the background).
- **Regression test:** a `PipelineTest` case with a provider that ignores cancellation, if the second option is taken.

#### RC1-41 · Low · Simulate and explain recompile on every call

- **Status:** open.
- **Scenario:** `Simulator.view` decodes and compiles the platform, tenant and app documents on every call (twice
  with a candidate); RFC 0007 §10.3 caches compiled versions by revision. A holder of `cosec:simulate` can loop calls
  and burn CPU on `Dispatchers.Default`, which the WebFlux data plane also resumes on. Simulated paths skip
  `PathNormalizer`'s limits, and on WebFlux the control routes read the body before checking security, bounded only by
  `spring.codec.max-in-memory-size`.
- **Evidence:** `core/control/src/main/kotlin/me/ahoo/cosec/control/api/Simulator.kt`,
  `host/spring-boot/src/main/kotlin/me/ahoo/cosec/spring/boot/starter/control/CoSecControlRoutesAutoConfiguration.kt`.
- **Fix:** cache compiled documents by key and revision; apply the path limits; check security before reading the
  body.
- **Regression test:** a `SimulatorTest` case that a repeated call does not recompile.

#### RC1-42 · Low · Unknown principals are not cached negatively

- **Status:** open (a known follow-up).
- **Scenario:** a still-valid credential of a deleted principal costs one Redis read and one loader call per request
  (a fill of up to 500 ms, not cancelled with the request). One to one, no amplification, and it needs a valid
  credential.
- **Evidence:** `backends/cocache/src/main/kotlin/me/ahoo/cosec/cache/CoCacheMembershipProvider.kt`.
- **Fix:** a short negative cache, invalidated with the membership cache.
- **Regression test:** a `CoCacheMembershipProvider` test.

### 7. Authentication paths

**Trust boundary.** CoSec verifies its own HMAC JWTs and its API keys; everything else is anonymous. A credential
that does not verify is evaluated as anonymous and a deny answers 401 with the matching problem (RFC 0006 K2).

| Attacker | Threat | Verdict |
|---|---|---|
| Anyone | `alg: none`, algorithm confusion, missing `exp` | Mitigated: `JWT.require(algorithm)`, `exp` required, no `kid` or `jku` |
| Anyone | A delegation token (`act`) read as its subject | Mitigated on every token path (`IDN-4`) |
| Anyone | A refused credential granting more than no credential | Mitigated: evaluated as anonymous, no identity forwarded |
| Key holder | Exceed the key's cap, or use a disabled or expired key | Mitigated for ALLOWs (`IDN-2`); DENYs: RC1-1 |
| Tenant admin | Read a credential header in a condition or rate-limit key | Mitigated for the listed headers (`CND-5`); renamed API key header: RC1-21 |
| Platform operator | A weak secret | RC1-24 |

**Conclusion.** Token and key verification are sound. The findings are hardening of what is trusted after
verification (RC1-22, RC1-25) and of configuration (RC1-21, RC1-24).

#### RC1-21 · Low · `CND-5` does not cover a renamed API key header

- **Status:** fixed in #1164.
- **Scenario:** with `cosec.pipeline.api-key-header: X-Acme-Key`, a tenant admin may read `http.header.x-acme-key`: as
  a rate-limit `key` it writes raw API keys into Redis key names; in a `prefix` condition it is a key-prefix oracle
  through shadow-window counts (PLAUSIBLE).
- **Evidence:** `core/model/src/main/kotlin/me/ahoo/cosec/model/condition/ConditionChecker.kt` (`CREDENTIAL_HEADERS`).
- **Fix:** add the configured header to the compiler's credential headers.
- **Regression test:** a `CND-5` scenario with a renamed header.

#### RC1-22 · Low · A non-string `tenantId` claim becomes the default tenant

- **Status:** fixed in #1164.
- **Scenario:** `Jwts.toPrincipal` reads `tenantId` with `asString()`, which is null for a number; the principal then
  has no tenant and lands in `(0)` with the token's roles, and escapes `revokeSubject` on its real tenant.
- **Evidence:** `extensions/jwt/src/main/kotlin/me/ahoo/cosec/jwt/Jwts.kt`.
- **Fix:** a `tenantId` that is present but not a string is an invalid token.
- **Regression test:** a `JwtTokenVerifierTest` case.

#### RC1-23 · Low · The tenant-switch pattern carries the previous tenant's roles

- **Status:** fixed in #1164.
- **Scenario:** `authentication.md` says to implement `switchTenant(targetTenantId, previousPrincipal)` and issue a
  token for the principal it returns. Wrapping `previousPrincipal` in `SimpleTenantPrincipal`, as the same page
  suggests for tenants, writes tenant A's roles into tenant B's token: an admin in A and viewer in B becomes admin in B.
- **Evidence:** `extensions/login/src/main/kotlin/me/ahoo/cosec/login/token/AbstractSwitchTenantAuthentication.kt`,
  `wiki/integration/authentication.md`.
- **Fix:** document that the returned principal carries the target tenant's memberships only, or have the base class
  drop `roles` and `policies` (or mark the token `cosec.membership: provider`).
- **Regression test:** a login test, if the base class changes.

#### RC1-24 · Low · No minimum JWT secret length

- **Status:** fixed in #1164.
- **Scenario:** `cosecTokenAlgorithm` checks only that the secret is not blank. A short secret can be brute-forced
  offline from any issued token, after which tokens for `(platform)` can be minted.
- **Evidence:** `host/spring-boot/src/main/kotlin/me/ahoo/cosec/spring/boot/starter/jwt/CoSecJwtAutoConfiguration.kt`.
- **Fix:** fail startup below 32, 48 or 64 bytes for HS256, HS384 or HS512 (RFC 7518 §3.2).
- **Regression test:** a starter test.

#### RC1-25 · Low · Social profile fields become signed attributes

- **Status:** fixed in #1164.
- **Scenario:** `DirectSocialUserPrincipalConverter` copies the provider's raw user info (name, company, bio, all
  user-editable) into the token's `attributes`, which conditions read as `subject.attributes.*` and the gateway can
  forward. No attribute name is reserved, so a token can also carry `apiKeyId`, which the docs suggest for targeting
  keys in DENYs.
- **Evidence:** `extensions/social/src/main/kotlin/me/ahoo/cosec/social/DirectSocialUserPrincipalConverter.kt`.
- **Fix:** copy only an allow-list of provider fields, under a prefix; reserve the names CoSec sets.
- **Regression test:** a converter test.

### Checked and found sound

Each line was read end to end by a reviewer; files are relative to the repository root.

- **Tenant from the credential only:** `Pipeline.authorize`, `ScopeResolver.resolve`, `MembershipClaims.tenantOf`.
  There is no tenant parameter; an anonymous subject is always in `(0)` with no roles (`SCP-6`).
- **Scope checks:** app before space, `*` and `:` refused, no fallback to the default space (`ScopeResolver`,
  `SCP-1`, `SCP-2`, `SCP-7`, `SCP-8`); differing non-blank `CoSec-*` values are 400 (`CoSecParameters`,
  `QueryParameters`), header names folded as ASCII.
- **Views and documents:** the tenant document is the scope's; an invalid tenant id is unresolved, never another key
  (`DocumentSnapshotViews`); `SnapshotView.checkScope` refuses a foreign document; tenant documents bind only their own
  tenant's subjects, app documents only roles within their app (`CompiledDocument`, `PolicyDocumentCompiler`).
- **Candidate order and decision:** principal and break-glass lookups keyed by the scope's tenant; `inScope` checks
  app, space and role tenant; a tenant and platform policy with one id are ambiguous, never substituted
  (`CandidateOrder`); every DENY first, an erring DENY is Indeterminate (`FlatEvaluator`).
- **Platform boundary:** only narrows; a missing boundary is Indeterminate; an unreadable tenant document cannot dodge
  it (`FlatEvaluator.withinBoundary`).
- **Memberships:** provider or claims, never mixed; failure, timeout or no answer is 503, never "no roles"; unknown or
  inactive principals refused (`MembershipResolver`, `IDN-3`); the cache key is length-prefixed and the TTL forced
  (`MembershipCache`, `CoSecCacheSpecs`).
- **Path normalization:** `;` parameters removed, decoded dot segments and `\` traversals rejected, malformed escapes
  rejected, length bounds (`PathNormalizer`); `HttpPath` splits as Spring's `PathContainer`.
- **Gateway identity:** stripped before any filter and at the last hop, set only on a permit with a principal and a
  credential, overflow fails closed (`PipelineGatewayFilter`, `IdentityGuard`, `IdentityIssuer`); strict decoding,
  one header only, age and expiry checked, scope re-resolved against the service's host app (`IdentityCodec`,
  `IdentityGate`).
- **Security context:** built from the same resolved scope that was authorized; the WebMvc holder is cleared in
  `finally` (`RequestSecurity`, `SecurityContextHolder`, `ReactiveSecurityContexts`).
- **JWT:** algorithm pinned, `exp` required, `nbf` and `iat` checked, `act` refused on verify and refresh, only the
  verifier decodes (`JwtTokenVerifier`, `Jwts`, `PIP-11`, `IDN-4`); malformed claims in a signed token fail closed.
- **API keys:** SHA-256 lookup by hash (no timing oracle), disabled and expired keys refused, a presented key never
  falls back to the token, store failure is 503, strict format 2 (`ApiKeyAuthenticator`, `CompositeAuthenticator`,
  `ApiKeyCodec`, `RedisApiKeyReader`).
- **`CND-5`:** every condition operand and the rate-limit key resolve through `ConditionChecker.attribute`; header
  names must be ASCII tokens.
- **Control plane:** `TenantIsolation` before every policy check and `Changes.visible` before any state is read
  (`TNT-3`); the document key comes from the path, and `apply` requires a matching kind and owner (`ControlHttp`,
  `Changes`); control checks run on confirmed-current documents and fail closed (`PipelineControlAuthorizer`); the
  authorizer cannot be replaced by an application bean.
- **Built-in control policies:** injected at compile time, not definable by a document, visible to the analysis
  (`CompiledDocument`, `GrantDocuments`).
- **Approvals:** bound to the candidate digest; reset by rebase; 72-hour expiry; author and publisher cannot approve;
  every transition is a compare-and-set on the change, and the head compare-and-set stops a double publish
  (`Changes`, `CoCacheControlStore`); `nomatch` confirmations only from the control plane, bound to the statement and
  policy condition (`Confirmations`).
- **Break-glass:** platform document only, platform-tenant principals only, always with `expiresAt`; last in candidate
  order; expiry checked against the request time with no cleanup needed; the cap checked at propose and publish;
  REQUIRED audit before the change is stored and before the head moves; 503 on use without a REQUIRED listener; a
  permit only break-glass gives is refused to `check` (`CompiledDocument`, `CandidateOrder`, `BreakGlass`, `Changes`,
  `Pipeline`).
- **Shadow windows:** closed only after the minimum duration and samples; `CANDIDATE_ERROR` blocks; skipping needs
  `cosec:skip-shadow` and a reason (`ShadowWindows`, `Changes`).
- **Snapshots:** strict codecs (UTF-8, duplicate keys, unknown fields, exact types, `schema: 2`, no default typing)
  (`SnapshotDocumentCodec`, `PolicyDocumentCodec`, `DocumentNode`, `ConditionJson`); one load per key and installs in
  order; a key seen and then missing is LOST and fails closed; undecodable or uncompilable documents installed as
  failed; `peek` does no I/O (`SnapshotSource`); `platformRequired` in the starter and the control plane; store-of-record
  caches pinned after customizers (`pinPolicySnapshot`, `CoSecCacheSpecs`).
- **problem+json:** fixed members, no message on 500, problem type from authentication only, so explicit and implicit
  denies match (`ProblemEncoder`, `StatusMapping`); the adapters write only the outcome's headers and body.
- **Rate limits:** obligations only after a permit and the boundary; per-document counter ids; `strictFailure` as
  documented (`Pipeline.obligations`, `FlatEvaluator`).
