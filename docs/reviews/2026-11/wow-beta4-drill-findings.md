# Wow on CoSec 8.0.0-beta.4: the drill

Draft pull request: https://github.com/Ahoo-Wang/Wow/pull/6537 (branch `claude/cosec-8-beta4-f3d712`, cut from `origin/main` at `38d774508e`, 2026-11-19).

Method: only the release notes of v8.0.0-beta.4, the page "Upgrading Between 8.0 Previews" (section "From 8.0.0-beta.3"), the pages `policies/testing` and the published artifacts (POMs, and the `-sources.jar` of `cosec-testkit` and `cosec-webflux` from Maven Central, which I read for signatures). I did not open CoSec's repository on this machine, and I did not read the sibling notes in the shared folder, because they come from the CoSec side.

## What the upgrade took

The version moved from `8.0.0-beta.3` to `8.0.0-beta.4` in `gradle/libs.versions.toml`, and every artifact resolved from Maven Central with nothing in `mavenLocal` for CoSec 8 (the only CoSec in `~/.m2` is `cosec-api` 6.1.0). Of the nine modules that compile or test against CoSec, eight needed no change at all. One test failed, and one test dependency had to be added. About 45 minutes of work, most of it Gradle runs and a shared machine's load, not searching.

Modules run one at a time with `nice -n 15 ./gradlew --no-daemon --max-workers=2 :<module>:check`: `:cosec` (51 tests), `:spring-boot`, `:ops-server`, `:view-store-server`, `:analytics-catalog-server`, `:eshop-ordering-server`, `:eshop-inventory-server`. The basket and catalog servers have no CoSec test; they only declare the dependencies, and the whole build runs on the PR's CI.

PipelineFixture: I read it against Wow's `CoSecPipeline` test fixture and did not convert it. For a new test suite it would be the right start.

## What the docs got wrong or left out

1. **Upgrade notes, PIP-27, and the release notes' "Security fixes".** They say a hand-made context "reads as no context", but not what a test that depends on it will look like. In Wow it did not fail loudly: the code under test treats "no context" as "a command without a request of its own" (a saga's) and allows it, so a test that expected a denial saw `Allowed`. Another application whose "no context" means "anonymous" would show a 401 and look like a different bug. A user needed one sentence: "a test fails with a missing or anonymous caller, or, where your code lets an absent context through, a permit it should not give; search your tests for `SecurityContext.KEY`, `mockk<SecurityContext>` and objects implementing `SecurityContext`". The entry's grep advice exists for documents but not for this.
2. **Testing your application: the dependency lines.** The page says what to call but not what to add. A user needs: `cosec-testkit` for `PermittedRequest`, `PipelineFixture` and `IdentityHeader`; `cosec-webflux` or `cosec-webmvc` for `CoSecTestBindings`, which is in the production jar, not in the kit (I only learned this by reading the POMs and the sources jar); and that without the BOM the version has to be given. The page's example has no imports either, so which of the three `testing` packages is which has to be guessed from the text.
3. **Testing your application: a suspend function under test.** Every sample binds a `Mono` (`withSecurityContext(mono, context)`) or an exchange. An application in Kotlin coroutines (as Wow is) needs `mono { suspendFunction() }` around it, and that the coroutine then sees the context. One line would do.
4. **Testing your application / `IdentityHeader`: a header is good for a minute.** The class says so in its KDoc ("make a header per request"), but neither the upgrade notes nor the testing page do, and the release notes only say it "writes the header a gateway forwards". Wow's tests keep a header in a value used for many requests (`val operator = signedIn(…)`), which works only because those tests finish in seconds. A user with a longer test, or one that waits with `eventually`, gets a 401 `token-expired` that looks like a defect in the service.
5. **Upgrade notes, the entry for `PermittedRequest.withToken` (IDN-27).** The testing page's table says `withToken(token, verifier, revocations)`; the upgrade notes say its default is gone and name `RevocationReader.NONE`. Fine, but the testing page does not repeat what to pass in a test, and `PipelineFixture.Principal` is not described in the page at all, only its use (`fixture.authorization(alice)`); its fields (`tenant`, `roles` as `role` or `role@space`, `policies`, `app`, `attributes`) are in the KDoc only.
6. **Release notes, "Known issues": "Every `@ExperimentalCoSecApi` declaration stays experimental in 8.0, the test kit and the test bindings included."** It does not say what that costs a user: every test file that uses the kit or the bindings needs `@OptIn(ExperimentalCoSecApi::class)`, and a project that does not opt in gets a compiler warning (an error where warnings are errors). Wow already opted in elsewhere, so it cost one line per file; the page that introduces the entries could show the annotation in its first sample.
7. **Release notes and upgrade notes: how to pick the version of the image.** The notes say the image changes (probes, management port, merged defaults) and that the library changes, but not whether a service on library beta.4 can sit behind a gateway image of an older beta. Wow runs library beta.3 behind an image of beta.1 and nothing in the notes says whether that is supported. I could not tell and did not test it.

## What in CoSec itself was awkward

1. **A context that cannot be read is indistinguishable from no context.** PIP-27 is a good rule, but the readers answer `null` or the failure of an unbound context for a refused context, the same as for a request that has none. An application that has to decide "no context" (Wow's saga commands carry none and are allowed) cannot tell "no request" from "a context CoSec refused". It turns a fail-closed rule into a fail-open one in that code. A reader that distinguishes the two, or a log line at the first refusal ("a context not made by the pipeline was ignored"), would have shown it at once.
2. **`CoSecTestBindings` ships in the production jars** (`cosec-webflux` and `cosec-webmvc`, package `…webflux.testing`), while the contexts it needs come from `cosec-testkit`, a different artifact it does not depend on. Its own KDoc says an application never imports it. A user adds a test-only class to every deployed image's classpath and still needs a second artifact to make an argument for it. A `cosec-webflux-testing` artifact, or having `cosec-testkit` carry the bindings, would be cleaner.
3. **`CoSecTestBindings.withSecurityContext` takes a `Mono`**, no suspend or blocking form. See item 3 above; Wow wrote a `mono { }` wrapper and `.block()`.
4. **`PipelineFixture` takes no authenticator.** Its principals are issued tokens, so a test suite that already has its own token convention, or one that sends a real `Authorization` header from a `WebTestClient` built elsewhere, has to go through `fixture.authorization(principal)` for each request. A `PipelineFixture.of(…, authenticator = …)` would let an existing suite adopt the fixture without rewriting its requests.
5. **`IdentityHeader.forSubject` takes `roles: Set<String>`** where Wow's equivalent took a `Collection` with duplicates removed; a vararg role list needs `.toSet()` at every call. Minor.
6. **`IdentityHeader.forSubject` writes a made-up session** (its own KDoc says so: an id from the random generator, generation 1). It is honest, and the KDoc says to use `withToken` when it matters; but a service that issues from the session behind a gateway (a tenant switch) then fails in a way that points at the service. Not something Wow hits.
7. **`PermittedRequest.forSubject` runs `runBlocking` inside** and makes a pipeline on every call (`PermittingHost.pipeline(...)`): a test that makes a hundred contexts builds a hundred pipelines. I did not measure it; Wow's suite makes about ten.

## Wow's own CI on the pull request

**Final result: green.** Draft pull request 6537, https://github.com/Ahoo-Wang/Wow/pull/6537, run https://github.com/Ahoo-Wang/Wow/actions/runs/44554693988: after re-running the two failed jobs, the run completed successfully at 16:13 UTC (no job failed; 20 skipped by the run's own scope rules; the coordinator counts 71 succeeded across the run's attempts). No Wow code or CoSec change was needed for the three failures.

What the three failures were: Check (apps) and View store contract failed at about 15:27 to 15:28 UTC on 2026-11-19 (49 seconds each, before any test) with "Could not find me.ahoo.cosec:cosec-spring-boot:8.0.0-beta.4" and "Could not find me.ahoo.cosec:cosec-webflux:8.0.0-beta.4"; ci-gate is only their aggregate. Their re-run at 16:03 UTC passed. Both passed on `main` at 38d774508e with beta.3.

Where Wow's CI resolves from: `build.gradle.kts` (`allprojects { repositories { mavenLocal(); mavenCentral() } }`) names exactly two repositories, and `mavenLocal()` is empty on a runner, so the dependency came from Maven Central itself, straight at `repo.maven.apache.org`. There is no mirror, proxy or GitHub Packages in the resolution path (the one `maven.pkg.github.com` line in the build is for publishing). The only cache is Gradle's own (`setup-gradle`, read-only on a pull request, restored from `main`'s).

Timing: the GitHub release says 14:33 UTC; the `cosec-webflux` 8.0.0-beta.4 POM on Maven Central now reports `Last-Modified: 14:54:35 GMT`, and the coordinator reports it listed from 15:02 UTC. The failing jobs therefore asked 25 to 35 minutes after Central had the file, so this is not a mirror lag we can name. The job's own cleanup step reported removing a missing-artifact record ("gradle-forget-missing: removed .../module-artifact.bin"), and the error carries no "Searched in" list, which fits a negative answer remembered somewhere between Gradle and Central (an edge of Central's CDN, or Gradle's cache) rather than a missing file. I could not tell which.

For CoSec's release notes, a finding: a user who upgrades within the first hour of a release may see "Could not find" for the new version from a runner, even though the file is on Central; the note should say so and say that a re-run fixes it, and that the release page should be linked only after Central lists every artifact of the BOM (the release notes were out at 14:33, about 20 to 30 minutes before the files were).
