## 1. The host that believes a stated identity

What I read: `GatewayModeTrust`, `CoSecGatewayModeAutoConfiguration`, `CoSecIdentityGuardAutoConfiguration`,
`ConditionalOnIdentityGate`, `CoSecSwitches` (UB-1), `CoSecPipelineWebAutoConfiguration` (the gate check and the WebFlux
filter), `ApplicationPort`, `ControlServicePort`, `ControlServiceListener`, `ServicePortFilter`, `ControlPeer`,
`CoSecControlRoutesAutoConfiguration`, `ControlProfile`, `ControlRoutes`, `ControlHttp`, `ControlHttpSupport.verbOf`,
`PathSegments.unescaped`, `DocumentRoutes`, `ChangeRoutes`, `Operator`, `ChangeOrigin`, `OriginJson`, `IdentityGate`,
`platform/control-server/.../application.yaml`, `k8s/control/*` and the ports section of `wiki/operations/deployment.md`.

### Checked and found sound (so you need not re-read them)

- **`forwarded-identity` spelling.** `OnIdentityGate` and `GatewayModeTrust.wiredByProperty` compare the string
  `forwarded-identity` exactly (ignoring case), while the typed `PipelineProperties.Caller` binds `FORWARDED_IDENTITY`,
  `forwarded_identity` and so on. That would wire no gate yet make the guard believe there is one. It is closed by UB-1:
  `CoSecSwitches` lists `cosec.pipeline.caller` with exactly `credential` and `forwarded-identity` and
  `CoSecPropertyCheckAutoConfiguration` fails startup otherwise. Residual: that check reads `environment.getProperty`, the
  conditions read the same, so they agree. I did not read when `CoSecPropertyCheckAutoConfiguration` runs relative to
  `cosec.enabled=false`.
- **The boundary statement.** `requireBoundaryStated` reads through `Binder` and accepts `true` in any case only; the
  guard bean is `StartupTask.OnCreation` in `CoSecGatewayModeAutoConfiguration`, so an application's own `IdentityGate`
  does not skip it (`cosecWebGateTrustCheck` covers the case where the properties did not wire the gate).
  `ControlServicePort.check` refuses `only-gateway-can-reach` beside a service port.
- **`STA-6`** (hidden-method filter) is checked by property, by bean and by `FilterRegistrationBean`: the three ways I could
  think of are covered. Not covered, and not claimed: a `WebFilter` of the application that rewrites the method itself.
- **Profile and route parse the same segment.** `ControlProfile.admits` and `DocumentRoutes`/`ChangeRoutes` call the same
  `verbOf` on the same raw segment and the same `unescaped`, `ControlRoutes.route` rejects `//`, a trailing `/` and a leaf
  with a tail before the profile is asked. I tried `tenant%3Aacme:apply`, `%70latform:apply`, `app%3Ax:apply`, a `;`
  matrix parameter and an encoded base path: each is a 404 or a 400, never a route the profile would not serve.
  The `relative()` of the adapter removes the base from the raw path, so `/cosec/control/%76%31/...` is no route.
- **The record's peer.** `ControlPeer` reads the Reactor Netty channel's remote address beneath any `ServerHttpRequestDecorator`
  or forwarded-header rewrite, and says nothing (null) where it cannot. A caller cannot choose it. `ChangeOrigin.asserted`
  is `identity != null`, which only the `IdentityGate` sets from the header, so a request verified by a credential is never
  recorded as asserted, nor the reverse.
- **K8s.** Three NetworkPolicies, one per port, additive and port-specific; the management port is published by no Service;
  the image exposes only `health,prometheus`; `replicas: 1` with `Recreate`.
- **Facade path text.** `LocalControlService.key` and `segment` percent-encode every byte but the unreserved ones, so an id
  with `:` or `/` cannot add a verb or a segment, and `ControlProfile.SERVICE` is the one definition the port and the facade
  share (CTL-58, CTL-65).

### R3-1 (S2): the service listener inherits nothing of the application's server

`ControlServiceListener.start` builds `HttpServer.create().port(port)...bindNow()`: no bind address, no TLS, no idle or
request timeouts, none of the application's `NettyServerCustomizer`s. `ControlServicePort.check` refuses a service port equal
to `server.port` or `management.server.port`, a missing statement and `http.enabled=false`, and nothing else.

Trigger: an operator who makes `only-trusted-callers-can-reach` true by mutual TLS (one of the three ways
`GatewayModeTrust.requireBoundaryStated` names) writes `server.ssl.client-auth=need` and `server.address=10.0.0.5`, and
leaves `cosec.control.http.service-port=8082` (the control image's default). The application's port is mTLS on one
interface; 8082 is plain HTTP on every interface, believing any `CoSec-Identity` header and serving the tenant documents
and the change flow. The statement covers the host, not a port, so startup passes. With the shipped NetworkPolicies this is
only reachable from the services' own namespace, so it is S2 (an insider, or an operator who relied on TLS) and not S1.
The same missing configuration means no idle timeout on a port that admits services only (a stalled connection holds a
channel until `stop()` closes the group).
Fix shape: `ControlServicePort.check` fails when `server.ssl.enabled`, `server.address` or `server.netty.*` is written
beside a service port (say what to do), or the listener takes the application's `HttpServer` customization.
Did not read: `server.http2`, `server.netty.*` handling in the starter at all, `StartupSummary`.

### R3-2 (S3): on a `forwarded-identity` host no `http:` decision runs

`CoSecGatewayModeAutoConfiguration.cosecIdentityGate` is `@Primary`, and `cosecPipelineWebFilter` takes `RequestGate`,
so on the control host (`mode=enforce`, `caller=forwarded-identity`) the web adapter's gate is `IdentityGate`, which only
admits the stated identity (`StatusMapping.asserted`). `Pipeline.evaluate` (route resolution, the `http:<METHOD>` decision,
the blacklist rule at that step, rate limit obligations, decision listeners, audit) does not run for control requests; the
control plane's `PipelineControlAuthorizer` decides each control action instead, which is the decision that matters.
On 8080 the gateway made the `http:` decision upstream; on the service port nothing did.
Consequences: (a) a rate limit rule on a control route (the code comments in `ControlRoutes` say a rule on `/simulate`
"covers every request that reaches one") holds only behind the gateway, never on the service port or the facade;
(b) no decision event or audit record for a service-port request at that level (the change events are the record);
(c) `wiki/operations/deployment.md` says "the application port is decided by the pipeline, so a kubelet is refused there":
on this host I read an anonymous request proceed to a 404 (`IdentityGate`: no header, "proceeds as anonymous"), not a
refusal. I did not run it.
Not exploitable by itself. It is the reason a service principal's volume is unbounded: see R3-3 and R3-4. Worth one sentence
in `deployment.md#control-plane-ports` and in `CTL-58`'s statement.

### R3-5 (S4): `ServicePortFilter` lets the whole base path through

The filter admits `path == basePath` or `startsWith("$basePath/")` on the raw path, but the control routes are
`$basePath/v1/**`. Another route of the application under the base path, or a catch-all handler (a static-resource `/**`,
an SPA fallback), answers on the service port. Nothing in CoSec's own code does; it is for an application that embeds the
control plane (IAM) and has such a handler. Matching `apiRootOf` closes it.

### R3-6 (S4): what a stated identity can say that the record shows as plain fields

- `IdentityGate.security` sets `breakGlass = identity.credential.method == JWT`, with the comment "the gateway names a
  credential `jwt` only for CoSec's own token". On the service port, and in `IdentityHeader.write` (public,
  `@ExperimentalCoSecApi`), the caller writes the method. A service can therefore state `jwt` and be break-glass capable
  (an active break-glass binding of the principal it states grants to it). The service profile serves no `/break-glass`,
  and a service can already state any roles, so nothing is gained that the network statement does not already concede, but
  the comment is untrue on this port and the deployment page says "a stated API key never approves where a stated token
  does", which is the same property seen from the other side.
- `ChangeOrigin.via.requestId` is the `CoSec-Request-Id` the caller chose (`RequestIds.isAcceptable`), recorded with
  `asserted=true`. Fine for a trace id; an audit reader should not take it as the host's.
- `via.method`/`credential` of an asserted identity are the caller's words. The record says so with `asserted`; the Kafka
  schema and `wiki` should say that `via` of an `asserted:true` event is not evidence. I did not read the event JSON schema.

### R3-7 (S4): the Servlet stack has no port rule and no peer

`CoSecControlRoutesAutoConfiguration.WebMvc` registers the routes with `ServletPredicates.path("$base/**")` only and builds
`ControlHttpRequest` without a peer. CTL-69 (no CoSec route on the management port) is enforced by `ApplicationPort` on
WebFlux only. Whether Boot's servlet management child context inherits `RouterFunction` beans (I believe
`RouterFunctionMapping` does not look in ancestors by default) I did not verify; and on WebMvc `peer` is always null, so the
record says nothing there (CTL-57 is honest about this: null, never a caller's value). Check that `deployment.md` says the
port rule is WebFlux-only.

### Ports, paths and listings: the question asked

Is there a port, path, method override, encoded path or listing through which the operators' profile, the platform
document, an approval or break-glass is reachable where it should not be? I found none:
the profile is decided by the socket's local port, which a caller cannot choose, against `boundPort` of the listener it
connected to; the service profile admits `GET|POST /changes`, `GET /documents`, tenant/app document reads and tenant
`:apply`, and by id a change is served only after its record is read (`ChangeRoutes.served`), with the same 404 whether the
change does not exist, may not be read, or is the platform's. Reading `served` calls `plane.get` (authorized as the caller)
before the method check, so a `GET` on `/changes/{id}:publish` on the service profile still costs one read; not a leak.

## 2. The SDK facade (`ControlService`, `LocalControlService`, `ControlCaller`, `IdentityHeader`, CTL-65)

Read: all four files, `ControlHttp.handle`, `Operator.of`, `ControlServiceConfiguration`, `WrittenIdentity`.

- Every `LocalControlService` call goes through `ControlHttp(plane, SERVICE).handle(request, security)`, so it is routed,
  profiled, authorized (`PipelineControlAuthorizer` as the operator) and recorded by the code the port uses. I found no call
  that reaches `ControlPlane` another way. `inProcess = true` is set by the facade only: it is a constructor argument of an
  `@InternalCoSecApi` class the adapters never set from a request.
- `ControlCaller.of(context)` requires `RequestSecurity.of(context)` non-null (a context CoSec made, PIP-29); an anonymous
  context has `principal == null` and `ControlHttp` answers 401 before any route. `ControlCaller.service(principal, roles)`
  states a principal and roles with no allow-list: an application that passes a request-controlled string as `principal`
  gives the caller any principal of the platform tenant, a platform administrator included. The KDoc says the control plane
  believes in-process code (it holds the store's write account anyway), which is true of the code, not of a string the code
  forwards. One sentence in `wiki/integration/checks.md#changing-policies-from-your-code`: "never build a service caller from
  request input".
- The service identity is `Method.API_KEY`, tenant `platform`, 30 s, run through `IdentityGate.admit`, so expiry, age,
  tenant and scope hold as for a header. `breakGlass` is false for it. Good.
- `IdentityHeader.write` writes any `Identity`, `jwt` included (see R3-6).
Did not read: `ControlService`'s KDoc against the wiki, the TypeScript or Kotlin client of a remote control plane (not
shipped yet per the ledger).

## 3. The listings (`DocumentListing`, CTL-68; open-change listing)

Read: `DocumentListing`, `DocumentPage`, `SharedRead`, `ControlProfile.admitsListing/admitsChange`, `ChangeRoutes.listing`,
`ChangeListings`, `DefaultControlPlane.changes`.

What a caller learns: with `cosec:read` on `doc/tenant` a platform operator learns every tenant id; a tenant's principal
learns its own document's existence only if it may read it; a tenant principal asking `app`, and anyone with no layer read
and no own document, gets the same 403 with no detail; `TenantIsolation` filters a tenant's layer permit to its own key.
So a listing never shows a key that `TenantIsolation` would refuse by id. By design, a layer read names documents that the
caller may not read; the KDoc says so. A change is listed only if `visible` would show it (`TenantIsolation`, then author,
then a READ decision cached per document per call); the service profile adds `admitsChange`.

### R3-3 (S2, availability): the state listing has no layer decision and can scan everything

`DocumentListing.list` decides the layer (`decideLayer`) before it touches the store. `ChangeListings.list` does not: a
caller with no permission at all reaches `byState`, which asks the store for pages (`store.changes(state, cursor, limit)`)
and filters each with `visible`, looping `while (found.size <= limit)` until the store's pages run out. For a platform
principal that reads nothing (a service principal bound to no read policy, which the deployment page's own scenario uses),
every open change of every tenant is listed and one READ decision is made per distinct document: O(open changes) store reads
and O(documents) decisions per call, answered with an empty page. For a tenant principal `TenantIsolation` filters inside the
store before reading, but the state's set is still walked.
Trigger: `GET /changes?state=SHADOWING&limit=1` as a principal with no `cosec:read`, in a loop, on 8080 (the gateway's
`http:GET` rule is the only gate) or on 8082 (R3-2: none).
Fix shape: one layer-level READ decision first (as `DocumentListing`), or a per-call bound on documents decided.
Did not read: `ControlStore.changes` of `cosec-cocache` (how the state set is walked), so I do not know whether the
filter is applied before or after the read per entry.

### R3-4 (S3): the own-document answer is a full scan

For a tenant principal (`DENY` on the layer, own document readable) `list` calls `documents.read()` (the shared sorted list,
fine) then filters the whole list: `ownerOf(it)`, `it.toString()` twice per key, and `shown(it)`, for a one-element answer.
At 10,000 to 50,000 keys that is tens of thousands of string allocations per call, for every tenant member who may read its
own document (the SaaS target). A binary search of the sorted list for `own` answers it. The platform path also re-filters
and `toString`s the whole list per page (paging 50,000 keys at 50 is 1,000 passes), correct but quadratic; `after` could be
a binary search too.

## 4. The shadow path (CTL-10 acknowledgement, CTL-12 compile on sight, OBS-8, CTL-47)

Read: `ShadowWindows` (`look`, `acknowledgement`), `ShadowLook`, `ShadowOptions`, `Staging.shadowed`, `InstanceStatuses`,
`SharedRead`, `ShadowReporter`, `CompileOnSight`, `CachingCandidateSource`, `StagedDocuments` (first 120 lines),
`InstanceStatus`, `ShadowCodec.encodeStatuses/decodeStatuses`, `CoCacheShadowReports` (write, list, statuses),
`platform/control-server/.../application.yaml`.

How a window passes: `vanished` is empty, every instance with a status in the last minute that `shadows` lists the window,
`elapsed >= 15 min` and at least 1,000 effective samples; a `CANDIDATE_ERROR` from any instance blocks at once; at 24 h it
closes insufficient. I could not make it pass with an instance that is live, shadowing and has not compiled the candidate.
Compile on sight cannot be starved by one bad candidate (it goes to the end of the queue), a read that fails is retried and
never cached, and an instance that holds no staged list acknowledges nothing (`windows == null`), so it holds windows open.
The control image sets `cosec.authorization.shadow.enabled=false`, so it writes no status and is not waited for; I checked
that is not "a live instance that never acknowledges".

### R3-9 (S3): what the acknowledgement counts as "live"

- **One bad status stops every window.** `CoCacheShadowReports.statuses()` `check`s that every listed id is valid and that
  the status under `<instance>` is that instance's, and decodes every status; any failure fails the whole read, and
  `Staging.shadowed` turns it into 503 for each window (`the shadow reports ... could not be read`). Fail closed is the
  intent. The cost: one instance writing a status the codec refuses (a `shadows` that is not a boolean, a `formatLevel` of
  0, a corrupt value) holds every window of every document until that status expires (1 minute) or is overwritten; a
  crash-looping version that writes a bad one every ten seconds holds them continuously. A status an older control host
  cannot decode (a newer member the codec refuses rather than ignores) does the same during a rolling upgrade.
  Fix shape: skip and count a status that does not decode, but treat its instance as waiting (not live-and-fine), so the
  window still cannot pass on it and the others are still read.
- **"Live" is a status written through the same Redis path.** `statuses()` keeps those with `at` within one minute
  (`STATUS_TTL`). An instance partitioned from Redis for over a minute still serves from its resident snapshots (the lag
  bound applies only to a tenant that fails closed); it drops out of `live`, and a window opened during the partition is
  never seen by it, never acknowledged and never waited for. When it reconnects it installs the published revision having
  compared nothing. The wiki says "every live instance"; that is what live means. Worth one sentence in
  `wiki/policies/testing.md` and `troubleshooting.md`.
- **A new instance is invisible until its first status** (and the control host reads at most every 5 s). A window can close
  in that gap without it. With a 15-minute minimum this is a narrow window; I did not read whether readiness waits for the
  first status.
- An instance with shadowing switched off (`cosec.authorization.shadow.enabled=false`) writes no status at all and is never
  waited for, but it still decides requests. The gateway image's default is not off, so this is a choice; the pages should
  say that a fleet with it off in one deployment is not covered by any window.

### R3-10 (S3): no freshness on a report

`ShadowWindows.look` reads each instance's cumulative report and checks identity, uniqueness, sign and that listed
reporters are present; it never looks at how old a report is (`ShadowReport` carries no time that I read). Meanwhile
`acknowledgement` drops an instance whose status is over a minute old. So an instance whose reporter coroutine stalls (a
cycle is `refresh` + compile on sight (budget one interval) + a write per window + the status, sequentially; a slow Redis
with many open windows can pass a minute) keeps serving, stops being "live", and its last report, hours old, stays in the
total. The window passes on evidence that omits that instance's recent traffic, which is exactly the traffic the
`vanished` rule exists to wait for (CTL-56). Trigger: 200 windows open, Redis writes at 300 ms: a cycle is 60 s plus; the
status is written last and ages out. Fix shape: write the status first, or write it from its own loop, so liveness does not
depend on the report cycle; and carry a report time and refuse a window to pass on a live instance whose report is older
than a few intervals.

### R3-11 (S3): the size of a status

`InstanceStatus.documents` holds every resident document (`key`, `revision`, `lagMillis`), encoded as a JSON object per
instance. At the default `cosec.authorization.snapshot.max-tenants` of 16,384 that is on the order of 1 to 2 MB per
instance, written every 10 s by each, and `statuses()` reads all of them (batches of 64) each time the 5-second shared read
expires, while any change is shadowing (the maintenance pass) or anyone reads a shadowing change (`GET /changes/{id}` adds
the acknowledgement). 20 instances is tens of MB per read. Not new in #1794 (`propagation` already read it), but CTL-10 now
puts the read in the window's closing path, and the 1-minute liveness of R3-10 rides on writing it in time. I did not
measure; the number is from the key and revision widths. Ask whether `windows`/`shadows` should live in a status of their
own, small, apart from `documents`.

### What I could not break, as asked

- **A window that passes without every shadowing instance having compared:** only through R3-9 (partition, first-status gap)
  and R3-10 (stalled reporter); not through an instance that is live and silent.
- **A state in which no window can ever pass:** (a) one status that does not decode (R3-9, until it expires); (b) a live
  `shadows=true` instance that cannot read the staged list or compile the candidate (an older version in a rolling
  upgrade, documented in `troubleshooting.md`): every window closes insufficient at 24 h, none passes; (c) an instance whose
  id collides with another's (two replicas sharing an instance id): `look` `check`s "reported more than once" and throws, a
  503 for every window it touches. I did not read `ShadowInstanceId` to see how the id is made on a host with no
  `HOSTNAME`.

## 5. `ChangeListeners` and its lanes (CTL-66)

Read: `ChangeListeners`, `ChangeListenerLane`, `ChangeEvent`, `ChangeLifecycle.audit`, `Approvals.approve/abandon`,
`ChangeListenersConfiguration`, `ChangeListenerMeters`. Not read: `ChangeEventSize`, `KafkaChangeListener`,
`ControlMetersConfiguration`, `Proposals`/`Publishing` beyond their `audit` call sites.

Sound: a gated step with a REQUIRED listener queues to every REQUIRED lane and waits, together, within `requiredTimeout`; a
timeout or failure is a 503 before the step writes, and a cancelled `done` stops a not-yet-started delivery. A gated step
that arrives while draining is refused before it takes effect. A non-gated event for a REQUIRED lane with no room waits up
to `requiredTimeout`, is then counted (`lost`) and logged at ERROR. BEST_EFFORT drops the incoming event, counted, so a
consumer sees a gap, never a reorder. The queues are bounded (`maxMemory/32`, shared equally). `drain` is a bean
`destroyMethod`, so it runs after the web servers' graceful stop.

### R3-8 (S3): a REQUIRED listener that fails loses a non-gated event, uncounted

`ChangeListenerLane.deliver` runs a REQUIRED listener under `withTimeoutOrNull(callTimeout)`; on a throw or a timeout it
calls `failed(entry, cause)`, which, for an entry with no `done` (every non-gated event), only logs at WARN. Nothing
increments `lostCount`; `lose()` is called only from `ChangeListeners.publish` for a queue that stayed full. The KDoc of
`ChangeListeners` says a full queue "is the one way a REQUIRED listener misses an event", and
`cosec.control.listener.lost` is documented "alert on any". With Kafka failing, `APPROVED`, `REJECTED`, `PROPOSED`,
`SHADOW_STARTED`, `SHADOW_SKIPPED`, `REBASED`, `ABANDONED` (not break-glass), `PUBLISHED` and `FAILED` are lost one by one
with a WARN each, no counter and no gauge moving (the queue drains: each failure removes its entry), while a gated
`PUBLISHING` correctly 503s. An auditor reading the stream sees a `PUBLISHING` with no `APPROVED` before it, and the
alert that was meant to say so is silent.
Trigger: stop the Kafka brokers with `cosec.control.audit.kafka.delivery=required`, approve a change; the response is 200,
the log has one WARN, `lost` is 0.
Fix shape: count it in `failed` (the same `lost` for a REQUIRED lane, a `failed` counter for BEST_EFFORT) and log REQUIRED
at ERROR as the full-queue case does; correct the KDoc and the meter description.

### R3-12 (S4): ordering under a full budget

`put` suspends in `freed.first { it != seen }` until `reserve(bytes)` fits, and `reserve` admits any event that fits.
So with a lane near its budget a large event waiting for room can be overtaken by a smaller event queued later, which fits.
The KDoc promises a change's events "in the order its steps wrote them". Two steps of one change are ordered by the store,
and the first's request is still waiting in `put` (up to 5 s) while the second step's request, which does not wait for it,
publishes; so the second reaches the lane first. Only under near-full queues, where loss is the bigger problem; a consumer
that orders by `time` and the record (as the KDoc already tells it to across instances) is unaffected. A ticket per lane
(`put` takes its place in line, then waits) would keep the promise.

### R3-13 (S4): a recorded event for a step that did not happen

By design a gated event is recorded before the step writes, and "its event is not delivered after all if it had not
started". What remains: (a) with two REQUIRED listeners, the first records, the second times out, the step is 503 and the
first holds an event of a step that never took effect; (b) `Approvals.approve` for break-glass records
`BREAK_GLASS_APPROVED` and then runs `transition`, whose lambda throws `CONFLICT` when the candidate changed since the
check: a recorded approval that did not happen; (c) a listener that timed out may still complete the send afterwards (the
cancelled call can have reached Kafka). All are in the safe direction (over-reporting) but a consumer must reconcile each
event with the change record, and the wiki's page on the event stream should say it.
