### Findings (in the order they were written; the index above orders them)

#### R2C-1 (S3, S) The REFERENCES finding names every referrer, with no bound
- **Module / symbol:** `core/control`, `lifecycle/RemovedReferences.check` (message built at the `Finding("REFERENCES", …)` line) and `lifecycle/PublishRules.referenced`.
- **What is wrong:** when a platform or app change removes a policy that other documents refer to, the finding's message is `"[policy] is referred to by ${referrers.sorted()}"`: every referrer key, sorted. At the target (tens of thousands of tenants, `base-access` bound by all of them) that is a string of tens of thousands of keys (about 0.8–1 MB at 50,000), where every other long message in the module is capped (`RouteFindings` has `SHOWN`). The finding is stored in the change record, which every state transition rewrites whole, and is returned by every `GET` of the change.
- **Evidence:** `RemovedReferences.kt` (the `findings += Finding("REFERENCES", …, "… referred to by ${referrers.sorted()}")`), `PublishRules.referenced`, `Finding.message` is an uncapped `String`; `ReferencedPolicies.blocking` returns the full set (`.keys` of the group). `saas-scale-control-plane.md` §2 measured the *read* cost of this refusal but not the size of what it produces.
- **Same in `cosec-migrate`:** `DocumentRestorer.restore` (`"… no longer defines what other documents refer to: ${outcome.referrers}"`) and `DocumentPublisher.write` (`"$key is referred to: ${outcome.referrers}."`) print the whole policy-to-referrers map in an exception message.
- **Breaking after RC:** no (text of a finding; an added structured count is additive).
- **Fix:** name the first N (say 20) and the count, as `RouteFindings` does; one helper for the three places. S.

#### R2C-2 (S2, M) The open-change list is one value everyone rewrites, and its failure after a landed write is thrown
- **Module / symbol:** `backends/cocache` `CoCacheControlStore.putChange` / `updateList` / `openChanges`, key `cosec:control:list:open-changes` (`Store<String, Map<String, Instant>>`); port: `ControlStore.openChanges(): List<ChangeRequest>`.
- **What is wrong (two things).**
  1. The list of open changes is one JSON map rewritten whole by read-modify-`putIfMatch` (16 attempts) at every first write of a change and at every write that makes one terminal. It is the shape PR B removed for referrers and the document list; `saas-referrers-design.md` left it ("open changes stay as they are, as they are few"). At the target they are not few: an onboarding wave is one change per tenant (tens of thousands), a tenant administrator's every edit is one more. Each rewrite moves the whole map (about 45 B an open change), and every concurrent proposal or publish of every tenant contends on this one value: with 16 attempts and no backoff, the failure the SaaS measurement showed for `refs` (half of 50 concurrent publishes) applies to *creating a change*.
  2. `putChange` writes the change, and only then, when the change is terminal, calls `updateList(OPEN_CHANGES) { it - id }`. When that throws (`IllegalStateException` after 16 attempts, or an unreadable list), `putChange` throws although the terminal state is already stored. Its KDoc and `openChanges` say a failed removal is made up later ("drops it the next time it is read"), but nothing catches it. The caller sees a failed write of a change that is `PUBLISHED`/`ABANDONED`/`REJECTED`: `afterHead` turns it into "could not be settled; publishing it again settles it", and a retry then finds the state already terminal (`settledPublished` reads it as "another call settled it" and returns without the audit event).
- **Evidence:** `CoCacheControlStore.kt` `putChange` (the `if (written && change.state.terminal) { updateList(...) }` with no try/catch) and `updateList` (throws after `MAX_LIST_ATTEMPTS = 16`); `ChangeLifecycle.transition` (`if (store.putChange(...)) return updated`), `Publishing.settledPublished`. Read, not run (no Redis here).
- **Breaking after RC:** **yes** for the store layout (`list:open-changes` key and its value format) and for `openChanges()`'s shape if it becomes per-document or paged; the swallowed failure in (2) is not.
- **Fix:** (2) catch the failed removal in `putChange` and log it: S. (1) members instead of a map (as `list:documents`), plus a store method that lists open changes by document or state: M, and best done before RC because of the stored format.

#### R2C-3 (S3, M) One undecodable open change stops every shadow window; the pass is bounded by its interval and always starts at the same change
- **Module / symbol:** `core/control` `lifecycle/ControlMaintenance.closeShadowWindows`; `CoCacheControlStore.openChanges`.
- **What is wrong.** (a) `store.openChanges()` fails when one listed change does not decode (it "is not known to be terminal"). That is right for reclamation, which must know every revision an open change rests on. But `closeShadowWindows` calls it too, outside `attempt`, so one record a rolling upgrade or a bad write left undecodable ends *every* tenant's shadow pass, every minute, until someone finds it: no window closes, no staged change reaches READY. (b) The pass is `withTimeout(shadowInterval)` over changes in the store's list order, one window after another; when the windows to look at cost more than the interval (each look reads the reporters key and up to 50 reports), the pass is cut at the same place every minute, and a window behind that point is never looked at while the ones before it stay open. Nothing counts or logs how many windows a pass reached.
- **Evidence:** `ControlMaintenance.kt` `closeShadowWindows` (`store.openChanges().mapNotNull { … }` then `shadowing.mapNotNull { … }` under `withTimeout`), `CoCacheControlStore.openChanges` (the KDoc: "One that does not decode fails this"), `ControlProperties` `checkInterval` default 1 minute. Read, not run.
- **Breaking after RC:** no (behaviour of a periodic task).
- **Fix:** a tolerant listing for the shadow pass (skip and count an undecodable change, as `attempt` does for a failed one); rotate the start of the pass or look at the oldest-unlooked window first; log "looked at k of n windows" when the timeout cuts. S–M.

#### R2C-4 (S3, M) The control API cannot list changes
- **Module / symbol:** `core/control` `api/ChangeRoutes`, `ControlPlane`; port `ControlStore.openChanges()`.
- **What is wrong.** The only change routes are `POST /changes`, `GET /changes/{id}` and the verbs on an id. An approver (platform principal with `cosec:approve`) learns of an `AWAITING_APPROVAL` change only if its author tells them the id; a tenant administrator cannot find their own open changes after losing the id; nothing shows the staged change of a document. The records have this nowhere (`usability-triage-beta5.md` has no listing item; `testing.md` documents only the two routes). At the target (a dozen apps, many tenants, a platform approver for the grants beyond a tenant administrator's) this is the first thing an approver needs.
- **Why it belongs before RC.** Adding the route is additive, but it needs a store question the port cannot answer today: `openChanges()` returns every open change of every tenant, whole, so a listing "of tenant X" or "awaiting my approval" is a read of all open changes (R2C-2). The store layout for it (by document, by state) is the stored-format change of R2C-2.
- **Breaking after RC:** the route no; the store layout it needs yes (same as R2C-2).
- **Fix:** decide the layout with R2C-2 now; add `GET /changes?document=&state=` later. M.

#### R2C-5 (S3, S–M) An escalation's `reason` is a free string, its constants are duplicated, and the audit types are not marked
- **Module / symbol:** `core/control` `change/Escalation` (`reason: String`), `lifecycle/ChangeLifecycle.BREAK_GLASS` and `lifecycle/EscalationAnalysis.BREAK_GLASS`, `audit/ChangeEvent`, `RevisionRef`, `MovedHead`, `Escalation`.
- **What is wrong.** `Escalation.reason` is what the approval flow branches on (`informational` is `reason == TENANT_BINDING`; `Approvals.approve` decides "break-glass: record before approving" by `it.reason == BREAK_GLASS`), what the stored change record keeps, and what the audit JSON (`ChangeEventJson`, `escalations[].reason`, read by SIEMs from Kafka) carries. Its values come from four places: two companion constants of `Escalation`, `NOT_ANALYZED` and `BREAK_GLASS` private to `EscalationAnalysis`, and `verdict.reason.name` (an analysis enum, `NOT_COVERED`, `DENY_OVERLAP`, …). The KDoc lists some of them. **`BREAK_GLASS` is defined twice** (`ChangeLifecycle.kt:196` for `Approvals`, `EscalationAnalysis.kt:295` for the producer); if one is edited alone the gated `BREAK_GLASS_APPROVED` record before an approval silently stops (the escalation is still raised, so the approval itself still needs a second person), and no test names both constants.
  The listener port is `@CoSecSpi` and `ChangeRequest` is `@ExperimentalCoSecApi`, but `ChangeEvent` (13-argument constructor), `Escalation`, `RevisionRef`, `MovedHead` carry no marker: applications read them in a `ChangeListener` and, at RC, they are as frozen as the stable API.
- **Evidence:** `Escalation.kt` (the class and its companion), `EscalationAnalysis.kt:59,195,229,282,295`, `ChangeAuthority.kt:270,284`, `Approvals.kt:66`, `ChangeEventJson.kt` (`reason` written as a string), `control.api` (those classes listed without a marker).
- **Breaking after RC:** **yes** (`Escalation.reason`'s type, the unmarked classes' signatures; the JSON values would stay).
- **Fix:** one `Escalation.Reason` enum (names unchanged on the wire, an unknown name read from a record kept as `UNKNOWN`), one definition of break-glass; mark the audit event types `@ExperimentalCoSecApi` until a release has used them. M.

#### R2C-6 (S2, M) A store failure is a 500 on most control routes, a 503 on some; the port has no failure type
- **Module / symbol:** `core/control` `api/ControlHttp.handle` (the `catch (e: Exception)` → `Problem.INTERNAL_ERROR`) and `ControlStore` (every operation "throws" an unspecified exception).
- **What is wrong.** 25 sites map a store failure to `ChangeRejectedException(UNAVAILABLE)` one by one (`ChangeLifecycle.stored`, `EscalationAnalysis`, `Staging`, `StagingSlots`, `PlatformChecks`, …). The reads and writes outside them are not wrapped: `revisions.head`, the index reads and writes, `putHead` (`Publishing.publish`, `Proposals.propose`, `DocumentReads`, `DecisionQueries`, `ReferrerIndex.addEntries` on a failed reference add) throw whatever CoCache throws, and `ControlHttp` answers every exception it does not know with **500** `internal-error`, logged at ERROR. So when Redis is slow or down the control API answers 503 on a change read and 500 on a document read or a publish. A client or a gateway retries a 503 and not a 500, and an operator's alert on 5xx cannot tell "Redis is down" from "a bug". The port gives no type to catch: `ControlStore`'s KDoc says "throws", and `CoCacheControlStore` lets CoCache's exceptions through.
- **Evidence:** `ControlHttp.kt` lines 80–109 (the catch chain), `Publishing.kt:99` (`revisions.head`), `DocumentReads.kt` (no catch), `grep UNAVAILABLE core/control/src/main`: 25 sites, none around a head read.
- **Breaking after RC:** **yes**: what the control API answers on a store failure (500 → 503) is client-visible, and the exception contract of `ControlStore` (a documented unchecked type) is part of the port an application implements.
- **Fix:** a `ControlStoreException` (or `StoreUnavailableException`) in `core/control` that the port documents; `CoCacheControlStore` wraps CoCache's failures in it at the `read`/`put`/set helpers (it already has them); `ControlHttp` maps it to 503. Then the 25 local mappings can go. M.

#### R2C-7 (S3, S) Every failure of a back-reference set tells the operator to run `repair-references`
- **Module / symbol:** `backends/cocache` `control/ControlSets.failClosed`.
- **What is wrong.** `failClosed` catches every `Exception` of the five set operations and rethrows `IllegalStateException("<what> could not be read or written (<message>). A store written before 8.0.0-beta.5 must be converted first: run cosec-migrate repair-references.")`. A Redis timeout, a lost connection or a failover during a tenant's publish gets that text; so does every later outage, for as long as the code exists. The operator is sent to a migration command that does nothing for them, and the error is an `IllegalStateException` (so a 500 by R2C-6) where the cause was an outage. Only the format case (a value of the old format) should carry the advice.
- **Evidence:** `ControlSets.kt` `failClosed`. The design (`saas-referrers-design.md` §5) says the old format makes the read "unreadable", and does not say any other failure should be dressed alike.
- **Breaking after RC:** no (message text and exception type).
- **Fix:** catch CoCache's specific "value cannot be read as this type" failure only (it is what an old-format string is for a `SetStore`), add the advice there, and let other failures through unchanged. S.

#### R2C-8 (S3, M) `repair-references` costs bytes quadratic in the referrers, and its 1-hour lease is taken once
- **Module / symbol:** `core/control` `store/ReferrerIndex.repairReferences` (run by `migration/migrate` `ReferenceRepair.repair`); `ReferenceRepair.LEASE_DURATION`.
- **What is wrong.** For each document and each of its references, `repairReferences` reads the **whole** referrer set of that policy (`store.referrers(target, policy).none { it.referrer == key … }`) to see whether the member is already there. At 50,000 tenants that each refer to `base-access` and 20 shared permissions, that is 50,000 documents × about 21 sets of up to 50,000 members (`HGETALL`, about 1–2 MB each): of the order of a terabyte read, one set at a time, by a single-threaded `runBlocking`. The member add it is guarding is idempotent (`addReferrer` is an `HSET` of one field), and the document's own forward record (`index.indexed`) already says what it indexed; neither is used to avoid the read. The run holds the lease `repair-references` for one hour and never renews it (`ReferenceRepair.run` acquires once, `repair()` runs to the end), so a run that takes longer lets a second run start beside it, which the lease exists to prevent. The comment says "Longer than a run over the largest store takes", which holds for the store of the beta.4 tests, not for the target.
  A run that dies leaves the lease until it expires: `busy` prints "run again when it is done", with no holder and no time; the operator cannot tell a live run from a dead one and cannot clear it (the command has no option for it).
- **Evidence:** `ReferrerIndex.repairReferences` (the `filter { … store.referrers(…) … }`), `ReferenceRepair.kt` (`LEASE_DURATION = Duration.ofHours(1)`, one `acquireLease`), `RepairReferencesCommand.kt` (the `busy` message). `saas-scale-control-plane.md` did not measure repair (its §6 measures reclamation).
- **Breaking after RC:** no (a command's cost and messages). It matters before RC because beta.5 is the release whose upgrade must run it on a SaaS-sized store.
- **Fix:** compare against the document's forward record and add idempotently (no read of the set); renew the lease per document (or per batch); print the holder and the expiry when busy. M.

#### R2C-9 (S4, M) `ControlStore` is one 25-operation port for ten stores
- **Module / symbol:** `core/control` `store/ControlStore` (`@CoSecSpi @ExperimentalCoSecApi`, suppressed `TooManyFunctions` with "one method per store operation").
- **What is wrong.** One interface holds the heads, the revision records, the revision index, the back-reference sets, the change requests, the staging slots, the candidates (through `CandidateStore`), the document and open-change lists, the app list and the leases. An implementer (a store that is not Redis) must write all of them, and they have different needs: the leases and the lists want TTL and set semantics, the heads want compare-and-set across a read path shared with the data plane. Two of its operations already moved to set semantics for scale (`referrers`, `documents`), one is waiting (`openChanges`, R2C-2). It is the interface whose shape R2C-2 and R2C-6 change, which is the argument for deciding its split before RC: after RC the experimental marker no longer covers a change of this size.
- **Evidence:** `ControlStore.kt` (the interface), the `@Suppress("TooManyFunctions")` stays-entry, `CoCacheControlStore` (13 constructor parameters, one per cache).
- **Breaking after RC:** yes if split (an application that implements it), unless the marker stays through 8.0.x.
- **Fix:** decide with R2C-2 and R2C-6: keep one port and say in the marker's KDoc that the port may change in 8.0.x, or split into `DocumentStore` (heads, records, index, referrers, documents, apps), `ChangeStore` (changes, stages, candidates, open changes) and `Leases`. M.


### What I read and consider sound
- **Forward record and drops (`ReferrerIndex.dropGone`, `Revisions.publish`, `CTL-44`).** Followed a lost race (a conflicting publish of the same revision number), a late settle, and a reference kept across revisions: a member added at an older revision stays until the document drops the reference, and is then removed with the later ones; no member is left that no record names, except by a crash between the two steps, which `pruneReferences` repairs by design. The record grows with the document's references, not with referrers.
- **Reclamation (`Retention.reclaim`).** The cheap path (`reclaimable`: one index, one head, no lease, no write when nothing is to reclaim) is in. A document with something to reclaim takes a per-document lease and releases it. The index is written first (`reclaiming`), so a listed revision never misses its record.
- **Conditional writes (`ConditionalStores.put`, `deleteIf`, `acquireLease`, `releaseLease`).** An unknown outcome is read back, never repeated; a lease is renewed with `putIfMatch` over the digest read, and released with `deleteIfMatch`, so a lease another holder took is never removed.
- **The sets of record (`ControlSets`, `SetsOfRecord`).** Never expire, no local copy a read could answer from, failed reads throw. Note: the argument for the 1 ns local max age quotes CoCache 8.1.0 line numbers (`AbstractEngine.kt` 409-412, `SetEngine.kt` 203); `SetOfRecordReadTest` pins the behaviour, so a CoCache upgrade is caught by a test, not by the comment.
- **`ControlStore`'s KDoc against `CoCacheControlStore` and `InMemoryControlStore`:** consistent for the referrer, head and lease operations.
- **`ReferenceRepair` order and failure handling:** the legacy list is removed last and only when nothing failed, a failed document is listed and the exit is non-zero, a second run changes nothing; the format marker design of `saas-referrers-design.md` §9.3 was not re-read here.
- **`DocumentPublisher`/`DocumentRestorer`:** compile as every instance does, refuse break-glass bindings, and refuse a head that moved; `restore` states in its KDoc that the change listeners do not hear it.
