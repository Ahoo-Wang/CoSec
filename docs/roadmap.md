## 1. 现状

- **已发布**：`8.0.0-rc.1`（2026-11-25），第一个候选版本：应用编译时面对的公共面定下了（哪些稳定、哪些在 8.0 里仍是实验性的、哪些不对外）。从 beta.9 升级不需要顺序，有三处不再编译（[`upgrading-previews.md`](../wiki/operations/upgrading-previews.md)，“From 8.0.0-beta.9”）。Wow 的 `main` 自 2026-11-25 起跑在 beta.9 上。
- **下一步**：GA（`8.0.0`），或者候选版本里发现缺陷时的下一个 `rc.n`。**两者都要维护者说“发”**（rc.1 是单次授权）。GA 之前：真实项目用过 rc.1（已通知 Wow 升级）；`test/compat` 与系统测试的“上一版镜像”段已以 rc.1 为基线（#2054，§8 “接上四十九行”），GA 的门禁直接用；`upgrading-previews.md` 在 GA 时删除（7.x 指南已不依赖它，剩两处开头的链接随它一起去掉）；V7、V6 登记的修复在 GA 之后做。
- **在途的工作**（2026-11-25）：没有在途的代码 PR。rc.1 的内容与门禁见 §8 “接上四十八行”。没有等合入的代码 PR：#2057（8.x 的镜像不发布 `latest`）已合入；GA 的发布 PR 备成了草稿 #2056，不合入。等的是三件事：Wow 升级到 rc.1 的结果（Wow 的维护者已同意并入，升级在做）；fetcher 8 的候选版，及 CoSec 两个 TypeScript 包对它放宽对等依赖并测过（§6）；维护者说“发”。
- **目标场景**（维护者 2026-11-19）：上万租户的 SaaS，最大的租户十万以上成员，十来个应用、每个十来个角色，判定在网关统一做；方向是“内存换性能”。
  8.0 是 Kotlin API，Java 调用方不是目标。8.0 不考虑与 7.x 的兼容：按最终架构设计，存量数据由 `cosec-migrate` 转一次。
- **维护线**：`main` 是 8.0；`7.x` 只接收安全和关键修复，维护到 8.0.0 GA 之后 6 个月；`release/6.1.x` 只接收安全修复。修复先进 `main` 再回移（[CONTRIBUTING.md](../CONTRIBUTING.md)）。

## 4. RC1 之前

**门槛**（RFC 0008 §3.9，以及维护者 2026-11-21 的门槛）：

1. **两轮深度审查**。第一轮按模块读全部代码，用攻击者与运维两种眼光，发现编号定级，写明所读文件与触发方式，列出未读部分；修复；
   第二轮换会话重读修复后的结果，并专门覆盖第一轮未读的部分。第二轮没有未解决的 S1、S2 才切 RC 候选。
2. **发版提交上的门禁**全部通过：全量变异检查（`gh workflow run mutation.yml --ref main -f parallel=16`）、一百万次性质压力测试、
   系统测试（两种部署加 kind）、代码扫描与依赖告警为零。beta.7 的整套门禁用了 41 分钟。
3. 网关与控制面两个镜像的 AOT 冒烟在 CI 中通过（每次推送到 `main` 都运行）。
4. 真实项目用过 beta，且没有未解决的阻塞问题。
5. RC 之前人工复核一次“`main` 里没有只被测试使用的类型”（RFC 0008 §4.6.2 的 G5，不做成自动检查）：并入第一轮深度审查。
6. **维护者说“发”**。RC 与 GA 都要；beta 由协调者在门禁通过后直接发布。

**审查之前：合订 RFC**（维护者 2026-11-23：“继续压 RFC”，对“排在重置之后、第一轮审查之前”答“可以”）。把每份 RFC 的修订说明并回正文，被取代的说法删去，写成一份说清现状的规格：审查者是拿 RFC 当规格读的，合订也会顺带查出规格与代码不一致的地方。
样板是 RFC 0010（#1882）。做法：一份 RFC 一个 PR，派给子会话，协调者审；章节号与被引用的编号（X、N、K、C、Q、I、J、P、D 各项）不变；每句并进正文的话对着代码与规则登记表核实，以它们为准；不改变任何规则的含义；PR 说明里列出删掉了什么。修订说明只占 RFC 的约 17 %，合订的收益是清楚，不是体积。

**试点之后定下的做法**（RFC 0009，#1888；它的 PR 说明是其余各份的格式样板）：

- 先做核实表，再动笔：每条修订说明提到的类名、属性键、默认值、模块、规则号逐项对着主代码与登记表查（属性键另查 `RemovedProperties.kt`），表附在 PR 上。费时的是核实，不是并入。
- 修订并回它所修订的那一节；没有章节可并的内容才进文末新增的一节，每份至多一节。修订说明里维护者的决定可以追加新的决定编号。
- 范围是 RFC 本身加上登记表里指向它修订说明的 `source` 字符串（合订后它们会失去所指），在同一个 PR 里改，跑 `:conformance:check`。指向别的 RFC 的句子列给协调者。
- 规则表只做索引，措辞以登记表为准，每行的范围不得比登记表窄或宽；不枚举“哪几条有变异体”。
- 体积可以变大（RFC 0009 从 27.6 KB 到 36.4 KB）：修订说明省略的上下文要写全。
- 大的六份（0003、0004、0006、0007、0008、0013，110 到 190 KB）按章节族分成几个顺序合入的 PR。
- 不只查修订说明：没有修订说明的规范性正文也会过时（RFC 0012 §7.7 说外部同步的执行者“即信任根”，而 `CTL-81` 规定服务端口上没有信任根），修订说明也可能已被别处更晚的规则超越（RFC 0011 的 `STA-4` 被 `CTL-69` 改了）。每个规范性段落在登记表里搜涉及同一行为的规则。
- 不一致时照哪边写：登记表更严，或它的说法来自更晚的维护者决定，照登记表写并列出；代码或登记表比 RFC 更宽，保留 RFC 原句并列出，协调者裁决。
- 可以在原章节下加小节；原来没有规则表的 RFC 不新增规则索引；引用核对用 `scripts/rfc/check_refs.py`（#1895）。
- 正文过时多于修订说明的 RFC（0001、0002、0003）：按后续 RFC 的“与 RFC 0001 不一致”各表与今天的代码陈述现状，被取代的设计写成一句话加指向；被外部引用的编号（S、E、X、F、P、Q 各项）保留并写出今天的对应。体积因此可以减半（RFC 0002：88 KB 到 43 KB）。
- 标题本身是被取代的说法、且仓库里没有按标题文字的引用时，可以改标题，章节号不变。被 #1882 压缩成一行的“实现拆分”章节里，凡被别处引用的 `PR-n`，在那一行下列出标签与提交标题。
- 合订查出的过时代码注释（引用已不存在的任务、章节或设计）：只改注释，可以放进同一个 PR 或单开一个小 PR。

**合订时要带上的**（来自 #1887 与 #1888 的发现）：RFC 0003 的 2026-11-22 修订没有陈述 `SNP-24` 的两句（“族里还没有文档时按典型文档估算”“上界低于预热文档数的宿主仍然就绪”），合订时对着代码补上；
RFC 0003（2026-11-21 修订）与 RFC 0006 各有一个链接指向 #1881 删掉的审查文件；RFC 0006 里“RFC 0009 的同日修订”改指 RFC 0009 §11.2。

## 5. 维护者定下的规则

- **协调者的权限**（2026-11-21）：按建议执行，不停下来问；重大决策先记在本文，一段工作或一次发布收尾时列成一张单子与维护者讨论。
  请维护者决定时，每一项用白话说清楚，不只给代号。
- **发版**：beta 在门禁通过后直接发；RC 与 GA 要维护者说“发”。2026-11-23 维护者重申：“默认按你推荐，重大决策先登记，继续推进目标，授权你发布 beta 版。”
- **合入**：squash；不强推；不加 `Co-Authored-By`；严格分支保护下每个 PR 合入前同步 `main`；协调者审过才设自动合并。
- **共享文档**：`docs/roadmap.md`、RFC 与根 `AGENTS.md` 只由协调者改；会话在 PR 说明里列出应改的内容。
- **规则要硬，策略要灵活**（2026-11-24，原话）。协调者的理解：框架的不变量与格式的硬约束不留宽松模式、开关或“默认放过”；使用者表达意图的空间不因此变窄。例（RFC 0014）：保留字符是编译错误，同时有转义写法，任何真实路径都点得出名；不认识的“必须理解”成员就拒绝；凭证种类必须显式声明；运维的显式设置优先于推出的默认值。
- **能算出来的不配置**（2026-11-21）：配置是负担；新增 `cosec.*` 属性之前先问它能不能从进程观察得到的东西算出，算出的值要看得见（根 `AGENTS.md`）。
- **CoCache 的问题先提 issue**（2026-11-22）：原因在 CoCache 的发现，对着它的源码核实后到 `Ahoo-Wang/CoCache` 提 issue，不在 CoSec 里绕。
- **验证 beta 的真实项目不在本仓库点名**（2026-11-22）：它的仓库是私有的，本仓库是公开的；需求用通用的话写。
- **代码扫描告警**（2026-11-22）：协调者不自行关闭；能改代码的改代码，属于测试有意为之的列给维护者，由维护者关闭或授权。
  CodeQL 只分析主代码，不分析测试代码（维护者：“做”）。
- **并发测试失败不叫“偶发”**：报出测试、断言与运行，先问协调者，再决定是否重跑。失败在“解析依赖”这一步的作业只重跑它自己。
- **7.x 的缺陷先记账**：8.0 优先；能被外部利用的漏洞照常报告。

## 6. 已定、没有新事实就不重提的取舍

每条的理由在所列的 RFC 或规则里。

- 语句省略 `resource` 表示“所有资源”，不改成必填：动作已限定资源类型。
- `cosec.authorization.remote-ip.max-trusted-index` 默认 1，保留那条 WARN。
- 单条策略的语句数不设上限：授出分析的代价由比较预算封住，超出的部分算“未知”、要人批准。
- `cosec.authorization.snapshot.fail-closed.tenants` 默认为空（可用性优先）；已验证令牌的缓存默认开。
- 解不出来的吊销值按“存储读不了”处理（`PIP-7` 的例外），8.0 不改。
- 两个应用定义同名的系统角色：警告，不拒绝。
- DENY 语句禁止按原样匹配路径（`DOC-14`）；编码的分号与控制字符答 400（`PIP-30`）；`gateway` 模式必须写明谁能到达它才能启动（`STA-7`、`STA-9`）。
- 4.x、7.x 策略 JSON 的翻译器不做成库：存量用 `cosec-migrate` 转一次。
- 谁可以不经逐次审批写租户的角色：持有 `cosec:manage-roles` 的作者，且永远不含控制面自己应用的角色（`CTL-79`）。
- 经服务端口或门面的变更一律分析，那里没有信任根（`CTL-81`）；应用文档可经它改，平台文档只给运维。
- 预览版之间不承诺兼容：升级说明逐项写明要做什么（[`upgrading-previews.md`](../wiki/operations/upgrading-previews.md)）。
- 超时是 `cosec.pipeline.timeout` 的份额（`PIP-33`）；内存上限是堆的份额（`STA-12`）；快照驻留上限从堆与驻留文档的重量算出（`SNP-24`）。
- 影子采样率在 8.0 保持按实例的比例。
- 被拒绝请求的响应体可由宿主渲染，状态码与响应头仍由 CoSec 写（`PIP-34`）。
- 变异检查的“杀死”由对照证明；不缓存“已杀死”的结果；各分片不共享预热（RFC 0008 §3.7，[`ci-efficiency.md`](reviews/2026-11/ci-efficiency.md)）。
- 重载读到了更新的修订、而它的编译超过期限时，保留已安装的修订（`SNP-22`）：它是“重载失败时按已安装的文档决策”这一例外的一部分，由落后时长的告警与 `fail-closed.tenants` 约束；冷加载与重编译的编译超时失败即拒绝（审查发现 DR1-D-1，协调者 2026-11-23，RFC 0003 §4.4）。理由：与“`fail-closed.tenants` 默认为空，可用性优先”同一个取舍；编译超时不是“用不了”的答案。
- DENY 语句与限流规则的 `http` 路径模式，除原路径外再按去掉一个尾 `/` 的路径匹配一次；ALLOW 与边界不变（审查发现 DR1-C-9，协调者 2026-11-23，取代 `PIP-14` 里“尾斜杠按原样读”对拒绝方向的含义）。理由：`PIP-14` 对 `//`、`%2F`、`\` 答 400 是因为后端可能把它们读成另一条路径，这对尾斜杠同样成立；只在拒绝方向放宽，匹配得多是安全的方向，与 `DOC-14` 按方向判断是同一个思路。
- 成员关系只在加载它的进程里缓存，不读写 Redis（`MEM-5`，#1921，审查发现 DR1-D-2）：成员关系是授权的输入，事实源是应用的加载器；代价是每个实例各自调用加载器。寿命是运维的设置 `cosec.authorization.membership.ttl`（RFC 0001 §3.2 把撤销延迟的上限定为部署的显式配置）。
- 条目预算数文档授予的全部条目，手写的加上短格式派生的（`CTL-40`，#1923，DR1-B-1）；角色绑定的默认预算是 20,000：目标场景（100 个角色各 100 个权限）在新的数法下是 10,000，留两倍余量，最坏情况的授出分析约 10 秒。
- 过长的限流 key 以 SHA-256 命名桶，引擎里有一份手写的 SHA-256（#1917，DR1-C-1）：引擎只依赖标准库，`MessageDigest` 要经安全框架查找提供者；它不涉及密钥，由对照 `MessageDigest` 的测试守着。
- 带路由映射的宿主，对以 `/` 结尾、映射不上、去掉尾 `/` 后能映射的请求答 400；拒绝方向上模式或路径末尾的一个 `/` 不算数（DR1-C-9 的设计，`PIP-35`）。社交登录 state 的上界从 Redis 报告的内存推出（DR1-D-9）。
- API key 的存储在数据面“在声明处只读、由开关指定签发的进程”不在第一批做：`storage.md` 的权限表已写明数据面只需读（#1921）；记为后面一批的加固。
- 经 HTTP 转述的调用方带着它的全部属性（#1930，DR1-F-1）：一条针对属性的 DENY 在进程内与经服务端口两种部署里判定一致。
- `analyze` 读每份文档都要 `cosec:read`，调用方自己租户的也是（#1932，DR1-F-8）：`cosec:analyze` 允许提问，不等于允许看答案里列出的绑定。
- `CTL-58` 的措辞改成 `CTL-81` 的说法：它说的是服务端口单独能发布什么，行为没有变（#1929，DR1-E-4）。
- 会话记录的寿命是“写入时刻起一个刷新有效期”与会话终点中较早的一个，由已有的两项设置推出；每个主体在每个租户只保留最近开始的 64 个会话，第 65 个开始时最早开始的那个被删除，新的登录不被拒绝（`IDN-35`，DR1-G-2，协调者 2026-11-23）。理由：拒绝新登录会让拿到凭据的人把账号主人锁在外面；64 是常量，进程里没有能推出它的状态。`TokenFamilyStore.create` 的签名不变，文档多一句“超出时结束最早开始的”。
- 切换租户开出的会话记下登录开始的那个会话，后者登出、被撤销或不存在时前者的下一次刷新被拒（`IDN-36`，协调者 2026-11-23）。记的是根而不是直接的来源，否则隔一层就传不到。带这个成员的记录写成格式 2，8.0.0-beta.7 的实例读到就结束那个会话；`TokenFamily` 加一个可空字段，自定义的存储必须保存它，切换时读回一次，没保存就让切换失败。访问令牌活到自己的期限，不做即时撤销。
- 网关宿主上应用自己的控制器与函数式路由不经判定：在 enforce 模式下启动失败，除非 `cosec.gateway.unprotected-handlers` 列出它们（`STA-13`，协调者 2026-11-23，取代只打一行 WARN 的做法）。理由：与 `STA-2` 对执行器端点的做法一致，启动时点名失败好过运行时悄悄改变结果；让管道也把守这些请求要每个请求多做一次路由匹配，而且现有部署会在运行时开始拒绝。这个属性是信任声明，算不出来。
- 一份文档的变更记录有两个按文档的上限，都取 `cosec.control.revisions.max-count`：未结束的（超出答 409 `OPEN_LIMIT`，先放弃作者自己检查失败的草稿）与已结束的（在结束变更的写路径上删最老的），回收另删过了 `min-age` 且所发布修订已不保留的（`CTL-83`，#1943，DR1-E-2，取代“终态的记录不删除”）。回滚也受未结束上限约束，break-glass 不受：豁免回滚会重新打开无界增长。`ControlStore` 为此新增两个抽象方法。
- 控制面的文档缓存不新开堆份额：运行控制面的宿主上，文档那四分之一堆由管道的快照源、控制面的快照源与这个缓存各占三分之一，每宿主一个缓存（`STA-12`，#1940，DR1-F-5）。代价是这类宿主的每个快照源在 2 GiB 时常驻的典型租户从约 7,200 降到约 4,800；网关不受影响。
- 控制面一次调用为自己处理、缓存不保留的东西（大请求体的树、缓存不收的文档、候选的编译）占用一份按字节计重的工作内存预算：容量是堆的 1/8，不是 `HeapBudget` 的份额（它不是为性能而持有的内存）；放不下就在管道剩余期限的一半之内等，超时答 503；按租户排队、租户之间轮转，有别的租户在等时一个租户至多占一半；已经持有预算的调用不再等待（`CTL-85`，设计已确认，协调者 2026-11-23，DR1-F-3 与 DR1-F-4 剩下的部分）。不改成“先授权再解析”：它挡不住本来有写权限的租户管理员，而文档级的预检会拒绝只有条目级写权限的人。
- `k8s/control` 的清单不再声明“只有受信调用方能到达”，由各 overlay 声明，旁边带一个从不被任何策略放行的 pod 去连宿主三个端口的检查 Job；它每次 apply 之前要先删（`STA-7`，#1938，DR1-G-1）。理由：网络插件是否执行 NetworkPolicy，清单无法知道。
- 经 HTTP 转述调用方时，“只为仍在进行的请求签发身份”由 `runtime` 里签发身份的映射自己保证，不把请求是否结束的读法公开给 `control-http`；这类拒绝不到达宿主，应用侧记一条限频的 WARN（DR1-F-2，协调者 2026-11-23）。
- `cosec.key-prefix` 只接受 `[A-Za-z0-9_.-]`，含 `:` 的启动失败；吊销表的 `local-max-age` 限在 30 秒以内；enforce 模式的 Web 宿主上没有装 CoSec 的门时启动失败（S4 的 DR1-D-4、D-3、G-6，协调者 2026-11-23）。前两条是破坏性的，GA 之后不能再收紧，所以现在定。
- 自定义认证器证明的主体，凭证方法名不是 `api-key` 或 `service` 的算作人；机器客户端用这两个名字之一声明自己是工作负载（`IDN-34` 的陈述与 `extending.md`，#1946，DR1-C-3，协调者改记 S3）。改成按出处认定是不是人动的是授权语义，留到 8.1。
- **主体 id 不是空白**（issue #1889，`IDN-38`，2026-11-23）：空串与纯空白都不是主体 id。`PrincipalId` 自己拒绝是后盾；令牌、签发、`CoSec-Identity` 的读写、API key 各在入口按自己的方式拒绝（令牌无效 401，身份头格式错误，记录读不出来）。不 trim，`" a "` 仍是 id：id 不透明、按原样比较，trim 会把身份源区分的两个主体并成一个。这不是越权（造出空白 id 的只能是签发方、运维、应用自己的认证器或网络边界之内的调用者），坏的是“已认证就是某个人”这句话，定 S3。
- CI 取依赖失败时不启用后备主机：Maven Central 答 429 时 Gradle 不会去问下一个仓库，靠 `main` 上写的依赖缓存。

- **修订记录的体积上界**（`CTL-84`，DR1-F-6，2026-11-24）：一份文档的修订记录合计不超过 `max-count` 乘以文档上限（默认 400 MB），最近的 `max-count` 个算在内且总是保留；
  索引在最近之外至多 26,214 条。两个数都从已有的设置推出，没有新属性。超出时回收不到 `min-age` 的记录，计数并告警：`min-age` 从“保证”变成“在预算之内的保证”。
  计量由持有回收租约的实例给出，回收进行中保留上一轮的值，跨实例取最大值（求和在租约换手后的一轮里会重复计数）。
- **丢失的头写入只在留得下痕迹的地方查**（`CTL-86`，DR1-F-7，2026-11-24）：能查出的是“头丢了、其后写的索引条目还在”，即 Redis Cluster 的故障切换；单个主节点上二者一起丢，存储里没有痕迹，
  只有数据面的回退信号。规则与文档照实写明这个范围，不装作都能查出。信号在两处给：每小时的回收，以及索引从头重建、丢弃条目之前。控制面不自动把头前移：那是对一个没人看过原因的丢失自动动手。
- **请求结束之后保留的调用方，经 HTTP 也被拒绝**（DR1-F-2，`CTL-77`，2026-11-24）：检查放在签发身份的地方（`IdentityIssuer`），所以任何转发方都跳不过；HTTP 实现在发送之前答 403。
  转发身份在宿主上仍不查撤销（撤销那一半不动）：进行中的请求的令牌在请求开始时验证过，这条路径关掉的是“请求结束后继续以那个用户行事”。
- **控制面 HTTP 客户端**（DR1-F-17，2026-11-24）：跟随重定向的 `HttpClient` 在构造时被拒绝（重定向会把不带签名的 `CoSec-Identity` 送到它指向的地方）；应答体至多读 20 MB，
  是控制路由读的最大请求体的两倍，由一条测试钉住，没有属性。
- **带 `/` 的权限 id 只在新增时被拒**（DR1-E-5，`CTL-8`，2026-11-24）：目录是整份提交的，检查若打到已存的 id，一个已有 `a/b` 的应用以后任何目录变更都过不了。与条目同一条规则：已存的原样带着不拒。
- **镜像里的应用文件归 root**（DR1-G-8，2026-11-24）：进程不能改写自己下次启动要跑的 jar、启动脚本与 AOT 缓存；只有 `logs/` 与 `data/` 归 `appuser`。在 CoSec 镜像之上再构建并以 `appuser` 写 `/opt/<app>` 的镜像要改。
- **控制面 S4 的分拣**（E、F 两块，2026-11-24）：30 行里现在修 17、只改文档 7、留到 8.1 五、已覆盖 1。DR1-F-23（转换后的文档经 `apply` 发布得到同一个快照，缺专门的测试）不是 RC1 的门槛：
  RFC 0007 §12.3 本来就写明它“是目标，不是守护”。
- **本机构建的一条事实**（2026-11-24）：架构测试曾跑在根构建的 TRACE 日志配置下，每次约 2 GB 输出经测试进程的连接涌进构建进程，构建进程内存溢出后丢一个线程，两边互等，表现为挂死数小时。
  现在架构测试用自己的 INFO 配置（约 30 秒、180 KB），测试进程内存溢出即退出（#1955）。

- **没有受保护的条目**（DR1-E-3，`CTL-87`，维护者 2026-11-24：“按 B 继续”）：租户文档里的 DENY 归租户，它的管理员可在写权限范围内删除或放宽，平台写进去的也一样，是劝告性的；
  平台要租户解除不了的限制，用边界或平台文档。只做了一半、从不运行的 `protected` 检查与 `cosec:unprotect` 删除。把标志补全（方案 A）是文档格式的变更，留到 8.1。
- **控制面的工作内存预算**（`CTL-85`，2026-11-24）：堆的八分之一，不是 `HeapBudget` 的份额；按调用封顶（一次调用合计至多算整个预算，所以最重的调用总能独自跑完）；
  预算由控制面对象携带，一台宿主只有一个（审查时发现进程内门面曾经各有一个）；等待取管道超时的固定一半，因为控制路由没有自己的期限。
- **移除与新增引用的竞争分两步**（DR1-F-9，`CTL-30`，2026-11-24）：写头之前紧挨着再查一次引用方现在做；写入之后的复查与信号留到 8.1。剩下的那一瞬间，结果是引用方文档编译不过（失败即拒绝），规则与 RFC 照实写了，不再说“绝不漏掉”。
- **迁移工具不把被点名的主体的 key 迁到专用主体**（第二轮 DR2-M-1、DR2-M-9，`MIG-6`，2026-11-24）：DENY 按 id 点名、或应用的黑名单拉黑了 key 的 7.x 主体时，专用主体会逃出它。
  能静态判定的静态判定，判定不了的（`subject.id` 与另一个属性比较）同样拒绝。黑名单在应用自己的数据源里，工具看不到：给了 `--blacklist` 就照它拒绝，没给就不声称它无从知道的事。
- **已发布的变更不过期**（DR1-E-7，2026-11-24）：头是它自己的修订的变更，过期时按重试发布的同一条路径落成 `PUBLISHED`；头写入之后的冲突答 503 而不是 409。

- **转发的身份带全成员关系**（`IDN-39`，第二轮 DR2-F-1 与 DR2-C-1，维护者 2026-11-24：“加成员”）：`CoSec-Identity` 新增 `memberships`，只装 `roles` 没有的部分（别的空间的角色、附加策略），写入方总是写它；
  按身份头判定的宿主要求它在。不选“拒绝这类转发”：在多个空间有角色的用户很常见，那会让控制面的主要部署方式对他们不可用。编码改成流式写出，转发一次的分配比加成员之前还少。
- **租户切换出示令牌对**（`IDN-22`，维护者 2026-11-24：“方案 2：出示刷新令牌”）：切换开出一个可刷新的会话，所以要求出示它开出的东西；代际的规则与复用的后果同刷新是同一段代码。只凭 access token 不能切换。
- **尾斜杠的镜像按 S2 修**（`PIP-35`，第二轮 DR2-C-2，协调者从 S3 改记 S2，同它的镜像 DR1-C-9）：路径只在另一种尾斜杠写法下才映射时答 400，不在加载时拒绝以 `/` 结尾的路由（会打断生成的路由图）。
- **签发的有效期不超过配置的**（`IDN-37`，2026-11-24）：撤销的保留期从配置的有效期算，按调用给出更长的有效期会让令牌比它的撤销记录活得久；拒绝签发，不做“按观察到的最大值延长保留期”，那在多实例之间算不出来。
- **越权项按语句分组并封顶**（`CTL-88`，第二轮 DR2-E-1）：组的 subject 带片段数与全部片段的摘要，审批覆盖的仍是它看到的那些片段。
- **变更记录的字节上界由乘积给出**（`CTL-83`，第二轮 DR2-E-2）：单条有上限、未结束的在提出时累加、已结束的不测量（测量就是每次读遍已结束的记录，正是要消除的放大）。
- **读未结束的变更按实际大小称重**（`CTL-85`，第二轮 DR2-E-4，协调者审 #1980 时发现）：逐条读，每条在解码之前按存储大小计入工作预算，小记录不占。不按上限一律计：那会让整台宿主同时只能有三个提案。
  为此 `ControlStore` 加了有默认实现的 `eachOpenChange`。
- **fetcher 与 CoSec 8 客户端的时机**（维护者 2026-11-24：“按这个安排”）：应用的前端在后端上 CoSec 8 时就从 `@ahoo-wang/fetcher-cosec` 换到 `@ahoo-wang/cosec-fetcher`，客户端跟的是服务端的契约；fetcher 去掉 CoSec 包的那个大版本在 RC1 之后出候选版，CoSec 8.0 GA 当天转正，同一天在 npm 上把旧包标记为弃用，并为 CoSec 7.x 的用户留 6.x 维护分支；CoSec 的两个 TypeScript 包在 GA 之前把对等依赖放宽到同时接受它（在候选版上测过）。fetcher 的版本号不与 CoSec 对齐。**这个大版本是 fetcher 8，跳过 7**（维护者 2026-11-25：“你来开始 fetcher v8 版本，fetcher 跳过 v7”）；协调者在 fetcher 仓库派会话做：移除 `fetcher-cosec` 与 `fetcher-react` 里的安全 hooks、备 `8.0.0-rc.1`，发布仍要维护者说“发”。
- **下一个版本是 beta.9 而不是 RC1**（维护者 2026-11-24：“按你推荐”）：RC 的含义是契约不再变，而 RFC 0014 的改动里有一批破坏性的（凭证种类、令牌的新声明、保留元字符、身份头的读法、登出语义）；它们不该第一次露面就在 RC 里。真实项目的验证要对着 RC 要冻结的那套接口；零窗口的承诺要两个真实版本（beta.9 与 RC1）混跑来证明。
- **候选版本写作 `8.0.0-rc.1`，不写 `RC1`**（协调者 2026-11-25，已告知维护者）：semver 按 ASCII 比较预发布标识，大写排在小写之前，`8.0.0-RC1` 在 npm 上会排在 `8.0.0-beta.9` 之下（对已用 beta.9 客户端包的项目是降级）；`-rc.n` 也与一直在用的 `-alpha.n`、`-beta.n` 一致。`CONTRIBUTING.md` §7 与分发标签表随之改了，并有守卫拒绝大写的预发布写法。
- **`TokenAuthenticator` 的 `acceptUnavailableRevocations` 没有默认值**（维护者 2026-11-25：“改成必填”）：原先默认接受，手工构造认证器的应用在撤销存储读不到时放行，不管运维怎么配。对稳定 API 的一处破坏性改动，与公共面的其余改动一起进 RC1（“直接进 RC1”）。
- **审计与判定的集合是可以增长的集合**（2026-11-25，随公共面一起定）：`DecisionEvent.Kind`、`StatementRef`、`BindingRef`、`AuditDecision`、`AuditReasonCode`、`AuditEventKind`、`AuditVia`、`Escalation.Reason` 在次版本里可以增加成员，消费者接受不认识的值。
- **凭证种类贯穿登录、令牌、校验器与身份头**（RFC 0014 的 R3，维护者 2026-11-24：“同意加”，范围扩大后再问，答“同意”）：`Identity.Credential`、`VerifiedToken`、`TokenSubject` 三处必需参数，没有默认值；访问令牌带 `cosec.kind`；缺失与未知一律按工作负载；break-glass 要求 CoSec 自己的令牌且是人。不按校验器定种类（同一个身份提供方既给人也给机器签令牌），不靠文档约束机器登录。
- **保留元字符**（RFC 0014 的 R4，`DOC-15`，维护者：“同意保留”）：路径、类型化资源、动作三种模式与路由图保留 `[ ] ( ) | ! ^ $ \`，未转义即编译错误，没有宽松模式；字面量经 `\` 转义写出，转义在编译时解除；路径模式里字面的 `\` 是编译错误（含它的请求路径一律 400，这样的模式永远匹配不到）。升级前用 `cosec-migrate` 的只读扫描找出受影响的文档。

- **切换租户后登出，连同登录的原会话一起结束**（`IDN-40`，维护者 2026-11-24：“一起结束”）。已发出的访问令牌在过期前仍有效；按会话的撤销索引留到 8.1（§7）。

## 7. 留到 8.1
