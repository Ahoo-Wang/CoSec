## 1. 现状

- **已发布**：`8.0.0-beta.7`（2026-11-23）。从 beta.6 升级无需任何动作。
- **下一步**：先合订其余十二份 RFC（见 §4），再做两轮深度审查，发现修完之后是 RC1。原定等周额度重置（2026-11-27 23:00 UTC）；2026-11-23 查到周额度已用 0 %，
  等待的理由不再成立，维护者说“继续推进 V8 目标”，当天开工。
- **在途的工作**（2026-11-23）：**RFC 的合订做完了**（十三份；0013 是 #1905，已审、等合入）。**第一轮深度审查**：第一路的 A 至 D 四块已交（#1908、#1909、#1912、#1913），没有 S1；第二路（会话 `e-h`）在审 E 至 H。**修复**：会话 `fix-1` 在修 A 至 D 里 S2、S3 的六条（§4）。同时至多两路会话。
- **目标场景**（维护者 2026-11-19）：上万租户的 SaaS，最大的租户十万以上成员，十来个应用、每个十来个角色，判定在网关统一做；方向是“内存换性能”。
  8.0 是 Kotlin API，Java 调用方不是目标。8.0 不考虑与 7.x 的兼容：按最终架构设计，存量数据由 `cosec-migrate` 转一次。
- **维护线**：`main` 是 8.0；`7.x` 只接收安全和关键修复，维护到 8.0.0 GA 之后 6 个月；`release/6.1.x` 只接收安全修复。修复先进 `main` 再回移（[CONTRIBUTING.md](../CONTRIBUTING.md)）。

## 4. RC1 之前

**门槛**（RFC 0008 §3.9，以及维护者 2026-11-21 的门槛）：

1. **两轮深度审查**。第一轮按模块读全部代码，用攻击者与运维两种眼光，发现编号定级，写明所读文件与触发方式，列出未读部分；修复；
   第二轮换会话重读修复后的结果，并专门覆盖第一轮未读的部分。第二轮没有未解决的 S1、S2 才切 RC 候选。至多两路，Opus，Effort 为高。
2. **发版提交上的门禁**全部通过：全量变异检查（`gh workflow run mutation.yml --ref main -f parallel=16`）、一百万次性质压力测试、
   系统测试（两种部署加 kind）、代码扫描与依赖告警为零。beta.7 的整套门禁用了 41 分钟。
3. 网关与控制面两个镜像的 AOT 冒烟在 CI 中通过（每次推送到 `main` 都运行）。
4. 真实项目用过 beta，且没有未解决的阻塞问题。
5. RC 之前人工复核一次“`main` 里没有只被测试使用的类型”（RFC 0008 §4.6.2 的 G5，不做成自动检查）：并入第一轮深度审查。
6. **维护者说“发”**。RC 与 GA 都要；beta 由协调者在门禁通过后直接发布。

**审查之前：合订 RFC**（维护者 2026-11-23：“继续压 RFC”，对“排在重置之后、第一轮审查之前”答“可以”）。把每份 RFC 的修订说明并回正文，被取代的说法删去，写成一份说清现状的规格：审查者是拿 RFC 当规格读的，合订也会顺带查出规格与代码不一致的地方。
样板是 RFC 0010（#1882）。做法：一份 RFC 一个 PR，派给子会话，协调者审；章节号与被引用的编号（X、N、K、C、Q、I、J、P、D 各项）不变；每句并进正文的话对着代码与规则登记表核实，以它们为准；不改变任何规则的含义；PR 说明里列出删掉了什么。修订说明只占 RFC 的约 17 %，合订的收益是清楚，不是体积。

**试点之后定下的做法**（RFC 0009，#1888；它的 PR 说明是其余各份的格式样板）：

- 先做核实表，再动笔：每条修订说明提到的类名、属性键、默认值、模块、规则号逐项对着主代码与登记表查（属性键另查 `RemovedProperties.kt`），表附在 PR 上。费时的是核实，不是并入。
- 修订并回它所修订的那一节；没有章节可并的内容才进文末新增的一节，每份至多一节。修订说明里维护者的决定可以追加新的决定编号。
- 范围是 RFC 本身加上登记表里指向它修订说明的 `source` 字符串（合订后它们会失去所指），在同一个 PR 里改，跑 `:conformance:check`。指向别的 RFC 的句子列给协调者。
- 规则表只做索引，措辞以登记表为准，每行的范围不得比登记表窄或宽；不枚举“哪几条有变异体”。
- 体积可以变大（RFC 0009 从 27.6 KB 到 36.4 KB）：修订说明省略的上下文要写全。
- 大的六份（0003、0004、0006、0007、0008、0013，110 到 190 KB）按章节族分成几个顺序合入的 PR。
- 不只查修订说明：没有修订说明的规范性正文也会过时（RFC 0012 §7.7 说外部同步的执行者“即信任根”，而 `CTL-81` 规定服务端口上没有信任根），修订说明也可能已被别处更晚的规则超越（RFC 0011 的 `STA-4` 被 `CTL-69` 改了）。每个规范性段落在登记表里搜涉及同一行为的规则。
- 不一致时照哪边写：登记表更严，或它的说法来自更晚的维护者决定，照登记表写并列出；代码或登记表比 RFC 更宽，保留 RFC 原句并列出，协调者裁决。
- 可以在原章节下加小节；原来没有规则表的 RFC 不新增规则索引；引用核对用 `scripts/rfc/check_refs.py`（#1895）。
- 正文过时多于修订说明的 RFC（0001、0002、0003）：按后续 RFC 的“与 RFC 0001 不一致”各表与今天的代码陈述现状，被取代的设计写成一句话加指向；被外部引用的编号（S、E、X、F、P、Q 各项）保留并写出今天的对应。体积因此可以减半（RFC 0002：88 KB 到 43 KB）。
- 标题本身是被取代的说法、且仓库里没有按标题文字的引用时，可以改标题，章节号不变。被 #1882 压缩成一行的“实现拆分”章节里，凡被别处引用的 `PR-n`，在那一行下列出标签与提交标题。
- 合订查出的过时代码注释（引用已不存在的任务、章节或设计）：只改注释，可以放进同一个 PR 或单开一个小 PR。

**合订时要带上的**（来自 #1887 与 #1888 的发现）：RFC 0003 的 2026-11-22 修订没有陈述 `SNP-24` 的两句（“族里还没有文档时按典型文档估算”“上界低于预热文档数的宿主仍然就绪”），合订时对着代码补上；
RFC 0003（2026-11-21 修订）与 RFC 0006 各有一个链接指向 #1881 删掉的审查文件；RFC 0006 里“RFC 0009 的同日修订”改指 RFC 0009 §11.2。

**第一轮深度审查的发现候选**（合订与日常审查中记下的，审查时定级；已分给对应的块）：

- `Approval` 与 `SimulatedRequest` 的 `principalBindings`、`breakGlass` 构造参数默认为 `true`，漏写时取的是更宽的值；`Subject` 正是为此不给默认值（RFC 0009 §3）。合订会话没有找到因此放宽的路径（`ApprovalCodec` 严格读取）。
- **动作名拼错的 DENY 静默不匹配**：控制面不按目录校验动作名与资源类型（目录声明的是权限 id；RFC 0005 §5.1 原说会校验，RFC 0007 §6.2 的 V4 现在是锁出检查）。没有任何校验或警告指出一条 DENY 的动作不是任何路由或目录会产生的。
- 登记表里措辞不一或落后于代码的规则：`GRT-2` 说“平台管理员审批”而 `APR-1` 说“持有 `cosec:approve` 的另一个人”（RFC 0007 Q10 是后者）；`DOC-1` 仍按“到达某个 `Broken` 条目的请求”描述，而 CoSec 的编译器是整份文档编译或整份失败。
- 没有守卫测试的规范性说法：`OFF` 时引擎不创建任何 trace 对象（只靠 JMH 的分配数字）；需要反射的每个库模块自带 `RuntimeHintsRegistrar`（只有 `cosec-cocache` 有，靠两个镜像的 AOT 冒烟）；快照编译 p99 不超过 200 ms（没有专门的基准）。
- 没有测试或门禁的目标：转换后的文档经控制面 `apply` 发布得到同一份快照（RFC 0007 §12.3 留下的性质，RFC 0008 §3.5）；端到端的 k6 预算没有工作流；`jmh-v7-v8.yml` 记录每操作分配但只判定吞吐比（RFC 0008 §3.8）。补上，或在审查时定为不做。
- [`docs/security/8.0-rc-review.md`](security/8.0-rc-review.md) 的引言仍按 2026-10-29 的两轮写；新的两轮开始时改成 §4 的定义（RFC 0008 §3.9 已改）。
- `PIP-4`（任何 SPI 的失败或超时都不产生放行，RFC 0006 §10.2 的 P13）只有三个例子测试，没有跨全部阶段的随机故障注入；`ALG-10` 引用 `PIP-5` 而 RFC 0005 §6.2 引用 `PIP-14`。
- RFC 0011 §5 的“`platform/*` 只依赖发布的模块”没有守卫测试（`DependencyRulesTest` 查的是反方向）；今天没有违反。补一条 `test/architecture` 的规则。
- RFC 0009 §5 把 8.1 的属性叫 `principal.type`，RFC 0010 §1 的表叫 `subject.type`，属性目录里的名字是 `subject.*`：8.1 设计时统一。

## 5. 维护者定下的规则

- **协调者的权限**（2026-11-21）：按建议执行，不停下来问；重大决策先记在本文，一段工作或一次发布收尾时列成一张单子与维护者讨论。
  请维护者决定时，每一项用白话说清楚，不只给代号。
- **发版**：beta 在门禁通过后直接发；RC 与 GA 要维护者说“发”。2026-11-23 维护者重申：“默认按你推荐，重大决策先登记，继续推进目标，授权你发布 beta 版。”
- **派发**（2026-11-21）：子会话一律 Opus，Effort 按任务难易度定，同时至多两路在干活；按五小时窗口控制节奏，不撞线。
  名额空出后协调者直接派下一路，不等维护者点（2026-11-23：“名额空出后直接派，不用等我点”）。
  有 PR 等合入时不手动触发基准对比、全量变异检查或一百万次压力测试，发版门禁除外。
- **合入**：squash；不强推；不加 `Co-Authored-By`；严格分支保护下每个 PR 合入前同步 `main`；协调者审过才设自动合并。
- **共享文档**：`docs/roadmap.md`、RFC 与根 `AGENTS.md` 只由协调者改；会话在 PR 说明里列出应改的内容。
- **能算出来的不配置**（2026-11-21）：配置是负担；新增 `cosec.*` 属性之前先问它能不能从进程观察得到的东西算出，算出的值要看得见（根 `AGENTS.md`）。
- **CoCache 的问题先提 issue**（2026-11-22）：原因在 CoCache 的发现，对着它的源码核实后到 `Ahoo-Wang/CoCache` 提 issue，不在 CoSec 里绕。
- **验证 beta 的真实项目不在本仓库点名**（2026-11-22）：它的仓库是私有的，本仓库是公开的；需求用通用的话写。
- **代码扫描告警**（2026-11-22）：协调者不自行关闭；能改代码的改代码，属于测试有意为之的列给维护者，由维护者关闭或授权。
  CodeQL 只分析主代码，不分析测试代码（维护者：“做”）。
- **并发测试失败不叫“偶发”**：报出测试、断言与运行，先问协调者，再决定是否重跑。失败在“解析依赖”这一步的作业只重跑它自己。
- **7.x 的缺陷先记账**：8.0 优先；能被外部利用的漏洞照常报告。

## 6. 已定、没有新事实就不重提的取舍

每条的理由在所列的 RFC 或规则里。

- 语句省略 `resource` 表示“所有资源”，不改成必填：动作已限定资源类型。
- `cosec.authorization.remote-ip.max-trusted-index` 默认 1，保留那条 WARN。
- 单条策略的语句数不设上限：授出分析的代价由比较预算封住，超出的部分算“未知”、要人批准。
- `cosec.authorization.snapshot.fail-closed.tenants` 默认为空（可用性优先）；已验证令牌的缓存默认开。
- 解不出来的吊销值按“存储读不了”处理（`PIP-7` 的例外），8.0 不改。
- 两个应用定义同名的系统角色：警告，不拒绝。
- DENY 语句禁止按原样匹配路径（`DOC-14`）；编码的分号与控制字符答 400（`PIP-30`）；`gateway` 模式必须写明谁能到达它才能启动（`STA-7`、`STA-9`）。
- 4.x、7.x 策略 JSON 的翻译器不做成库：存量用 `cosec-migrate` 转一次。
- 谁可以不经逐次审批写租户的角色：持有 `cosec:manage-roles` 的作者，且永远不含控制面自己应用的角色（`CTL-79`）。
- 经服务端口或门面的变更一律分析，那里没有信任根（`CTL-81`）；应用文档可经它改，平台文档只给运维。
- 预览版之间不承诺兼容：升级说明逐项写明要做什么（[`upgrading-previews.md`](../wiki/operations/upgrading-previews.md)）。
- 超时是 `cosec.pipeline.timeout` 的份额（`PIP-33`）；内存上限是堆的份额（`STA-12`）；快照驻留上限从堆与驻留文档的重量算出（`SNP-24`）。
- 影子采样率在 8.0 保持按实例的比例。
- 被拒绝请求的响应体可由宿主渲染，状态码与响应头仍由 CoSec 写（`PIP-34`）。
- 变异检查的“杀死”由对照证明；不缓存“已杀死”的结果；各分片不共享预热（RFC 0008 §3.7，[`ci-efficiency.md`](reviews/2026-11/ci-efficiency.md)）。
- 重载读到了更新的修订、而它的编译超过期限时，保留已安装的修订（`SNP-22`）：它是“重载失败时按已安装的文档决策”这一例外的一部分，由落后时长的告警与 `fail-closed.tenants` 约束；冷加载与重编译的编译超时失败即拒绝（审查发现 DR1-D-1，协调者 2026-11-23，RFC 0003 §4.4）。理由：与“`fail-closed.tenants` 默认为空，可用性优先”同一个取舍；编译超时不是“用不了”的答案。
- CI 取依赖失败时不启用后备主机：Maven Central 答 429 时 Gradle 不会去问下一个仓库，靠 `main` 上写的依赖缓存。

## 7. 留到 8.1

GA 之前不派发。

- **外部身份提供者（IdP）的 RFC**，8.1 的第一份设计：资源服务器模式（JWKS 验签、issuer 映射到租户、校验 audience、声明经平台文档里的显式映射变成成员关系）；
  不透明令牌的内省（RFC 7662）；`cosec-login`、`cosec-social` 里的 OIDC 授权码登录；不做 SAML。接缝都是新增（[RFC 0010](rfc/0010-ga-extension-points.md) §1）。
  设计时要回答：JWKS 的获取与缓存不阻塞事件循环；JWKS 不可用时失败关闭，已缓存的密钥能用多久；算法白名单；拒绝 `jku`、`x5u`；密钥轮换；
  同时接受 CoSec 自己的令牌与外部令牌时怎么组合认证器；“拒绝带 `act` 的令牌”这道闸门要移到每个认证器。
- **社交登录提供者的 SPI**：与 IdP 的 RFC 一起设计。
- **快照的整体版本号**（8.1 的第一项实现）：每个实例今天每 10 秒对持有的每份文档各做一次条件读；改为先查一个版本号，变了才逐份查。
  做法是加法（`SnapshotDocumentStore` 带默认实现的新方法、一个新键、默认关闭），并保留间隔更长的逐份确认兜底；变成默认行为留到 9.0。
- **大文档**：8.0 的边界是文档 8 MB、主体绑定 1,000、派生绑定 50,000 与 `CTL-40` 的条目预算。等真实部署碰到上限再做：租户文档按空间或应用拆分、修订存差异或压缩、增量编译。
- **影子采样率的集群级设计**：按实例算出的速率会扭曲一个窗口证明了什么。
- **给应用自己的认证器一个一等的“工作负载”标志**（8.0 里只能把凭据命名为 `api-key` 或 `service`），与外部 IdP 一起设计；**运维端口上拒绝 `service` 凭证**（只能发现错误配置，#1898 的说明）。
- **native image 的 CI 冒烟**（`cosec-gateway-server`，含去掉一条 hint 的反向用例；RFC 0001 §3.10）；`cosec-kafka` 用数据绑定写审计记录而没有 `RuntimeHintsRegistrar`（RFC 0006 §12，只影响 native image）。
- **租户读取目录和系统角色**（`GET /apps/{app}/catalog`，只返回目录与角色定义）与**“可授出范围”的只读预检**（控制台灰显授不了的权限）：纯新增，出自 RFC 0012 §12。
- **手工装配 `Pipeline` 转为稳定**；**测试工具场景里的外部属性**（8.0 里读 `ext.*` 的文档在测试工具中不编译，文档已写明）。
- **网关镜像支持 API key**（成员关系从哪来要先设计）；**`gateway` 模式的身份头签名**；**被拒绝的转发身份进审计与追踪**；**`JwtSigning` 的非对称密钥工厂**；
  **在 CoSec 自己的令牌上追加检查的钩子**（8.0 里放进策略条件）。
- **大版本依赖**（Renovate 面板 #771）：JDK 25、Redis 8 镜像、pnpm 12、TypeScript 7、vite 8、vitest 5、jsdom 31、Node 26。

排队、尚未派出的小事：Renovate 的小更新（Gradle 9.9.2 已由 #1884 合入，BlockHound 1.0.19 是 #1883；其余 mermaid 12.3、Node 22.23.5、dokka 2.3.0、fluent-assert 1.3.0、pnpm 11.29 等 Renovate 逐个开出后审）；
请 Wow 出基于 CoSec beta.7 的 10 beta。
